# 立项：GPU 呈现层直通 + 文本测量卸载 CPU（2026-11-01）

> 来源：2026-11-01 RK3568 板端 485 联调实测——
> 「主站错误 154 / 请求 158」追查到底：链路上零字节错误，
> 根因是**从站 CPU 100% 饱和 → 事件循环滞后 42~659ms → 485 应答被饿死**
> → 主站 1s 轮询周期里一半请求在途未回（SKIP 16 次 vs RECV 8 次）。
>
> 同日已落地 GPU 接入（Mali-G52 跑通，见 §1.1），但**CPU 仍未卸下来**。
> 本立项定义「真卸 CPU」的目标、方案、风险、验收门槛、回退开关。
>
> 本文件是**立项书**（不是实施记录）。实施另开分支。

---

## 0. 先说清这件事的位置：不是「GPU 没接上」，是「接上了但 CPU 不在那儿」

2026-11-01 已完成的 GPU 接入（EGL/GLES 后端）把**绘制**搬到了 Mali-G52：

| 指标 | 接入前（GLX/llvmpipe） | 接入后（EGL/Mali-G52） |
|---|---|---|
| 渲染器 | llvmpipe (LLVM 11.0.1) | **Mali-G52 (OpenGL ES 3.2)** |
| 进程 RSS | 149.2 MB | **109.5 MB（−27%）** |
| VmData | 183.4 MB | **119.9 MB（−35%）** |
| `swrast_dri.so` 是否加载 | 是 | **否（0）** |
| CPU | 100% | **100%（没降）** |

省下的 40~64 MB 是 llvmpipe 的 LLVM JIT 匿名内存。但 **CPU 一格没降**。

原因不在「呈现管线」，而在**文本测量**。见 §2。

## 1. 事实基线（全部为实测，非推测）

### 1.1 GPU 通路已通

- `Drive/Posix/Graphics/XPlatformGraphics_egl.c`（新增）：EGL/GLES 后端，
  `eglGetDisplay(X11)` + `eglCreateWindowSurface(X11 Window)`，
  **不用 GBM**（板端 GBM 路线实测全失败：`gbm_bo_create` 连 ioctl 都没发
  就返回 NULL，Mesa 的 `libgbm.so.1` 与厂商 `libmali.so` 的 gbm 符号并存但
  Mesa 版在这板子不可用）。
- `Drive/Posix/Graphics/XPlatformGraphicsBackend.h`（新增）：GLX/EGL 双后端
  内部契约 + 运行期开关 `XGUI_GL_BACKEND=egl|glx`（默认 EGL 优先）。
- `XGpuRenderDriver_gl.c`：加 `m_isGles` 标志（按 `glGetString(GL_VERSION)`
  含 `"OpenGL ES"` 判定）；纹理上传快速路径用的
  `GL_BGRA + GL_UNSIGNED_INT_8_8_8_8_REV` 是**桌面 GL 专有**，
  GLES 上 `GL_INVALID_ENUM` ⇒ 快路径条件加 `&& !self->m_isGles`。
- 板端实测：`[gl-info] vendor=ARM renderer=Mali-G52 version=OpenGL ES 3.2`，
  `/dev/mali0` 被进程持有，`swrast_dri.so` 计数 0。截图核对颜色/布局/中文
  渲染全部正确。

### 1.2 但 CPU 仍 100%，且**与呈现管线无关**

`XGPU_PRESENT=swap`（GPU 直通呈现，`XWidget.c:11480` 的 `presentToWindow`
腿）实测确实生效：

| 页面 | 默认（readback 路径） | `XGPU_PRESENT=swap`（直通路径） |
|---|---|---|
| page 0（按钮演示） | CPU 4% | CPU 4% |
| **page 19（时钟与 DDNS）** | **CPU 98%** | **CPU 97%** |
| page 18（Modbus 从站） | CPU 99% | CPU 99% |

**swap 路径对 page 19 完全无效**——这直接排除了「呈现管线是瓶颈」的假设。

框架自带的 `wprof` 画像（`XGUI_W_FRAME_PROF=1`）印证：

```
[wprof] tot=8 (71.293ms) p2w=8 (20.494ms) drb=0 (0.000ms) soft=0 (0.000ms)
        paint=8 (50.685ms) commit=8 (20.498ms) gap=3 (832.142ms) ...
```

- `soft=0`（软件呈现腿未走）、`drb=0`（readback 未走）——**呈现侧已经干净**。
- `paint=50.685ms` 是 CPU 大头，但注意 `gap=832ms`：**帧间隔极长**，
  说明 CPU 不是被「一帧内画太多」烧掉的，而是**每秒被某个周期性任务打满**。

### 1.3 CPU 开销的真正位置：文本测量

页面差异是决定性证据：

| 页面 | 内容 | CPU |
|---|---|---|
| page 0 | 按钮演示（静态） | **4%** |
| page 18 | Modbus 从站（表格 + 1s 定时刷新） | 99% |
| page 19 | 时钟与 DDNS（1s 定时刷新） | 99% |

两页的共同点：**有 1s 周期定时器反复 `XLabel_setText_2` 改文本**，
每次 `setText` 触发**控件树重绘**。

链路（`Src/XGui/Widget/XLabel.c` → `Src/XGui/Widget/XWidget.c`）：

```
XLabel_setText_2 (2934)
  └─ XLabel_setText
       └─ label_updateLabel (2761)        ← 推 sizeHint/minSizeHint（3 次 label_sizeForWidth）
            └─ XWidget_updateGeometry + XWidget_update   ← ★ 触发控件树重绘

XWidget 重绘（XWidget.c:10903）：
  XPainter_begin_image(&painter, image)    ← ★★ 绑**软件 XImage**，不是 GPU
  XWidget_paintTree → 各控件 paintEvent → XPainter 逐控件软件光栅
```

### ★★ 真正的 CPU 大头：双画布（**这是本立项的核心发现**）

**架构事实**（代码实测）：

| 画布 | 归属 | 谁在画 | 成本 |
|---|---|---|---|
| **软件 XImage** | 框架后备缓冲（`buffer-mode=software-single surface=framework`） | **控件树全部内容**（`XPainter_begin_image`） | **CPU 逐像素光栅化** |
| **GPU FBO** | GPU 会话 | 仅 GPU 直通腿的图元（fillRect/glyphQuad 等） | GPU |

即：**同一帧内容被画了两次**——一次 CPU 画进软件 XImage（控件树），
一次 GPU 画进 FBO（GPU 腿的原语），最后 `presentToWindow` 把 **FBO** blit 上屏。

⇒ **`XGPU_PRESENT=swap` 只切换了「上屏取哪块画布」，没切换「控件树画在哪」**。
⇒ 所以 CPU 不降（这解释了 §1.2 的实测），**而 GPU 那次画其实是白画的**。

**字形路径进一步佐证**（`XPainter.c:13349`）：

```c
if (painter8x16CanAntialias(painter) &&
    painter->m_deviceKind == XPainterDevice_Image &&      /* ← 只在 Image 时走 */
    painterDrawOutlineGlyphSoftwareAA(...))               /* ← 软件逐像素 AA */
    return true;
```

`XPainterDeviceKind` 只有 `None / Image / Picture` 三值（`XPainter.h:447`），
**没有 GPU 设备类型**。GPU 字形（图集）是**旁路**（`painterGpuDrawOutlineGlyph`），
只有 painter 绑了 GPU 后端（`m_gpuBackend`，`XPainter.c:8246`）才走到。
控件树绑的是 `begin_image` ⇒ `m_deviceKind = Image` ⇒ **软件 AA 路径**。

**推论**：文本相关的 CPU 开销（逐字形软件 AA 光栅 + 逐像素混合）是
**「控件树画在软件 XImage 上」的直接后果**，不是独立问题。
把控件树画到 GPU 上，这部分成本**自然消失**，无需单独优化文本测量。

⇒ **因此 §3.1 的「文本测量缓存」降级为次要项**（仍值得做，但非主项）；
**主项是 §3.2 的「控件树 GPU 直通」**：让 painter 绑 GPU 后端，
控件树内容直接画进 FBO，不再经过软件 XImage。

## 2. 目标与范围

### 2.1 目标

**G1（首要）**：板端从站在 485 联调负载下，事件循环滞后（`WHEEL lag`）
中位数 **≤ 20ms**、p99 **≤ 100ms**，使 485 应答 RTT p99 回到 **≤ 50ms**
（当前实测 1~4s）。

**G2**：文本测量不再逐帧逐码点重复——同一内容同一尺寸的测量结果可复用。

**G3**（可选，见 §5）：呈现管线真正 GPU 直通（`present=1`），
消灭「GPU 画完再 readback 回 CPU」的双份搬运。

### 2.2 明确的范围边界

**不在本次范围**（避免重蹈「以为改呈现就能省 CPU」的覆辙）：

- 帧泵/事件循环架构改造（帧率策略、限频）——另议。
- 字体光栅化缓存（`XFONT_GLYPH_ALPHA_CACHE_ENTRIES`）的容量调优：
  **2026-10-31 已从 512 扩到 16384**，静态表仅约 1.6 MB，
  而页面的 IR/HR 表格与时钟标签**文本内容各不相同**，
  灰度缓存**命中不了**（缓存键含字形位图，文本变 ⇒ 键变），
  扩容对本问题无效。**不要动它**（动了会退回 2026-10-31 之前的
  「逐帧全量 FT 重光栅」CPU 风暴）。

## 3. 方案

### 3.1 任务 A：控件树 GPU 直通（**主项，对症 G1/G3**）

**问题（§1.3 的双画布）**：控件树画在软件 XImage（CPU 逐像素光栅），
GPU FBO 只是旁路 ⇒ 每帧内容画两遍，CPU 那遍还是全量的。

**方向**：

| # | 方向 | 说明 | 风险 |
|---|---|---|---|
| **A0** | **painter 绑 GPU 后端画控件树** | 让 `XWidget_paintTree` 的 painter 走 `m_gpuBackend`（`XPainter.c:8246` 已有绑定路径），控件内容直接进 FBO，软件 XImage 不再参与 | **高**：需处理「GPU 后端不可用」的降级、离屏/图片控件的混合、字形图集与软件 AA 的口径一致性 |
| A1 | 帧级直通：`XWidget` 整窗重绘时，painter 直接绑 GPU 会话 | 只在**整窗重绘**这一种情况下走 GPU，其余（局部脏区）仍走软件 | 中：局部脏区路径不受益 |

**建议**：先做 A0 的**可行性验证**（把 page 19 的控件树切到 GPU 后端，
量 CPU 与画面），再决定是否全量推广。

**跨平台要求（用户明确要求）**：
- **必须在框架公共层**（`Src/XGui/`），**不得**放进 `Drive/` 下任何平台目录。
- 复用**既有的** `XPlatformBackingStore` 三形态抽象
  （`SoftwareSingle / SoftwareDouble / PlatformSurface`），
  **不得新增第四种形态**（`XPlatformBackingStore_bufferMode` 是跨平台统一判定，
  新增形态会破坏所有平台的形态契约）。
- 平台差异全部收敛到 `Drive/<平台>/` 的**提交实现**里（Windows 已有
  `platform-surface` 先例，参照 `Drive/windows/` 的实现）。
- 字形口径：GPU 图集与软件 AA 必须**逐像素一致**
  （框架已有 `XGUI_ALPHA_INVARIANCE` 探针用于此，改造后须复跑）。

**验收门槛**：
- page 19 / page 18 在 485 联调负载下 CPU **≤ 25%**（当前 99%）。
- `WHEEL lag` 中位 **≤ 20ms**（当前 42~659ms）。
- 主站侧：请求/错误比 **≥ 0.95**（当前 158/154 ⇒ 错误几乎等于请求）。
- 画面与改造前**逐像素一致**（`xwd` 截图对比 + `XGUI_ALPHA_INVARIANCE` 探针）。

### 3.2 任务 B：文本测量结果缓存（**次项**）

**问题**：`label_updateLabel` 每次 `setText` 都做 3 次全量逐码点测量
（sizeHint 一次 + minSizeHint 宽一次 + 高一次）。

**方向（按性价比排序）**：

| # | 方向 | 预期收益 | 风险 |
|---|---|---|---|
| B1 | **`sizeForWidth` 单次测量复用三处**：sizeHint / minSizeHint 宽 / minSizeHint 高，其中 minSizeHint 高在非 wrap 时等于单行高 ⇒ 可由已测结果推出 | 单次 `setText` 的测量量降到 **1/3** | 需核对 wrap/非 wrap 两分支语义，不能想当然 |
| B2 | **测量结果按（文本内容 + 字体 + 宽度）缓存** | 文本不变的标签（表格里 99% 的单元格）直接命中 | 缓存键设计要含字体与宽度；换字体/改宽度需失效 |
| B3 | **增量测量**：只测变化的码点区间，宽度累加 | 最彻底 | 改动面大，文本换行/对齐都要重算 |

**建议顺序**：先 B1（低风险、立即 3 倍），再 B2，A3 只在不够时再上。

**跨平台要求**：同 A0 —— 必须在 `Src/XGui/`（`XLabel.c` 或 `XPainter.c`），
字体度量接口（`XPainter_textWidthRange`）本身已是跨平台抽象，
缓存挂在它之上即可天然跨平台。

**验收门槛**：
- 文本宽度**逐位一致**：改动前后同一字符串同一字体同一宽度的
  `XPainter_textWidthRange` 结果必须完全相同（宽度变了会引发布局漂移，
  这是本项最大的正确性风险）。
- page 19 / page 18 的 CPU 不劣于 A0 单独实施时的水平（不得回退）。
  这是本项最大的正确性风险）。

### 3.3 任务 C：后备缓冲形态与 X11 平台表面（**配套项**）

**现状**：`XGPU_PRESENT=swap` 已能走 `presentToWindow`（FBO→默认帧缓冲
blit + swapBuffers），板端实测 `present=10`、`readback` 从 18 降到 5、
事件循环 lag 中位从 159ms 降到 62ms。**但 CPU 收益为零**（因为瓶颈在任务 A）。

**要做的事**：

1. **后备缓冲形态**：让 POSIX/X11 侧支持 `XPlatformBackingStoreMode_PlatformSurface`
   （当前 X11 恒 `software-single surface=framework`；Windows 是
   `platform-surface`）。
2. **GPU surface 与 X11 窗口的交换**：EGL window surface 直接
   `eglSwapBuffers`（探针已验证像素级上屏可行）。

**跨平台要求**：`XPlatformBackingStore` 已有 `SoftwareSingle /
SoftwareDouble / PlatformSurface` 三形态抽象（`Src/XGui/Platform/XPlatformBackingStore.c`
的 `XPlatformBackingStore_bufferMode` 是**跨平台统一判定**），
本任务 **必须复用这三个形态，不得新增第四种**。
平台差异全部收敛到 `Drive/<平台>/` 的提交实现里（Windows 已有
`platform-surface` 先例可直接参照）。

**风险**（必须写进实施记录）：
- **呈现中间态可见**：GPU 直通时「绘制期中间态」可能被扫上屏
  （软件路径靠双帧交替规避）。`buffer-mode` 契约明写「可见表面看不到
  绘制期中间态」——GPU 单缓冲会破这条契约。**必须验证**。
- **与脏区语义交互**：框架是多矩形脏区，GPU 直通若整窗重画会退回
  「上屏 3.96MB/次」的旧问题（2026-10-30 已修，见
  `docs/485轮询性能排查与修复_20261029.md`）。**不得回退**。
- fbdev 平台**故意不提供**平台表面（直写可见 fb 会把中间态扫上屏），
  本任务不得把 X11 的做法套到 fbdev 上。

**验收门槛**：
- 板端 `present` 计数持续 > 0 且 `readback` 归零（当前 5/周期）。
- 画面**无中间态闪烁**（录像逐帧核对）。
- 帧率**不低于**当前基线（当前 GPU 路径 29 FPS，软件路径 ~29 FPS）。

### 3.4 任务 D：帧泵与限频（**后置，视 A/B/C 结果定**）

若 A+B+C 后 CPU 仍高，再查帧泵本身：`gap=832ms` 说明帧间隔极长却 CPU 满载，
需查「帧间隙」定义是否把**阻塞等待**也算成了 CPU 时间（wprof 的
`gap` 段名有歧义，需先澄清其语义再动）。

## 4. 风险与回退

| 风险 | 等级 | 对策 |
|---|---|---|
| 文本宽度测量改动导致**布局漂移**（表格列宽、标签换行） | **最高** | A2/A1 都必须先补「改动前后逐位一致」的回归断言；宽度口径含字体与缩放，缓存键必须齐全 |
| GPU 直通破坏「中间态不可见」契约 | **高** | 上屏前用 `xwd` 抓帧序列逐帧核对；保留 `XGPU_PRESENT` 开关可退回 |
| GPU 直通回退「整窗上屏」⇒ 485 尖刺复现 | **高** | 以 `docs/485轮询性能排查与修复_20261029.md` 的 235ms→7.4ms 为红线，回归即停 |
| 文本测量缓存无失效路径 ⇒ 换字体/改宽度后显示旧宽度 | 中 | 缓存键含字体句柄与宽度；字体变更/控件 resize 必须失效 |
| 跨平台风格走样（把平台特定逻辑漏进 `Src/`） | 中 | 评审逐条查「`Src/` 里不得出现平台 API」；度量缓存放 `Src/` 但只用跨平台抽象 |

**回退开关**（全部为运行期环境变量，无需重编）：

| 开关 | 作用 | 回退到 |
|---|---|---|
| `XGUI_GL_BACKEND=glx` | GPU 后端 | GLX（llvmpipe 软件） |
| `XGPU_PRESENT` 不设 | GPU 呈现腿 | 默认 readback 路径 |
| （任务 B 新增）`XGUI_TEXT_MEASURE_CACHE=0` | 文本测量缓存 | 直测（本次新增，实施时定名） |

## 5. 验收（板端真机，全部可复现）

**环境**：RK3568 192.168.0.10（`slave485.mode`，ttyS3/115200）；
PC 侧 CH343 USB-485 = COM17 作主站（`XGUI_DEMO_MB_SERIAL=1`
`XGUI_DEMO_MB_SERIAL_PORT=COM17` `XGUI_DEMO_MB_AUTOSTART=master`）。

| # | 验收项 | 门槛 | 测量方法 |
|---|---|---|---|
| V1 | 从站 CPU（联调负载下） | ≤ 25% | `/proc/PID/stat` utime+stime 差分 |
| V2 | 事件循环滞后 | 中位 ≤ 20ms、p99 ≤ 100ms | 板上日志 `[WHEEL] lag=` |
| V3 | 485 应答 RTT | p99 ≤ 50ms | 主站 `XGUI_DEMO_MB_POLLTRACE=1` 的 `RECV dt` |
| V4 | 主站请求/错误比 | ≥ 0.95 | 主站页统计行 |
| V5 | **无内存泄漏** | `xmemory_stat_systemBytes` 恒定、fd 恒定 | 持续 485 负载 ≥ 10 分钟，gdb 读记账变量 |
| V6 | 画面正确 | 颜色/布局/中文/表格全对 | `xwd` 截图逐项核对 |
| V7 | GPU 生效 | `renderer=Mali-G52`、`swrast=0` | `XGPU_PROF=1` |
| V8 | 文本宽度逐位一致 | 改动前后完全相同 | 回归断言（实施时建） |
| V9 | **画面逐像素一致** | 改造前后截图逐像素一致 | `xwd` + `verify/xwd_diff.py` 已有工具 |

**V1/V2/V4 的当前基线（2026-11-01 实测，可直接对比）**：

| 项 | 当前值 | 目标 |
|---|---|---|
| page 18/19 CPU | 98~99% | ≤ 25% |
| page 0 CPU（对照） | 4% | —（说明 GPU 通路本身不耗 CPU） |
| `WHEEL lag` 中位 | 159ms（默认）/ 62ms（swap） | ≤ 20ms |
| 主站请求/错误 | 158 / 154 | 比值 ≥ 0.95 |
| 板端 485 应答 | 1~4 秒（POLLTRACE `RECV dt`） | p99 ≤ 50ms |

**V5 的当前基线（2026-11-01 实测，可直接对比）**：
持续 485 负载下 19 次采样，`xmemory_stat_systemBytes` 恒定 **1,273,238**
（零增长）、`fd` 恒定 20、`VmData` +4 KB（噪声）。

## 6. 排期建议

| 阶段 | 内容 | 产出 |

**为什么 A0 优先于其它项**：A0 直接对着**唯一的大头**——控件树在软件
XImage 上的逐像素光栅化（§1.3）。B（文本测量）只是 A0 的**衍生开销**，

（§1.2 已实测：`swap` 路径对 page 19 完全无效）。

**先做 P0 的可行性验证再全量投入** —— 若验证发现「控件树无法整体走 GPU」
（例如局部脏区路径、离屏控件、混合控件的约束），则需要重新评估，
避免全量改造后才发现架构不通。
