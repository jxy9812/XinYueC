# HSF 服务端按会话内存占用 —— 板端长测、根因定位与修复（实施记录 2026-11-11）

> 起因：用户要求「监视板子上的 HSF 服务端和客户端，并用桌面客户端多次连接断开，
> 长时间监测是否有内存泄漏」；随后追问「你确定泄漏了吗」，触发本轮的两轮更正，
> 最后定位到框架层根因并已修复。

## 1. 最终结论

| 对象 | 结论 |
|---|---|
| 板端 `HsfClient`（C） | **无泄漏**。2h04m：VmData 49 076→49 208 kB、堆 45.94→46.25 MB 平台期、fd 恒 10、线程恒 1（堆计数 + 真实进程内存双证） |
| 板端 `HsfServer`（C） | **有框架层泄漏：每次 SQL exec 净漏 40 字节（= `sizeof(XSqlQuery)` 的可用块）**。已定位并修复（见 §3） |
| 会话回收（板端 Linux） | 正常。3 135 接入 / 3 134 断开，并发路数始终 ≤12，最后回到 1 路 |

**根修**：`Src/XCore/XCode/XSql/XSqlQuery.c` 的 `XSqlQuery_init_database()`
在**二次初始化**时把「堆对象」标志清掉了 ⇒ `XClassDelete` 不释放查询对象壳。
修复后：1 347 次 exec 的净留**全部为 0**，C 组堆增长由 131 B/会话降到 14 B/会话。

## 2. 两次自我更正（留档：判据比结论重要）

**首版**：「服务端每次会话泄漏 ≈400 字节，定位在落盘写库路径」。
错在一条没验证的前提——我断言「SQLite 走系统 malloc、不进 XMemory 计数」，
实际 `Library/sqlite/sqlite3_xin_memory.c` 用 `sqlite3_config(SQLITE_CONFIG_MALLOC)`
把 SQLite 的分配器接到了框架 `XMalloc_System/XFree_System` ⇒ **SQLite 的
页缓存/WAL/b-tree 全都计入堆计数**。于是把 SQLite 写侧内存算成了泄漏。
首版引用的「曲线平台化」也不成立——那轮 `[heap]` 停止打印是**事件循环停摆**。

**二版**：「确有泄漏，≈42 B/INSERT，在框架 SQL 执行路径」。
这次用四组对照把「写库副作用」与「执行路径本身」分开（B 组写失败、
C 组写成功但丢弃，斜率几乎相等 ⇒ 与落库无关），但**没找到具体分配点**，
且仍把「SQLite 侧的量」混在总数里。

**三版（本轮）**：把 SQLite 自己的内存计数打开（`SQLITE_DEFAULT_MEMSTATUS`
被编成 0，`sqlite3_memory_used()` 恒为 0）⇒ 框架堆与 SQLite 内存并排打印
⇒ 确认「与落库无关的那部分」100% 是框架自己的对象；再用定点字节探针
（exec 边界 / 结果对象析构 / 建查询各步）逐段对账 ⇒ 抓到那 40 字节的壳。

## 3. 根因与修复

### 机制

```c
void XClass_init(XClass* object) {          /* Src/XCore/XClass/XClass_virtual.c */
    ...
    Set_Class_Memory(object, XCLASS_DEFAULT_MEMORY_TYPE);
    Set_Class_IsHeap(object, false);         /* ← 把「堆对象」标志清掉 */
}

XSqlQuery* XSqlQuery_create_database(...) {
    XSqlQuery* query = XSqlQuery_create();   /* create_ex 里 Set_Class_IsHeap(query, true) */
    if (query) XSqlQuery_init_database(query, database);   /* ← 二次初始化 */
}

void XSqlQuery_init_database(...) {
    XSqlQuery_init(query);                   /* → XClass_init → 标志被清回 false */
    ...
}

void XClass_delete_base(XClass* object) {
    XClassDeinit(object);
    if (!is_heap) return;                    /* ← 壳不释放！ */
    if (memory && memory->free) memory->free(object);
}
```

⇒ **每次 `XSqlDatabase_exec/exec_utf8` 漏一个 `XSqlQuery` 对象壳**。
`sizeof(XSqlQuery)`=32 字节（XClass 16 + m_result 8 + m_ownsResult 1 + 填充），
Windows 下 malloc 可用块 40 字节 ⇒ 与实测 **恒定 net=40** 完全吻合。

### 修复（`Src/XCore/XCode/XSql/XSqlQuery.c`）

```c
void XSqlQuery_init_database(XSqlQuery* query, const XSqlDatabase* database)
{
    XMemory* mem;  bool wasHeap;
    if (!query) return;
    mem  = Class_Memory(query);
    wasHeap = Class_IsHeap(query);
    XSqlQuery_init(query);                    /* 会清堆标志/复位分配器 */
    if (wasHeap) {                            /* ← 根修：原样夺回 */
        Set_Class_IsHeap(query, true);
        if (mem) Class_Memory(query) = mem;
    }
    ...
}
```

### 验证

| 项 | 修复前 | 修复后 |
|---|---|---|
| exec 级净留（定点探针） | 恒定 **+40 B/次**（1 020/1 023） | **0**（1 347/1 347） |
| C 组（写入被 IGNORE 丢弃、库不长）堆增长 | 131 B/会话 | **14 B/会话** |
| D 组（正常落库）堆增长 | ≈340 B/会话 | ≈176 B/会话，且**其中 ≈全部是 SQLite 自己的内存**（堆 +70 616 / sqlite +69 896） |
| 框架 SQL 回归 | — | `XinYueC_Static --test xdata`：**SQL=通过**（全量通过） |

**修后剩下的增长不是泄漏**：D 组里那 16 次「+4 376 字节」正好是
**SQLite 每新增一个 4 KB 页 + WAL 索引项**（页缓存，受 `cache_size` 约束）。

## 4. 影响评估

- 每会话 3 条会话日志 + 历史采样各一次 exec ⇒ 板端 ≈130 B/会话。
- 板端历史采样周期 60 s ⇒ **40 B × 1 440 ≈ 57 KB/天**（≈21 MB/年），
  这是长期跑现场最实在的那一份（客户端重连少，影响可忽略）。
- 修复后这部分归零。

## 5. 四组对照实验（判别口径，本轮最有用的一招）

同一构建、同一压测速率（4.4~5.3 会话/秒）、各 1 200 会话，只改「落盘行为」：

| 组 | 落盘状态 | 堆斜率（修复前） | 折合每次 INSERT | 判读 |
|---|---|---|---|---|
| A | 库**打开失败**（只读文件） | +1.6 B/会话 | — | 基准：无 exec 路径 ⇒ 会话/订阅路径无关 |
| B | 库开，写**失败**（`BEFORE INSERT` 触发器 `RAISE(ABORT)`） | +130 B/会话 | ≈43 B | exec 路径跑、写被拒 |
| C | 库开，写**成功但丢弃**（触发器 `RAISE(IGNORE)`，库不长） | +127 B/会话 | ≈42 B | 与 B 几乎相等 ⇒ 与错误分支、落库都无关 |
| D | 库开，写成功且落库 | +340 B/会话 | ≈113 B | 多出的 ≈210 B/会话 属 SQLite 写侧 |

**页缓存贡献可忽略**：`PRAGMA cache_size` 压到 64 页（256 KB）后斜率几乎不变
（+332…+368 vs 默认 +370…+394 B/会话）。

**「SQLite vs 框架」怎么拆**：临时把 `Library/sqlite/CMakeLists.txt` 的
`SQLITE_DEFAULT_MEMSTATUS=0` 改成 1 并在堆追踪里多打一行 `sqlite3_memory_used()`
⇒ C 组实测 `sys +78 720 / sqlite +8` ⇒ 与落库无关的那部分 **100% 是框架对象**。

## 8. 通用教训（值得进 AGENTS.md）

1. **`XClass_init` 会清掉「堆对象」标志**：任何「`_create` 之后再调 `_init` 变体」的
   路径都会让 `XClassDelete` 跳过释放 ⇒ 每次调用漏一个对象壳。
   本项目里 `XSqlQuery_create_database → XSqlQuery_init_database` 就是这个形状。
2. **判泄漏必须把「第三方库自己的内存」和「框架内存」拆开**：本项目里 SQLite 的
   分配器接进了 XMemory ⇒ 堆计数里混着 SQLite 的页缓存；
   `SQLITE_DEFAULT_MEMSTATUS=0` 又让 `sqlite3_memory_used()` 恒为 0 ⇒ 拆分要改编译开关。
3. **「曲线平台化」要先排除「打印者停了」**：本轮那轮长压测的 `[heap]` 不再打印
   是事件循环停摆，不是缓存到顶。
4. **板端交叉编译：口宏不传＝编出 Windows 缺省口，板端 485 全离线**（2026-11-11 实踩）：
   直接调 `verify/board/build_board.sh` 而**不传** `BOARD_BUS_A_PORT` /
   `BOARD_BUS_B_PORT` 时，它的缺省是 **`COM17`/`COM18`**（Windows 口径）⇒
   板端日志 `串口 COM17 打开失败（错误码=3）——整路跳过` ⇒
   **串口上的 5 台设备（变频器/温湿度/浊度×2/流量计）全部消失**，界面表现为
   「设备少了一半」。**正解**：走一键脚本 `Tools/posix/hsf-board-deploy.sh`
   （它默认 `--bus-a /dev/ttyS3 --bus-b /dev/ttyS4` 且**同步工作区→WSL**）；
   手工调 `build_board.sh` 必须显式带
   `BOARD_BUS_A_PORT=/dev/ttyS3 BOARD_BUS_B_PORT=/dev/ttyS4`。
   另：**只把改动文件塞进 WSL 树编译 ≠ 编了本地改动**——板端要的是**当前工作区**，
   一键脚本的同步步骤不可省。
5. **一键部署的同步环节有两个真 bug（2026-11-11 已修 `Tools/posix/hsf-board-deploy.sh`）**：
   ① **同步只传「与 HEAD 不同」的文件** ⇒ 合并/回退时**被还原成 HEAD** 的文件
      （如 `HsfTheme.h`、`HsfExport.h`）永远不刷新到 WSL 树 ⇒ 板端编译报
      `HSF_THEME_KEY_SKIN undeclared` 之类的**假错**（本地树明明是对的）。
      修法：**每次都用 `git archive HEAD` 重建基线**，再叠加工作区差异。
   ② **Windows 检出的 .sh 带 CRLF** ⇒ 同步进 WSL 后 dash 读 `set -eu\r`
      报 `set: Illegal option -`，脚本直接挂。修法：同步后对
      `*.sh/*.py/*.cmake` 归一 LF。
   另：**改公共头后必须全量重编**（Windows ninja 缺头文件依赖，增量编译会
   拿旧 obj 编过、给出假绿）；本轮就是桌面增量编译"通过"、板端全量编译
   才暴出问题。
