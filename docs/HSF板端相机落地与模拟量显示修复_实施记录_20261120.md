# HSF 板端相机落地 + 模拟量显示修复 —— 实施记录（2026-11-20）

> 本轮起点：相机在板端已能出帧，但「重启相机后画面就没了」「CPU 吃满」
> 「画面偏色」「触摸全屏退出后点不动」「温度传感器断线显示 -50℃」
> 「历史页模式列显示不全」等问题在一天内集中暴露。
> 本记录按**问题 → 根因 → 修法 → 实证**组织，可直接当现场排查手册用。

## 一、相机：硬件 JPEG 编码在板端固件上**不可用**（结论性，勿再尝试）

### 1.1 现象

`mppvideodec ! mppjpegenc`（全硬件）CPU 仅 6%，但：

- 真实画面**偏紫/棕**（截图实见）
- 体积 **12KB/帧** vs 软件编码 **113KB/帧**（9 倍差距 ⇒ 色度信息几乎全丢）
- `q-factor` 从 10 调到 96，体积只从 11KB 变 14KB（**质量参数几乎失效**）

### 1.2 已试尽的手段（全部无效）

| 尝试 | 结果 |
|---|---|
| `q-factor` 10 / 30 / 50 / 80 / 96 | 11 / 12 / 12 / 13 / 14 KB —— 与色度错乱同形 |
| `mppvideodec dma-feature=true`（零拷贝） | 14KB，与基线**完全一致** |
| `mppvideodec dma-feature=true ! video/x-raw(memory:DMABuf) ! mppjpegenc` | caps 被退回普通内存，仍 14KB |
| `mppjpegenc` 强制 I420 / NV21 / RGB 输入 | **静默 0 帧**（rc=0、无报错） |
| 给 `mppvideodec` 加强制格式 capsfilter（I420/NV21/NV16/RGB） | **静默 0 帧**（原生只出 NV12/NV16） |
| 让解码器输出 `colorimetry=bt601` | `not-negotiated` |
| `videoconvert` 软转 601 后再硬编 | 能出帧，但 CSC 本身慢 70 倍（失去意义） |

### 1.3 定性

该固件（gstreamer-rockchip **1.14.4**）的 `mppjpegenc` 在 NV12 输入下
**把色度平面解释错了**（U/V 交错按平面读），叠加相机 H.264 是 **BT.709**
而 JPEG/JFIF 约定 **BT.601** ⇒ 颜色错误无法通过参数修正。要根治需升级到
含 JeffyCN/mirrors PR #68 之后的插件版本，但该补丁只补 DMABuf sink caps，
**不修色度计算**，收益不确定、风险大 ⇒ 本轮不采用。

**另需澄清**：RK3568 的 **Mali-G52 不参与视频编解码**（VPU / JPEG Codec 是
独立硬件块）；GPU 只能做 GL 着色器的 CSC/缩放，且在服务进程里
`EGL_BAD_PARAMETER`（无 display/GBM 上下文）⇒ 指望 GPU 救不了这条路。
板上也没有 `rgaconvert` 元素（RGA 由 MPP 内部隐式使用）。

## 二、相机：管线定稿 —— **抽帧必须放在昂贵的色彩转换之前**

### 2.1 成本拆解（704×704，板端实测）

| 环节 | 单帧 CPU | 说明 |
|---|---|---|
| `mppvideodec`（VPU 硬解） | **1.1 ms** | 与帧率无关地解每一帧 |
| `videoconvert` NV12→I420 | **147 ms** | **占总成本 96%**（GStreamer ORC 在解码器 buffer 上退化；同 jpegenc 在普通 buffer 上只要 6.6ms） |
| `jpegenc` | 6.6 ms | 与 quality 几乎无关 |
| `videoscale` | 很贵 | 同样在解码器 buffer 上 |

### 2.2 两种顺序的实测差距（6 秒窗口，25fps 源）

| 管线顺序 | CPU | 出帧 |
|---|---|---|
| `videoconvert → videorate → videoscale → jpegenc`（**旧**） | **295%**（吃满 3 核） | 4 帧 |
| `videorate → videoconvert → jpegenc`（**新**） | 5fps **93%** / 2fps **31%** | 61 / 25 帧 |

⇒ **CSC 成本 ∝ 输出帧率，不再 ∝ 相机帧率**。这是本轮最大的性能收益。

> 口径说明：上表是 `filesrc` 离线流 6 秒窗口的 A/B（含起播，均值偏低）；
> 实机稳态见 §九（2fps **47%**、5fps 97%、10fps 176%）。两者结论同向，
> **别把 31% 与 47% 当成矛盾**（测法不同）。

### 2.3 定稿管线（服务端 `camera.py::_build_cmd`）

```
gst-launch-1.0 -q fdsrc fd=0 ! h264parse ! mppvideodec
  ! videorate ! video/x-raw,framerate=<fps>/1
  ! videoconvert n-threads=2 ! video/x-raw,format=I420
  ! jpegenc quality=<Q> ! fdsink fd=1
```

三条硬约束（实测踩过，改之前先读）：

1. **不许给 `mppvideodec` 加强制格式 capsfilter** ⇒ 静默 0 帧。
2. **`jpegenc` 不吃 NV12** ⇒ 必须 `videoconvert` 产出 I420（旧代码在
   `videoscale` 后钉 `format=NV12` ⇒ 管线构建期失败、gst 立即退出 ⇒
   `_pump` 的 sink 写失败走 dead 分支**静默返回**、无任何日志）。
3. **不做 `videoscale`**（缩放也在解码器 buffer 上贵）；要更省 CPU 请把
   **相机子码流分辨率**调小（成本 ∝ 像素数）。

### 2.4 `quality` 与 CPU **无关**（实测）

| 配置 | CPU | 每帧体积 |
|---|---|---|
| 5fps q80 | 93% | 35KB |
| 5fps q20 | 111% | 18KB |
| 2fps q80 | **31%** | 35KB |

`quality` 只改量化表、不改运算量 ⇒ 它影响的是**带宽/卡顿**（弱网下值得降），
不是 CPU。降 CPU 只有三个旋钮：**fps**、**相机端分辨率**、**切 stream 模式**。

## 三、相机：MAC 连接（动态 IP）真正可用

### 3.1 换网线实锅

相机 MAC 未变（`f8:c9:03:5e:1c:5a`），但插上网线后 IP 从
`192.168.1.181`（WiFi 段）变成 **`10.168.1.101`**（eth0 段）。
旧实现只按「配置 IP 所在 /24」扫网段 ⇒ 永远扫不到 ⇒ 日志
「MAC 未解析到 IP ⇒ 暂用配置 IP 连接」→ `No route to host`。

### 3.2 修法（`hsfsrv/camera_mac.py`）

1. **`local_ipv4s()`**：枚举本机全部非环回 IPv4（解析 `ip -4 -o addr`；
   本板 eth0=10.168.1.100 / eth1=192.168.0.10 / wlan0=192.168.1.249）
2. **`resolve_mac_ip(seed_ip=…)`**：按「seed 优先 + 其余本机网段依次」
   逐个 `sweep_subnet`（对 /24 做 554/80 TCP 探测，借内核建 ARP），命中即返回
3. **`_probe_reachable()`**：解析到的 IP 先验 TCP 可达（ARP 可能残留旧网段
   的同 MAC 条目，不可达就继续找）
4. **回落**：全失败但配置里有 IP ⇒ 先用 IP 连（连上后 ARP 建立，下轮恢复 MAC）
5. **留痕**：解析结果**变化**时打一条
   `相机地址解析：MAC xx → IP`（现场唯一证据）

### 3.3 实证

```
相机地址解析：MAC f8:c9:03:5e:1c:5a → 10.168.1.101
ss -tnp → 10.168.1.100:41980 → 10.168.1.101:554   （走 eth0 有线）
ip route get 10.168.1.101 → dev eth0 src 10.168.1.100
```

⇒ 相机换了网段/IP，服务端自动跟上，且走的是**有线**（比 WiFi
-75dBm/15% 丢包/RTT 300ms 抖动稳得多）。

## 四、相机：「重启相机后画面就没了」的五层根因

| # | 根因 | 修法 |
|---|---|---|
| 1 | `read_es` 的 `except socket.timeout: continue` 是**永久空转**（相机重启时 TCP 半死，收不到 FIN/RST）⇒ 采集线程挂死、重连循环轮不到（零日志） | **静默判死 30s**（`RTSP_SILENT_TIMEOUT_S`；10s 太短：弱链丢包重传自愈要十几秒，会把刚播的会话砍掉） |
| 2 | 重连太密把相机会话槽堆满（TP-LINK 只有 2~4 个）⇒ 相机接受 PLAY 却不推流 | 失败按 `base×2^(n-1)`（封顶 8×）退避 + `teardown_stale()` **用新连接**给旧 session 发 TEARDOWN（死 socket 上发不出去） |
| 3 | `videoscale` 钉 NV12 而 `jpegenc` 不吃 ⇒ 管线构建失败、gst 立即退出、**静默重连无数轮** | 见 §二（钉 I420、抽帧前置） |
| 4 | 采集线程在某处未捕获异常**静默死亡**（进程活着、健康照推、线程没了） | `_run` 外层 `except BaseException` 留痕 + `alive()/ensure_alive()` 看门狗（App 每拍调） |
| 5 | Windows `arp -a` 输出是 **GBK**，`text=True` 按 UTF-8 解 ⇒ MAC 永远解析不到 | 拿 bytes 按 `mbcs/gbk/utf-8` 依次解 |

**看门狗装上后立刻抓到第 6 个 bug**：多行补丁把 `stale_session = ""` 初始化
那行漏了 ⇒ `UnboundLocalError` ⇒ 线程死（这正是"静默死亡"的活样本）。

## 五、触摸屏：全屏退出后「点什么都无响应」

### 5.1 根因（鼠标路径复现不出来）

板端是 ILITEK **触摸屏**（`/dev/input/event3`）。相机页原先用独立
`Qt.Window + showFullScreen()` 做全屏：

- 触摸序列进行中把那个**顶层窗** close/hide ⇒ Qt 的触摸状态机认为它仍持有
  隐式 grab + 主窗收不到 `mouseRelease` ⇒ 之后每次点击都被当"拖拽中"
- 鼠标事件路径（本机离屏测试）**完全复现不出来** —— 所以第一版修
  「延迟 close + releaseMouse」对鼠标有效、对触摸无效

### 5.2 修法：主窗内**覆盖层**（同一个 QWindow）

`_FullscreenPlayer`：`parent = page.window()` 的普通子控件

- `enter()` = `setGeometry(host.rect()) + show + raise_ + setFocus`
- `exit_fs()` = `hide + releaseMouse/Keyboard + 补发一次合成
  MouseButtonRelease + raise_/activateWindow + 交还焦点`
- 双击 / Esc / 退出钮 一律 `QTimer.singleShot(0, exit_fs)`（不在事件处理里切窗口）
- 主窗 resize 用 `eventFilter` 跟随

**回归锁**：`client_py/tests/_fs_exit_check.py`（6 检：与主窗同 QWindow /
退出后覆盖层隐藏且不遮挡下层 / 无残留 grab / 主窗可命中可操作）。

## 六、模拟量：温度传感器与量程可配（本轮早段完成）

- **温度传感器接在 CH1**（通道号可配），压差计 CH0；两端都可配通道号 +
  **量程上下限**（4mA→下限、20mA→上限，`AnalogChannelScale.lowValue` 两点定标）
- 「**4mA 以下有效**」逐传感器开关（压差计缺省开=负压线性延续；温度缺省关）

- **电机超温保护**（protect 节三键：启用/阈值℃/是否停设备；2s 去抖 +
  报警锁存 + 需人工复位；缺省不启用）
- 主页搅拌泵卡新增 **电机温度** 块（`motorTempC`，随 VFD 遥测下发；
  缺键显示 `--`）

## 七、模拟量：**0mA 判定断线**（用户实报，本轮收口）

### 7.1 现象

温度量程配成 **-50~200℃** 时，0mA 走「欠量程钳到下限」⇒ 主界面电机温度显示
**-50℃**（看起来像个真实温度！）⇒ 现场会把"传感器断线"当"零下 50 度"。
随后修断线时又引出**通道名字丢失**。

### 7.2 三处修法

1. **`AnalogChannelScale.engineering()`**：`ma ≤ 0.5mA` ⇒ **断线**
   （返回 `None` + 「断线（xx mA 回路无电流）」）。阈值依据：真断线≈0mA，
   正常 4~20mA 变送器最低合法电流远高于它。
   **`3.9mA` 这类零点漂移仍按欠量程/负压**（不能一起判死）。
2. **AI 快照**（`app.py::encode_analog`）：`value is None` 但有 note 时，
   仍下发 `ew<n>`（断线文案）+ `en<n>`（名字）—— 界面要能显示「断线」
   而不是光 `--`。
3. **客户端解析**（`model.py`）：`e/eu/en/ew` **四键各自独立判在**
   （原来整段被 `e<i>` 存在才解析 ⇒ 断线通道既丢名字又丢文案）；
   `pages_monitor.py` 的名字不再依赖"有没有换算值"。

### 7.3 效果（本机离屏 + 板端实测）

```
通道 0   压差计       4.012    0.003                        mA / MPa
通道 1   温度传感器   0.000  断线（0.00mA 回路无电流）       mA
```

- 主界面电机温度显示 **`--`**（不再 -50℃）
- **超温保护不拿断线值判定**（读不到 ≠ 超温，不会误停机）

## 八、历史页：「模式」列显示不全

**根因**：列宽下限按**表头**量（「模式」2 字），而内容最长是
「自动·运行中」（6 字符）⇒ 截成「自动…」。**网页端 `COL_MIN_TEXTS` 早有
这一项，桌面端漏了。**

修法：桌面历史页 `auto_min_texts` 补 `1: "自动·运行中"`。
**回归锁 E1b**：模式列宽必须 ≥ 「自动·运行中」实测宽度（150 ≥ 132 px）。

## 十一、待办 / 已知限制

1. **板端历史库表结构**：本轮未动；如需历史报警查档仍需 0x011A（既有项）。
2. **硬件 JPEG 编码**：如将来升级 gstreamer-rockchip 到 PR #68 之后版本，
   可重测「零拷贝 + 色度」；当前版本明确不可用。
3. **stream 模式（ES 直传）**：板端 CPU ≈0 的最优解，前提是网页端用
   Chrome 内核浏览器（WebCodecs）；手机自带/国产浏览器不支持。
4. **模拟量温度传感器（电机温度，CH1）当前报 0mA/断线**：属现场接线或供电
   问题（非软件）；接好后自动恢复正常读数，不需要改配置。**不要**为了"让它
   显示个数"去关掉断线判定或把 `belowValid` 打开——那会把断线伪装成 -50℃。
