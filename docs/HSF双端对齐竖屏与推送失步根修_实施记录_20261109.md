## 一、P0 根修：推送失步（§六.2 闭环）

### 1.1 判定过程（为什么不是 485 自愈）

- 交接台账怀疑 `HsfServerBusHeal_step` ③「在线但数据停滞」分支对虚拟
  客户端是 no-op。本轮**代码走查闭环该疑点**：③ 的 `setPollInterval`
  实现是 `hubStopDevicePollTimer + startTimer`（XModbusHub.c:1815-1827），
  重挂设备周期定时器是**有效动作**；pump 的 `state != ConnectedState`
  门槛（:1359）只挡离线设备，与定时器无关；`lastSuccessMs` 只在成功
  应答刷新（:2480/:2500）。看门狗静默的真正含义是 **modbus 侧根本没病**
  （进程内虚拟从站应答零开销）——现场三条链路同灭 + 健康恒绿 + 零自愈
  日志的真因在 **XLink 传输层**（见 XLink.md §15）。
- 根因链：客户端读方向慢/停 ⇒ 服务端会话 TX 队列（128KB）队满 ⇒
  Publish 帧整帧静默拒绝且无任何记账/再同步/判死 ⇒ 变值事件帧
  （健康变化/阀告警/状态跃迁，只发一次）永久丢失 ⇒ 「在线但遥测空 +
  操作了没反应」；慢滴漏让既有三条判线全部失效。
- 复现证据链：限速代理（SO_RCVBUF 8KB + 200B/s）使服务端 TX 停摆时
  客户端仍 Ready；50B/s 全停档由既有「发方向判线」（6s）接管——三条
  判线覆盖「全停」，唯独「滴漏但排不空」是真空地带。

### 1.2 修法摘要（详见 XLink.md §15）

- `XLinkSession`：拒帧计数+失步戳（sendWithPrefix 队满分支）；队列排空
  发 `txResyncNeeded_signal`（txFlush 末尾）；失步超时踢线（pump，默认
  15s，可调）。
- `XLinkServer`：新会话信号接线 + `setResyncCallback`（authChanged 同款
  模式）。
- `HsfServerApp`：`hsfAppTxResync` 按会话订阅表补发全量（订阅即补发同
  路径），不断链。
- 回归：`--test xlink` 830/3（3 条失败为 HEAD 基线既有，A/B 对照证伪
  本轮引入；详见 XLink.md §15.4）。
- 两个框架契约坑（信号函数 NULL 契约 / XVar 取址）实录见 XLink.md §15.3。

### 4.2 万次会话压测（双轮零增长门）

- 第一轮（580s timeout）被超时掐断（EXIT=124）——**教训：万次压测必须
  给足时长（实测 8×1250 一轮 >10 分钟，本轮双轮实跑 52.5 分钟）**。
- 双轮完整跑（改传输层后）：**9992/10000 成功**，8 次失败=每 worker 恰
  1 次「连接超时」，全部落在压测中段与 GUI 联调/探针并发的时间窗（压测
  与联调不可并跑的实证，见 4.4）。
- **堆基线判定（终值）**：压测前 635KB → 万次双轮后干净重启 **618KB** →
  最终轮（再 1 万次，**10000/10000 全部成功零失败**）后干净重启再次
  **618KB**——跨夜累计 **~20,000+ 次连接周期，进程级泄漏为零**。
  压测后不重启的平台（3.96MB）= **SQLite 页缓存高水位**（logs 52,506 行、
  DB 落盘 4.5MB，缓存随数据量有界增长且按页复用）——**logs 落库会让
  「压测后堆基线」从 ~0.6MB 抬到缓存水位，判读时必须先归因 DB 缓存
  再定性**（本轮新经验）；进程级判据=重启回基线，两次均 618KB 铁证。

## 六、追加根修：Py 客户端 xcb 平台退出段错误（用户「偶发性也不行要查出来」指令）

### 6.1 现象与取证

  **指向匿名堆**（块早已释放并被复用）——PyQt 解释器退出拆卸遍历踩到
  「C++ 侧已释放但 sip 未失效」的包装器 = 绑定层退出期双重所有权 UAF。
- 定位过程中排除：TrendChart（拆成哑控件仍崩）、AlarmPage（skip=alarm
  仍崩）、悬垂包装器审计（gc 可见的 isdeleted 包装器 = 0——损坏对象是
  gc 不追踪的未跟踪包装器，审计天然盲区）。

### 6.2 根因定性

**运行期零影响的退出期 UAF**：崩溃只发生在 main 返回之后（每轮测试
38×2 步「异常 0 次 / 通过」打印全部完成）；退出时 sip 遍历销毁全部
QObject 包装器，与 Qt5 的「QApplication 进程单例 + 复杂所有权树」在
解释器终结场景下不兼容。

### 6.3 处置（对齐 C 端 §8.2 既有裁定）

`hsfsrv_client/__init__.py` 首个 QApplication 之前
**`sip.setdestroyonexit(False)`**（附完整证据链注释）：退出持有交 OS
回收，不做遍历销毁——与 C 端「夹具全量拆除实证不可行、已回退」同一
裁定的 Qt/PyQt 侧对应物。运行行为零变化（纯退出路径）。

### 6.5 追加：test_history_page 的退出段错误（第二处，独立机制，已根修）

faulthandler 全栈实证（xcb 下 ~50% 复现）：
`_run（自动重连）→ _connect_once → _teardown → _set_state(202 行) →
on_state_changed(→bridge._on_state→Qt emit)` 段错误——**服务端被 stop 后
自动重连线程的最后一拍状态迁移发生在解释器终结期**，接收端 Qt 对象已析构。
combo 的退出崩溃是「app release 遍历踩已释放包装器」（§7.1）；本处是
「终结期网络线程 emit」——两个独立机制。

修法（两层闸）：
1. `XLinkClient._set_state` 首行 `if self._closed: 静默落账 return`
   （close 后重连迭代剩余拍不再触碰 on_state_changed/Qt 层）；
2. 桥层 choke point：bridge._shutting_down 闸 + `_emit_net` 收口全部
   16 处 emit + `disconnect_from` 置闸/关自动重连/close 同步 join
   （`XLinkClient.close(join_timeout=3)`）；
3. 首层兜底（§7.3）`sip.setdestroyonexit(False)` 不变。

验证：test_history_page 三连 **EXIT=0**（163/166/170 passed——断言数随
库内数据浮动属设计）；combo 双端口复跑 EXIT=0。

### 6.6 第三处：combo 双端口退出段错误（析构级联处理器发射，已根修）

修复 §7.5 后 combo6200 仍 ~50% 崩于 main 返回（faulthandler 只见
`<module> line 317`=主函数返回路径）——**第三机制：局部引用无序释放 →
主窗 C++ 级联析构 → 页面 destroyed/状态处理器链里 emit 进半死接收方**
（此前 core：帧 0=pyqtBoundSignal_emit）。

修法=顺序化拆卸（断开→泵消化 deleteLater→关窗→泵→显式 del）落两处：
`tests/test_vfd_combo.py` 尾部 + 产品入口 `__main__.py`（app.exec_ 返回
后同款序列；产品路径本就断开，此改把释放顺序钉死）。

验证：combo 6200 ×4 + 6100 ×4 **全 EXIT=0**；产品入口活窗定时退出 ×3
**全 EXIT=0**；桥层改动后的 13 套件电池全绿（677+163 断言）。
