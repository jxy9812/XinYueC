## 1. 立项书三处实测前提已过期（本次订正）

立项书写于 2026-11-01 当日早些时候，其事实基线与后续实测不符。**实施按实测走**，并在立项书补记指针。

### 1.1 「控件树全部画在软件 XImage」——不成立

立项书 §1.3/§1.3★（`XPainter_begin_image` 绑软件 XImage ⇒ 控件树 CPU 逐像素光栅化）。

**实测**：控件树**早已**在 GPU FBO 上绘制——`XPainter_begin_image` 在 GPU 请求下会同时挂上 GPU 后端（`XPainter.c:8197` 起），且 fillRect / 字形图集 / drawImage 三条快速路径都直写 FBO。软件 XImage 只接收**上屏用的回读**。

真正在 CPU 上的部分是**绕行软件暂存画布**的那批命令（见 §2.1），不是「全部」。

### 1.2 「page 18/19 CPU 98~99%」——过期

该基线取自**布局自激活活锁修复之前**。修复后（提交 9093919d 已含）板端实测：

| 臂 | 空闲 CPU（单核占比） |
|---|---|
| 软件光栅 | **3.8%** |
| GPU 直通（默认口径） | **15.0%** |

⇒ CPU 大头已从「布局活锁」转移到「GPU 路径的绕行上传」，且 **GPU 路径反而比软件贵 4 倍**。

### 1.3 「X11 侧加 platform surface 走 eglSwapBuffers」——swap 腿已能跑通

实测 `XGPU_PRESENT=swap` 在板端 `p2w>0`（EGL window surface + swapBuffers 可用）。真正的缺口不是「加形态」，而是 **GPU 上屏后框架仍会再做一次 XPutImage**（同片区域两次搬运）。

## 2. 实施内容

### 2.1 任务 A0 阶段一：消除斜线绕行（`Src/XGui/Graphics/XPainter.c`）

**根因**：`painterRaster_drawLineDevice` 的 GPU 分支对**非轴对齐**线段无 GPU 原语，落入「软件暂存画布回退」；而暂存画布内容与相邻直绘原语交错时，**每条命令触发一次暂存画布冲批上传**（板端 5.3s 窗口 3610 次 × ~0.73ms ≈ 2.6s，占该窗口 CPU 的约一半）。

**归因实测**（`XGPU_QUAD_PROF=1` + `XGPU_PAINTER_PROF=1`，板端 page 18）：

```
[xpainter-quad] axis=7599 axisFalse=0 diagExt=0 diagExtFalse=0 diagCanvas=2613 diagAa=0
[xpainter-prof] flush=3610 (2639.018ms 0.7310/次) batchDraw=4137 (38.798ms 0.0094/次)
```

⇒ `batchDraw`（软件光栅）仅 38.8ms，`flush`（上传）却 2639ms ⇒ **98.5% 的成本是上传，不是光栅**。且上传按字节计费（整幅 2.8MB → 55.9ms；区域 ~27KB → 0.54ms，均 ~50MB/s，主因是驱动侧逐像素预乘+R/B 交换）。

**改法**：`painterGpuFastPathExtRequested()` 由「env 未设即恒关」改为**缺省开、显式 `"0"` 回退**（与 `xgpu_flush_lean_requested` 同解析式）。

**效果**（板端同批四臂对照，同页同负载）：

| 臂 | 空闲 CPU | diagCanvas |
|---|---|---|
| 软件 | 3.8% | — |
| GPU（改前默认） | **15.0%** | 2613 |
| GPU（改前 + `XGPU_FASTPATH_EXT=1`） | **6.8%** | 0 |
| GPU（改后默认，= 阶段一落地） | **6.2%** | 0 |

**代价（必须记录）**：quad 是**硬边**光栅，与软件 Bresenham 覆盖非逐位一致。量化：剔除时钟噪声后模式差异 **590 px**（集中在圆弧/按钮圆角）。该项由任务 A0 阶段二消除（见 §4）。

### 2.2 任务 C：GPU 已上屏时抑制框架重复 XPutImage（`Src/XGui/Widget/XWidget.c`）

**改法**：swap 腿中，`XGpuRenderBackend_presentToWindow()` 成功即认定「整幅窗口内容已呈现」（该路径内部是 FBO→默认帧缓冲整幅 blit + swapBuffers，窗口直通会话的 FBO 是持久缓冲、始终持有整窗内容）⇒ 跳过框架的 `XBackingStore_flush` 上屏动作。

**例外**：软件双缓冲形态（`SoftwareDouble`）需把提交区同步进另一块缓冲，跳过 flush 会破坏双帧配对 ⇒ 该形态仍走 flush。当前默认 `XGUI_BACKINGSTORE_BUFFER_COUNT=1`（两平台皆 SoftwareSingle），不触发。

**效果**（板端 swap 臂，wprof 段）：

| | 改前 | 改后 |
|---|---|---|
| 框架提交腿 `flush` | 0.727ms / 6 次 | **0.004ms / 6 次**（重复 XPutImage 归零） |
| 回读 `drb` | 4.921ms / 6 次 | 0（swap 腿本就无回读） |
| GPU `p2w` | — | 10.916ms / 6 次（1.82ms/次） |

**诚实结论（X11 特有）**：呈现总成本 swap 1.82ms/次 **>** 回读+BitBlt 0.74ms/次。原因是 EGL window surface 的 swap 要经 X server（llvmpipe 软件合成），像素拷贝从我们的代码挪进了厂商驱动线程（线程级归因：swap 臂 `mali-cmar-backend` 0.5%→0.8%、主线程 5.6%→6.1%），**并未消失**。

⇒ **X11 上应继续用回读腿作默认呈现通道**；任务 C 的抑制逻辑在显式选 swap 时消除真实的冗余搬运，其价值在真零拷贝平台表面（fbdev/DRM，fbdev 侧仍按既有约定故意不提供平台表面）。

### 2.3 默认后端改为软件、GPU 按需启用（`Src/XGui/XGuiConfig.h` / `XGuiApplication.c`）

**改法**：`XGPU_RUNTIME_DEFAULT_ON` 缺省 1 → **0**（不再是「桌面探测到 GL 即默认 GPU」）；命令行 `--gpu` / `--software(--sw)` 的解析从该宏的守卫中**解耦**，任何默认口径下都生效；启用口按优先级：`addRequestedOverride(true)` > `--gpu` > `XGUI_RENDER_BACKEND`/`XGPU_BACKEND` > 编译期 `-DXGPU_RUNTIME_DEFAULT_ON=1`。

**依据**（板端 page 18，485 联调负载）：

| 臂 | 空闲 CPU | 485 负载 CPU | RTT p50 | RTT p99 | RTT max |
|---|---|---|---|---|---|
| **软件（默认）** | **3.6%** | **17.7%** | **3.50ms** | **4.50ms** | **13.24ms** |
| GPU（回读上屏） | 6.2% | 31.5% | 3.58ms | 14.07ms | 126.72ms |
| GPU（swap 上屏） | 7.3% | — | — | — | — |

⇒ 文本/表格型 HMI 上，GPU 直通在**每个维度**都更差：CPU 1.8~2 倍、485 应答尾延迟 3 倍。

### 2.4 板端部署形态（`/root/Desktop/XinYueC/run_demo.sh`）

新增两个标志文件开关（沿用既有 `slave485.mode` / `master485.mode` 惯用法）：

- `gpu.mode` → `XGUI_RENDER_BACKEND=gpu`
- `gpuswap.mode` → `XGUI_RENDER_BACKEND=gpu` + `XGPU_PRESENT=swap`

默认（无标志文件）= 软件光栅 = 框架新默认口径。

## 4. 未完成项与理由

### 4.1 任务 A0 阶段二（Bresenham 覆盖图 → drawAlphaBitmap 直传）——**暂缓**

原计划：给 Bresenham 循环加「写 8bit 覆盖图」变体，GPU 直传 `drawAlphaBitmap`，与软件路径共用同一条光栅化 ⇒ 逐像素一致且无画布绕行。

**暂缓理由（实测驱动）**：

1. **CPU 收益≈0**。阶段一后斜线已走 `drawSolidQuad`，成本 ~1.5µs/条（`XGPU_PROF` 实测），2613 条/5.3s ≈ 3.9ms——相对 CPU 总量可忽略。阶段二反而要付「掩膜光栅 + 掩膜上传」的固定成本。
2. **达不到 A0 的目标**。阶段二只修斜线（590 px），而本页 **SW↔GPU 的像素分歧主体是文本：29,775 px**（关闭 `XGPU_FASTPATH_EXT` 复现旧行为后仍为 29,775 px ⇒ 与本次改动无关）。先修斜线无法实现「画面逐像素一致」（V9），必须先治文本分歧。
3. 风险：新增光栅化代码 + 每次调用新增掩膜分配（与「泄漏零容忍」的红线相冲）。

**后续顺序建议**：① 治 SW/GPU 文本 AA 口径分歧（见 §4.2）→ ② 再做斜线同源覆盖图路径（届时 V9 才可能整体达成）。

### 4.2 既存缺陷（非本次引入）：SW↔GPU 文本抗锯齿口径分歧

板端 page 18 对比软件渲染与 GPU 渲染（同构建、同内容、剔除时钟噪声）：

- **29,775 px**（约 2.9% 像素）模式相关差异，集中在**文本字形边缘**。
- 目视：软件路径字形边缘为平滑灰度过渡（FreeType 平滑光栅），GPU 图集路径边缘更硬。
- 隔离实验：设 `XGPU_FASTPATH_EXT=0`（复现改动前 GPU 行为）差异仍为 29,775 px ⇒ **与本次改动无关，是既存分歧**。

⇒ 立项书 V9「画面逐像素一致」当前**不成立**，且主因在文本路径而非斜线。建议单独立项（对齐 SW 的 FreeType 平滑覆盖与 GPU 图集覆盖的量化口径）。

### 4.3 既存缺陷修复：r6-b 回归锁误判（本次已修）

**现象**：`XGuiRegression`（软件钉死）稳定失败 1 项——「r6-b 登记覆写不泄漏（在用字节回落基线）」。经 HEAD 原样全量重编对照确认为**既存失败**，与本次改动无关。

**诊断**：插桩实测批内增量为 **1054 字节**（阈值 1024，仅差 30B 即判红）。倍增对照（4 轮 vs 8 轮）显示增量**恒为 1054 字节、与轮数无关** ⇒ **一次性惰性初始化残留，不是按轮泄漏**（测试要抓的「按轮线性泄漏」早已被 2026-10-21 的「覆写前即时回收」补丁修掉）。

**修法**（不放宽阈值，改断言口径）：改为**三批次增量比对**，断言落在记账已稳定的第 3 批（与上一批终值比）。

- 软件模式：batch0=+1054、batch1=0、batch2=0 ⇒ 末批增量 0 ✅
- GPU 模式：batch0=−273540、batch1=+285832、batch2=0 ⇒ 末批增量 0 ✅
  （GPU 模式的那 ~286KB 是会话/FBO/暂存画布大块分配的**归属时点台阶**，
  实测第 1~4 批在用字节逐批完全相同 ⇒ 非泄漏。）

### 4.4 未测项

- **V4（主站请求/错误比）**：本次未接 PC 侧主站压测（CH343 在位但未接入本轮脚本）；板端从站侧 485 应答 err=0（n=1500）。
- **V2（事件循环 lag 中位 ≤20ms）**：板端 `[WHEEL] lag` 采样点太少（1s 级间隔、每窗仅数个样本），统计意义不足；软件与 GPU 两种形态均观测到 68~169ms。**该门槛当前未被任何形态满足**，需专门的 lag 采样改造（提高采样率）后重评。

| 软件 | 3.03ms | 3.60ms | **4.93ms** | 14.98ms | 20000 / 0 |
| GPU | 3.00ms | 5.64ms | **115.39ms** | 390.50ms | 3000 / 0 |

⇒ 中位相同而**尾部差 23 倍**：GPU 路径的长帧（每 painter 一对 begin/end + 回读呈现）
偶发把事件循环卡住数百毫秒，485 应答随之延迟 ⇒ **GPU 路径不适合承担 485 实时角色**
（前序战役据此把默认后端改回软件，本轮在双重负载下再次证实）。

注：`[WHEEL] lag` 指标两臂都高且互相矛盾（软件臂 p50 329ms 却 RTT p99 仅 4.93ms），
**该指标口径本身需先澄清**（见续立项书 §2.4 的 D 项），本记录不以其作结论依据。
