# HSF 接入网络相机（TP-LINK IPC 鱼眼）设计方案 —— 2026-11-19

> 目标：设备菜单下新增「相机」页显示实时画面；远端设置可配相机 IP/端口/账号/口令/
> 码流（主/子）/帧率；**由服务端采集并转发给客户端**；回答「要不要压缩、占多少带宽」。
>
> 本文所有数字都是**在真机（相机 192.168.1.181 + 板端 192.168.1.249）实测**得到的，
> 不是估算。测量脚本与命令附在各节。

---

## 0.0 已定决策（2026-11-19 用户拍板）

| 决策点 | 结论 | 影响 |
|---|---|---|
| **画面质量档** | **704² 分片传输**（不降到 352²） | 服务端按 ≤12KB 切片 + 片头元信息；**三端都要写组帧器** |
| **采集器归属** | **Python 服务端**（`server_py`） | C 端服务端只占协议号不实现（照 0x011B 先例） |
| **网页端取数链路** | **网页端也从服务端取数据，不能直连相机**（外网访问场景：浏览器在公网、相机在内网） | ⇒ **网页端同样走 XLink 分片**；webui 在本地重组后以 `image/jpeg` 喂浏览器。**没有一条路径是浏览器直连相机的** |

⇒ **统一架构**（所有客户端都经服务端，帧只解码一次、多端分发）：

```
相机 RTSP ──板端采集器（自研 RTSP 客户端 + gst 硬解硬编）──► JPEG 704² 帧队列
                                                       │
                                     服务端按 ≤12KB 分片 publish(TOPIC_CAMERA_FRAME, RAW)
                                                       │
              ┌──────────────────────┬───────────────────┴─────────────────────┐
       桌面 Python 客户端        C 端客户端                                  webui（本地 HTTP）
       组帧 → QLabel 贴图        组帧 → XImage → drawImage_3            组帧 → 存最新帧
                                                                        → GET /api/camera/frame
                                                                        （浏览器 <img> 轮询）
```

**帧只被解码/编码一次**（服务端），三端各拿一份分片重组 ⇒ 相机只占一路 RTSP 会话。

## 0. 结论摘要（先看这段）

| 问题 | 结论 |
|---|---|
| **远程能做到 30fps 吗？** | **不能 —— 相机本身就没有 30fps**。相机的帧率可选值只有 `65537/65546/65551/65556` = **1/10/15/20 fps** 四档（`/ds` 能力表实测）。⇒ 采集帧率**跟随相机档位**（1/10/15/20），不做 25/30。 |
| **要不要压缩？** | **要，而且压缩必须发生在服务端**。相机的原始码流（H.264 512K / H.265 2048K）虽然已经是压缩态，但**三端客户端都解不了**（浏览器不能播裸 RTP；C 端 XGui 没有视频解码器）。服务端硬解→重编码成 JPEG 帧后，不仅三端通吃，**带宽还比原始码流更低**（降分辨率+降帧率+有损重编码三重收益）。 |
| **需要多大带宽？** | 见 §5 表：子码流 704²@10fps ≈ **3.3 Mbps**；缩到 352² 单帧直发档 ≈ **0.96 Mbps**；主码流 2528²@1fps ≈ **5.8 Mbps**。**默认档建议 704²@2~5fps（0.7~1.6Mbps）**。 |
| **板端要装 ffmpeg 吗？** | **不用**。RK3568 的 Rockchip MPP **硬解可用**；但**硬件 JPEG 编码不可用**（`mppjpegenc` 色度平面解析错误、颜色偏紫，参数层面无解 —— 见 §2.5 的 2026-11-20 订正）⇒ 定稿走「**VPU 硬解 + `videorate` 抽帧 + 软件 `jpegenc`**」，板端 2fps/704² 实测 **47% 单核**（旧顺序不做抽帧前置时 295%）。 **ffmpeg CLI 装不上**（板端 libavcodec-dev 4.3.8 与 apt 的 4.3.9/4.3.7 冲突），GStreamer 的 `rtspsrc` 对本相机会失效（§2.4）⇒ 采集器要**自研最小 RTSP 客户端**。 |
| **最大的硬约束** | **XLink 单帧载荷上限 16KB**（`XLink_config.h:295`）⇒ 一张 704² JPEG（41KB）塞不进。⇒ 要么**缩到 ≤352² 单帧直发**，要么**分片**（§4.3）。 |

## 1. 相机侧实测事实

### 1.1 设备

| 项 | 值 |
|---|---|
| 型号 | TP-LINK **IPC**（鱼眼，方形 2528×2528 传感器），MAC `f8:c9:03:5e:1c:5a` |
| 位置 | `192.168.1.181`，与板端 `192.168.1.249` **同网段** ⇒ 板端可直接拉，不必绕本机 |
| 账号 | `admin` / `mk123456`（Digest，realm `TP-LINK IP-Camera`；Basic 也接受；**错口令 DESCRIBE 直接 401**） |
| 开放端口 | **80**(网页) / **554**(RTSP) / 443 关 / **8899(ONVIF) 关** ⇒ 只有 RTSP + HTTP |
| 画面内容 | 圆形鱼眼俯拍过滤工位（罐体、搅拌电机、管路、绿色地坪、两名工人），四角黑边，左上角 OSD 时间戳 |
| **音频** | **RTSP 拿不到**。SDP 声明 `m=audio 0 RTP/AVP 8`(PCMA/8000)，但单独建轨 PLAY 后**零音频包**；视频轨已建时再 SETUP 音频轨直接 **400** ⇒ **只当纯视频设备设计** |
| **HTTP 抓图** | **无**。网页端「抓图」走的是 IE/旧火狐**插件**（ActiveX/NPAPI 拉 RTSP 自己渲染），`/ds` 无快照命令 ⇒ 只能走 RTSP |

### 1.2 码流能力表（`/ds` 的 `video_capability` 实测原文）

```
main:  encode_types=[H264,H265]  frame_rates=[65537,65546,65551,65556]
       bitrates=[1024,1536,2048,3072]  resolutions=[2528*2528,1920*1920,1600*1600,1280*1280]
minor: encode_types=[H264,H265]  frame_rates=[65537,65546,65551,65556]
       bitrates=[64,128,256,512]       resolutions=[704*704,640*640]
当前值: main=H265 2528*2528 frame_rate=65556(20) VBR 2048K
        minor=H264 704*704 frame_rate=65556(20) VBR 512K
```

⇒ **帧率码值 = 65536 + fps**（65537=1 / 65546=10 / 65551=15 / 65556=20）。
⇒ **上限 20fps**，用户要的「设置帧数」只能在这四档里选（跟随相机）。
⇒ 主码流分辨率四档、子码流两档，且**两条流都能切 H264/H265**（子码流切 H265 可再省一半带宽）。

### 1.3 RTSP 行为（实测）

- 认证：Digest（`WWW-Authenticate: Digest realm="TP-LINK IP-Camera", nonce=...`），
  先 401 再带 `Authorization` 重发即通过。
- `SETUP` 要**带 track id**（`<base>/track1`），`PLAY` **必须带 SETUP 应答里的
  `Session:` 头**（否则回 **400 Bad Request**）。
- 传输：TCP interleaved ✅ / UDP unicast ✅（`SETUP` 应答带 `server_port`）。
- **会话状态敏感**：残留的客户端进程占住会话后，其它连接会「能握手但收不到 RTP」。
  ⇒ 采集器必须**单连接 + 优雅退出（TEARDOWN + 关 fd）**，不能留残进程。

### 1.4 相机会话数与 rtspsrc 的坑（重要）

同一时刻、同一个相机：

| 客户端 | SETUP 的轨 | 结果 |
|---|---|---|
| 自研 RTSP 客户端（只 SETUP **track1** 视频轨） | 1 条 | ✅ 3 秒收 **3014 帧 / 3.1MB** |
| GStreamer `rtspsrc`（对 SDP 里**全部 3 条**轨逐条 SETUP：video + audio + `application/TP-LINK` smart 轨） | 3 条 | ❌ **0 帧**（RTP 一个都收不到；管道能 preroll 是因为 SDP 拿到了 caps） |

⇒ **本相机不能用 GStreamer 的 `rtspsrc` 直连**（它会去 SETUP 本相机不出数据的
音频轨与 smart 轨，把会话带崩）。⇒ 采集器必须**自研最小 RTSP 客户端，只 SETUP 视频轨**。

## 2. 板端能力实测（RK3568）

### 2.1 硬件与内核驱动

```
/dev/mpp_service  /dev/rga  /dev/video-dec0  /dev/video-enc0  /dev/mali0
mpp_vdpu2 (解码) / mpp_vepu2 (编码) / mpp-iep2 (图像编码) —— 内核驱动在位
libgstrockchipmpp.so:  mppvideodec  mppjpegenc  mpph264enc  mpph265enc  mppjpegdec
librockchip_mpp.so / librockchip_vpu.so / libmali.so (Mali-G52 GPU)
```

⇒ **硬件 H.264/H.265 解码可用**；硬件 JPEG **编码元素存在但不可用**（色度平面
解析错误，见 §2.5 的 2026-11-20 实测订正）；H.264/H.265 硬件编码本轮未用于
本功能。GPU 那块是 Mali-G52，只负责渲染 —— **它不参与视频编解码**（VPU/JPEG
Codec 是独立硬件块），两者别混。

### 2.2 实测：硬解→硬编 JPEG 出图（板端 gst-launch 管道）

```
gst-launch-1.0 -q rtspsrc location=rtsp://admin:mk123456@192.168.1.181:554/stream2 \
  protocols=tcp latency=200 ! rtph264depay ! h264parse ! mppvideodec ! videoconvert \
  ! videorate ! video/x-raw,framerate=2/1 ! mppjpegenc ! multifilesink location=/tmp/sub_%05d.jpg
```

| 源 | 档位 | 结果 | 单帧 | CPU（10 秒窗口） |
|---|---|---|---|---|
| 子码流 H.264 704² | 2fps | 40 帧/20 秒 ✅ | 55~85KB | **114 ticks ≈ 11% 单核** |
| 主码流 H.265 2528² | 1fps | 25 帧/25 秒 ✅ | 280~800KB | **135 ticks ≈ 13.5% 单核** |
| 本地 .h264 文件（绕开相机） | — | 解码正常 ✅ | — | — |

⇒ 板端 4 核，**H.265 2528² 硬解也跑得动**（13.5% 单核），主码流完全可用。
⇒ 板端产出的 JPEG 拉回本机验过：704×704 / 2528×2528，**尺寸**正确。

> ⚠ **2026-11-20 订正**：上表的「11% / 13.5% 单核」是**错的**，且这批 JPEG
> **颜色是错的**。详见下一节 §2.5。上表保留只为记录当时的误判过程。

### 2.3 板端缺什么

| 缺 | 状态 | 影响 |
|---|---|---|
| `ffmpeg` CLI | **装不上**：板端已装 `libavcodec-dev 4.3.8`，apt 的 4.3.9(security 池 404) / 4.3.7(依赖冲突) 都装不进 | 不能用 ffmpeg CLI 当采集器（可解依赖，但没必要） |
| H.264 **软**解码器 | `avdec_h264`/`openh264dec` 全无（只有 `vp8dec`） | 软解兜底不可行 ⇒ 必须走 MPP 硬解 |
| `gstreamer1.0-libav` | apt **可干净安装**（1.18.4） | 可作为 `avdec_h264` 软解兜底（CPU 换稳定） |
| Python 的 GStreamer 绑定（PyGObject） | 未装 | ⇒ 采集器用**子进程管道**而不是进程内驱动 GStreamer |

### 2.4 板端 GStreamer 的两个坑

1. **`rtspsrc` 多轨 SETUP**（见 §1.4）⇒ 采集器不用 rtspsrc。
2. **`videoscale` 后必须显式给格式**：只写 `video/x-raw,width=320,height=320`
   会协商不上（管道静默卡住、0 帧）；写 `video/x-raw,width=320,height=320,format=NV12`
   才能跑通。另外 **RKVdec 硬件最小宽度 512**（dmesg: `min_width 512`）⇒
   缩放要放在解码之后（`videoconvert ! videoscale ! video/x-raw,...,format=NV12`）。

### 2.5 2026-11-20 板端复测订正：**硬件 JPEG 编码不可用 + 管线定稿抽帧前置**

> 本节结论**取代** §2.2 那批数据。当时测的是「有没有帧」，没验颜色 ⇒ 把
> 一个色度已经坏掉的产物当成了"可用"。

**（1）`mppjpegenc` 在这块固件上产出的颜色是错的（参数层面无解）**

| 尝试 | 结果 |
|---|---|
| `mppvideodec ! mppjpegenc`（全硬） | CPU 仅 6%，但画面**偏紫/棕**；**12KB/帧** vs 软件编码 113KB |
| `q-factor` 10 / 30 / 50 / 80 / 96 | 11 / 12 / 12 / 13 / 14 KB —— **质量参数几乎无效** |
| `mppvideodec dma-feature=true`（零拷贝） | 14KB，与基线完全一致 |
| `+ video/x-raw(memory:DMABuf)` | caps 被退回普通内存，仍 14KB |
| `mppjpegenc` 强制 I420 / NV21 / RGB 输入 | **静默 0 帧**（rc=0、无报错） |
| 给 `mppvideodec` 加强制格式 capsfilter | **静默 0 帧**（原生只出 NV12/NV16） |
| 让解码器输出 `colorimetry=bt601` | `not-negotiated` |
| `videoconvert` 软转 601 后再硬编 | 能出帧，但 CSC 本身就慢 70 倍（失去意义） |

定性：固件（gstreamer-rockchip **1.14.4**）的 `mppjpegenc` 在 NV12 输入下
**把色度平面解释错了**（U/V 交错按平面读）；叠加相机流是 BT.709 而 JFIF 约定
BT.601 ⇒ 参数层面修不了。上游补丁（JeffyCN/mirrors PR #68）只补 DMABuf sink
caps，**不修色度计算** ⇒ 不采用。

**GPU 救不了这条路**：Mali-G52 不参与编解码；GL 做 CSC 在服务进程里
`EGL_BAD_PARAMETER`（无 display/GBM 上下文）；板上也没有 `rgaconvert` 元素
（RGA 由 MPP 内部隐式使用）。

**（2）真性能瓶颈是 `videoconvert`，不是 jpegenc**

成本拆解（704²，板端实测）：`mppvideodec` **1.1ms/帧**、`videoconvert`
NV12→I420 **147ms/帧（占总成本 96%）**、`jpegenc` **6.6ms/帧**。
要害：**CSC 的成本 ∝ 它实际处理的帧率**，与"输出多少帧"无关地把它放在最前面，
就是在为相机全部 25fps 做 CSC。

| 管线顺序 | CPU（6 秒窗口，25fps 源） | 出帧 |
|---|---|---|
| `videoconvert → videorate → videoscale → jpegenc`（旧） | **295%**（吃满 3 核） | 4 帧 |
| `videorate → videoconvert → jpegenc`（**新**） | 5fps **93%** / 2fps **31%** | 61 / 25 帧 |

⇒ 整机负载 **4.0 → 1.1~1.7**。

**（3）定稿管线**（`server_py/hsfsrv/camera.py::_build_cmd`）

```
gst-launch-1.0 -q fdsrc fd=0 ! h264parse ! mppvideodec
  ! videorate ! video/x-raw,framerate=<fps>/1
  ! videoconvert n-threads=2 ! video/x-raw,format=I420
  ! jpegenc quality=<Q> ! fdsink fd=1
```

三条硬约束（改之前先读）：

1. **抽帧（`videorate`）必须在 `videoconvert` 之前** —— 这是本功能最大的一笔
   CPU 收益，顺序一反就回到 295%。
2. **不许给 `mppvideodec` 加强制格式 capsfilter** ⇒ 静默 0 帧。
3. **`jpegenc` 不吃 NV12** ⇒ 必须显式产出 I420。旧代码在 `videoscale` 后钉
   `format=NV12`（§2.4 第 2 条的写法）⇒ 管线构建期失败、gst 立即退出 ⇒
   `_pump` 的 sink 写失败走 dead 分支**静默返回**、无任何日志、无休止重连。

**（4）`quality` 与 CPU 无关**（实测）：5fps q80 = 93% / q20 = 111%（噪声内）；
2fps q80 = 31%。q 只改量化表，影响的是**体积**（35/26/18KB @80/50/20）与弱网
卡顿，不是 CPU。降 CPU 只有三个旋钮：**fps**、**相机端子码流分辨率**、
**切 stream 模式**。

**（5）本轮板端实测基线（2fps / 704² / q80 / JPEG 软编）**

| 指标 | 值 |
|---|---|
| gst CPU | **47% 单核**（5fps 97%、10fps 176%） |
| 服务端 VmData | +612KB → +212KB（**收敛**） |
| fd / 线程 | 31/31/31、4/4/4 **恒定** |
| 客户端 / 网页 VmData | **零增长**（60s） |
| 整机负载 | 1.13~1.7 |

## 3. 采集器设计（服务端侧）

### 3.1 放在哪个服务

**放 Python 服务端（`server_py`）**，理由：
- 胶水/子进程/管道处理成本最低，Python 天然擅长；
- 板端 `hsfserverpy`（systemd 单元）就在跑；
- **C 端服务端只占协议号不实现**（照 0x011B 先例：`XhsfLinkProto.h` 加号，C 端
  `HsfServerApp.c` 不动）⇒ 不必把 GStreamer 拖进交叉编译。

### 3.2 采集器形态（三个进程/线程的协作）

```
[自研 RTSP 客户端]  ──H.264 ES──▶ 管道 fd3  ──▶ [gst-launch-1.0 子进程]
   (Python 线程)                                        fdsrc fd=3 ! h264parse ! mppvideodec !
                                                        videoconvert ! videoscale ! videorate !
                                                        video/x-raw,framerate=N/1,format=NV12 !
                                                        mppjpegenc ! fdsink fd=4
                                                                │ 连续 JPEG 帧流
                                                                ▼
                                              [Python 读 fd4 → 按 SOI/EOI 切帧 → 帧队列]
                                                                │
                                                        publish(TOPIC_CAMERA_FRAME)
```

- **为什么自研 RTSP 客户端**：本相机的 `rtspsrc` 不可用（§1.4）；而且我们需要
  精确控制「只 SETUP 视频轨 / 优雅 TEARDOWN / 退避重连 / 超时」——这些本来就得自己写。
  已验证的最小实现（本会话写的探针）约 150 行：DESCRIBE → SETUP track1 →
  PLAY → 读 interleaved 帧 → 解 RTP。
- **为什么 gst 单独起进程**：板端没有 PyGObject ⇒ 进程内驱动不了 GStreamer；
  子进程 + 管道最省事，且**进程崩了不影响主服务**（采集器重启即可）。
- **JPEG 切帧**：JPEG 以 `FFD8` 开头 `FFD9` 结尾，按标记切即可（与 `image2pipe` 同款）。

### 3.3 配置项（远端设置 → 新增「相机」节）

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `camera/enabled` | bool | false | 总开关（不启用就不起采集进程） |
| `camera/ip` | str | "" | 相机 IP |
| `camera/port` | int | 554 | RTSP 端口 |
| `camera/username` | str | "admin" | 账号 |
| `camera/password` | str | "" | 口令（**落盘要脱敏/不进日志**） |
| `camera/stream` | str | "minor" | `main`（主码流）/ `minor`（子码流） |
| `camera/fps` | int | 2 | **采集帧率**，取值跟随相机档位 1/10/15/20（也可低于相机帧率做抽帧） |
| `camera/width` | int | 704 | 输出帧宽（服务端缩放，等高） |
| `camera/quality` | int | 15 | JPEG 质量（ffmpeg/mpp 口径 1~31，越小越好） |
| `camera/timeoutMs` | int | 5000 | RTSP 握手与重连超时 |

落点：`server_py/hsfsrv/config.py` 的 `Config.__init__/load()/save()` +
`proto.py` 的 `CFG_SECTION_CAMERA` / `CFGK_CAMERA_*` +
`app.py` 的 `_h_config_set` **section 白名单**（fail-closed，不加直接被拒）。

### 3.4 健康与重连

- 采集进程退出/无帧超过 `timeoutMs` ⇒ 判「相机离线」⇒ **退出码/状态上报客户端**
  （页面上显示「相机离线」而不是黑屏）。
- 重连：指数退避（1s→2s→4s…上限 30s），**先 TEARDOWN 再关 fd**（§1.3 会话卫生）。
- 改配置 ⇒ **运行期生效**（重启采集进程，不重启服务端）。
- 相机被改配置（码流/分辨率变了）⇒ 采集器要能自适应（重新 DESCRIBE 取 SDP）。

## 4. 传输设计（三端不一样）

### 4.1 共同的硬约束

`XLINK_MAX_PAYLOAD = 16KB`（`Src/XCore/XProtocol/XLink/XLink_config.h:295`，
三份 proto.py 同值）⇒ **一张 JPEG 塞不进单帧**；超限会让客户端
`decode_header` 返回 None ⇒ **整会话断链**（app.py:3947 有踩坑记录）。
⇒ `publish` 必须用 `data_type=proto.DATATYPE_RAW`（BSON **不支持 binary(0x05)**，
两端 bson.py 遇未知类型直接 raise ⇒ 别想着塞 BSON binary）。

### 4.2 帧大小实测（子码流 704² 源，ffmpeg `-q:v` 质量档）

| 输出尺寸 | q=8 | q=15 | q=23 | 能否单帧直发(≤12KB) |
|---|---|---|---|---|
| 704² | 66KB | 41KB | — | ❌ |
| 512² | — | 22KB | — | ❌ |
| 448² | — | 18KB | — | ❌ |
| **352²** | — | **12KB** | — | ✅ |
| 320² | — | 10KB | 7KB | ✅ |
| 256² | — | 7KB | 5KB | ✅ |

主码流：2528² q5 = **730KB**；1280² = **263KB**。

### 4.3 传输通道（已定：三端统一走 XLink 分片）

**结论（用户口径：网页端也要从服务端取数据，因为要外网访问）** ⇒ **没有任何一条路径让
浏览器/客户端直连相机**。所有画面都经服务端：

| 端 | 链路 |
|---|---|
| 桌面 Python 客户端 | 服务端 --XLink 分片--> 客户端 --组帧--> QLabel 贴图 |
| C 端客户端 | 服务端 --XLink 分片--> 客户端 --组帧--> XImage → XPainter_drawImage_3 |
| 网页端 | 服务端 --XLink 分片--> **本地 webui** --组帧--> 存最新帧 --HTTP image/jpeg--> 浏览器 `<img>` |

webui 这一层是**必须的**（不是可选优化）：浏览器在公网、webui 在客户端机器上、
相机在服务端那边 ⇒ 浏览器只能问本机的 webui，webui 再问上游服务端。
webui 已经跑在客户端侧并通过 XLink 连上游（`hub.py`），**沿用现成通道即可**。

#### 4.3.1 分片协议（应用层，覆盖 XLink 16KB 上限）

服务端把一帧 JPEG 切成若干片，每片一个 XLink 帧（`DATATYPE_RAW`）：

```
XLink 帧负载 = topicId(4B, 由 XLink 既有规则加) + 片头(16B) + 片数据(≤12KB)
片头(小端, 16B):
  u16 magic     = 0x4341 ('CA')     // 魔数，防错帧
  u16 version   = 1
  u32 frameId   // 帧序号，自增；同一帧的所有片相同
  u16 seq       // 片序号，从 0 开始
  u16 total     // 本帧总片数
  u16 width     // 图像宽
  u16 height    // 图像高
  u16 flags     // bit0=关键帧/新帧, bit1=末片
```

**组帧规则（三端一致）**：
1. 收到片 ⇒ 按 `frameId` 找/建缓冲；`seq==0` 时**丢弃同一 frameId 的旧缓冲**（覆盖式）。
2. 收到 `seq==total-1` 且 `flags&bit1` ⇒ 该帧收齐 ⇒ 校验 JPEG 头尾（`FFD8`…`FFD9`）
   ⇒ 交给显示层，释放缓冲。
3. **丢片即丢整帧**：下一帧的 `seq==0` 到来时，未收齐的旧缓冲直接丢弃（不等超时）。
4. **慢客户端不堆积**：服务端只发**最新帧**的分片序列；发新帧时，上一帧未发完的
   剩余片**直接跳过**（客户端那一帧自然作废）。⇒ 客户端看到的永远是"最近的一帧"，
   延迟上界 = 1 帧间隔 + 组帧耗时。

**为什么不用 BSON**：两端 `bson.py` 只实现 0x01/0x02/0x03/0x04/0x08/0x0A/0x10/0x12，
**binary(0x05) 直接 raise** ⇒ 帧数据必须走 `DATATYPE_RAW`（协议层支持，
`xlink.py` 的 `publish(..., data_type=)` 形参现成），片头用**定长小端二进制**编码
（不要 JSON —— JSON 会被 base64/转义再涨一截）。

#### 4.3.2 片大小与帧数的关系（704² q15 实测 41KB/帧）

| 帧尺寸 | 单帧 | 片数(≤12KB) | @5fps 片/秒 | @10fps 片/秒 |
|---|---|---|---|---|
| 704² q15 | 41KB | 4 | 20 | 40 |
| 704² q8 | 66KB | 6 | 30 | 60 |
| 2528² q5（主码流） | 730KB | 61 | 305 | —— |

⇒ 704²@10fps = **40 片/秒**（每会话）⇒ 一个客户端 40 帧/秒的 XLink 帧，
负载 10fps×41KB = 410KB/s = 3.3Mbps —— 与 §5 的带宽表一致，无额外开销
（片头 16B/12KB = 0.13%）。

## 5. 带宽与压缩（直接回答用户两问）

### 5.1 三个量级的对比

| 传输形态 | 单帧 | @1fps | @5fps | @10fps | @20fps | 客户端能解码？ |
|---|---|---|---|---|---|---|
| **不压缩**（704² RGB32 原始像素） | 1.98MB | 15.8Mbps | 79Mbps | 158Mbps | 317Mbps | —— |
| 相机原始码流（子码流 H.264） | —— | 0.51Mbps | —— | —— | （20fps 恒 512K） | ❌ 浏览器/��端都不行 |
| 相机原始码流（主码流 H.265） | —— | 2.05Mbps | —— | —— | （20fps 恒 2048K） | ❌ |
| **服务端抽帧 JPEG 704² q15** | 41KB | 0.33 | 1.6 | **3.3** | 6.6 | ✅ 三端都行 |
| **服务端抽帧 JPEG 352² q15（单帧直发档）** | 12KB | 0.10 | 0.48 | **0.96** | 1.9 | ✅ 且单帧 ≤16KB |
| 主码流抽帧 2528² q5 | 730KB | 5.8 | 29 | —— | —— | ✅（建议只在「按需取高清」时用） |

### 5.2 结论

1. **压缩是必须的**，而且**只能由服务端做**（客户端三端都解不了原始码流）。
2. 压缩后的带宽**比相机原始码流还小**（因为同时降了分辨率与帧率）⇒
   「转码转发」不但不费带宽，反而更省。
3. **省流量的三个旋钮，按性价比排序**：
   - **帧率**（线性）：20→10 fps 直接砍一半；
   - **分辨率**（平方级）：704²→352² 面积降到 1/4；
   - **JPEG 质量**（近似线性）。
4. **子码流 vs 主码流**：子码流（704² H.264 512K）解码成本低、帧小 ⇒
   **默认用子码流**；主码流（2528² H.265）只在「要看清细节/存证」时临时用，
   且降到 **1fps**（13.5% 单核）。
5. **推流节流**：客户端没订阅相机页时**不推帧**（现有 `_gate_due` 闸 + 订阅即补发
   机制直接复用）；多客户端时服务端**只解一次**、各自发一份（不按客户端重复拉流）。

### 5.3 建议的三档预设（远端设置下拉）

| 预设 | 源 | 输出 | 帧率 | 带宽 | 适用 |
|---|---|---|---|---|---|
| **巡视（默认）** | 子码流 704² | 352² q15 | 2 | ≈0.2 Mbps | 日常看一眼，**单帧直发** |
| **值守** | 子码流 704² | 704² q15 | 5 | ≈1.6 Mbps | 盯着看，需分片或走 HTTP |
| **取证** | 主码流 2528² | 2528² q5 | 1 | ≈5.8 Mbps | 单帧高清留证（按需触发） |

## 7. 风险与未决项

| 风险 | 影响 | 处置 |
|---|---|---|
| **XLink 16KB 单帧上限** | 704²/2528² 的 JPEG 传不了 | 默认走 352² 单帧直发；高质量走分片或 HTTP |

| **相机会话数上限**（未测出确切值，可能 1~2） | 多客户端不能各自拉流 | 服务端**只拉一路**，多客户端分发（设计已如此） |

## 11. 架构转向：画面直传（2026-11-19 用户拍板，**推翻 §0 的 JPEG 转发**）

用户点破："应该直接传输 H.264 数据，很多网站也是直接传输 H.264 编码数据的，
如果可以的话用 H.265 带宽还可以减半"。

### 11.1 原 §0 决策哪里错了

| §0 原前提 | 事实 |
|---|---|
| "三端客户端都解不了（浏览器不能播裸 RTP）" | 浏览器确实播不了裸 ES/RTP，但能经 **WebCodecs / MSE** 播 H.264——**网站传 H.264 就是这条路**，解码发生在浏览器，服务端从不解码。"所以要转 JPEG"是错误推论 |
| "C 端 XGui 没有视频解码器" | 成立，但用户已明确「c 端不用改」⇒ 约束消失 |
| 桌面端"不引入新依赖" | 偷懒不是技术必然：PyAV（libav 绑定）可解 |

### 11.2 新架构（transport="stream"，**缺省**）

```
相机 RTSP → 服务端 RtspClient（自研，只 SETUP track1）→ Annex-B NAL
          → 【不解码】GOP 缓冲 + NAL 切片扇出（XLink 分片，flags 带 ES 位）
                ├─ 桌面端：PyAV 解码（GPU 硬解优先 qsv/cuvid/amf，软解兜底）
                ├─ 网页端：WebCodecs VideoDecoder + canvas（/api/camera/es 增量）
                └─ C 端：不实现（占协议号）
transport="jpeg"（旧路）保留为配置兜底：gst 硬解→软编 JPEG，老客户端可用。
```

**收益（实测）**：服务端相机 CPU 从 gst 58% + 服务端 34% 单核 ⇒ **≈0**；
帧率 2fps ⇒ **相机自身 20fps**（JPEG 2fps 本身就是幻灯片——这是"卡顿"的
真正主因）；带宽 0.42~0.8Mbps ⇒ 0.5Mbps 定档（不升反略降）。

### 11.3 H.265（用户要求，配置可选）

- 相机两条码流都支持 H265（能力表 §1.2 实测）；配置键 `codec=h264|h265`。
- 子码流 512K → **~256K**（外网带宽场景收益 50%，用户口径正确）。
- **浏览器是拦路虎**：H.265 只有带硬件解码的 Chrome/Edge/Safari 支持
  ⇒ 页面 `isConfigSupported` 探测，不支持明确提示（不黑屏）。
- H.265 的真正主场是**主码流** 2528²（H265 2048K vs H264 需 4-6M）。

### 11.4 桌面端 GPU 硬解（用户问"桌面端可以用GPU硬解吧"）

PyAV(FFmpeg) 硬解后端逐家 GPU：Intel=qsv、NVIDIA=cuvid、AMD=amf（**没有**
通吃的 Media Foundation 解码器——ffmpeg 的 `*_mf` 只是编码器）。
`hwDecode=auto`（远端设置可编辑）：按 qsv→cuvid→amf 试，**真解出首帧才算
可用**，否则回落软解。本机 Intel UHD 770 实测 qsv 出帧且像素可取；
cuvid/amf 干净失败（auto 回落的必要性实证）。**704²@20fps 软解仅
0.47ms/帧** ⇒ 桌面硬解收益本来就小，主码流 H.265 时才有意义——接口已留好。

### 11.5 全屏播放（2026-11-19 追加需求「类似网站视频的播放界面」）

- 桌面端：画面行「全屏」钮 / **双击画面** ⇒ 独立全屏覆盖窗（黑底铺满 +
  100ms 自刷 + 右上角退出钮 / Esc / 双击退出；与页面共享 model 不另拉流）。
- 网页端：画面区 `requestFullscreen()`（浏览器原生）+ `.camera-stage:fullscreen`
  CSS 铺满规则。

| **硬件 JPEG 编码** | **不可用**（色度平面解析错误、颜色偏紫、q-factor 失效、零拷贝/强制格式全部无解）⇒ 见 §2.5；`transport=jpeg` 时用**软件 `jpegenc`** |
| **管线顺序** | **`videorate` 必须在 `videoconvert` 之前**：295% → 47%（2fps）—— CSC 成本 ∝ 它处理的帧率 |
| **`quality`** | 与 CPU **无关**（只影响体积/带宽） |
| **`transport=stream`** | 板端是**近零 CPU** 的正解，但要求浏览器有 WebCodecs；用户手机自带浏览器不支持 ⇒ 当前板端跑 `jpeg` 通道，stream 留作可选 |
| **MAC 连接动态 IP** | 必须扫**本机所有网段** + 可达性验证（相机换网线后 IP 从 192.168.1.181 → 10.168.1.101，MAC 未变） |
| **重启相机丢画面** | 五层根因（静默空转 / 会话槽堆满 / 管线静默失败 / 线程静默死亡 / Windows GBK）全部修掉 |
| **触摸屏全屏** | 全屏必须做**主窗内覆盖层**，独立顶层窗会让 Qt 触摸状态机卡死（鼠标路径复现不出来） |

**板端实测基线**：2fps / 704² / q80 / JPEG 软编 ⇒ gst **47% 单核**、
服务端 VmData 收敛、fd/线程恒定、客户端与网页 VmData **零增长**、
整机负载 **1.13~1.7**（改造前 4.0+）。
