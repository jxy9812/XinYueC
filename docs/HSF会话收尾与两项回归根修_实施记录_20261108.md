## 一、本轮处理的两项回归（均已根修 + 实测验证）

### 1. `XGuiRegression_Test.exe` 稳定段错误

**现象**：`cd bin && ./XGuiRegression_Test.exe` 稳定 `exit=139`（连跑 3 次），
输出停在 `[WHEEL] lag=...`，`FAIL:` 计数 0（崩溃前无断言失败）。

**根因（本轮改动引入，cdb 铁证）**：
- cdb `sxe av; g; r; ln @rip; u @rip` 抓到故障指令
  `mov eax,[rax+1Ch]; shr eax,3; and eax,1`（`VXAbstractEventDispatcher_processEvents+0x3f3`），
  `rax` 为 page-heap 已释放块；对应 C 源码
  `Src/XCore/XCode/XEvent/XAbstractEventDispatcher.c:700`
  `if (!ePost->m_receiver || ePost->m_receiver->m_is_deleting_children)`
  —— 派发循环读到 posted 队列里**残留的悬垂 `m_receiver`**。
- 上一手本会话早前为修「HsfClient 退出时 AV」，在
  `Src/XCore/XClass/XObject.c` 的 `VXObject_deinit` 里把
  `XAtomic_store_uintptr_t(&object->m_threadData, NULL)` 从函数**末尾**挪到了
  **开头**（「threadData 提前取快照」）。但 deinit 中段紧接着仍执行
  `if (XObject_thread(object) == XThread_currentThread())
   XCoreApplication_removePostedEvents(object, XEVENT_TYPE_NONE);`
  与 `XObject_eventDispatcher(object)`（定时器注销）——两者都经 `m_threadData`
  取线程亲和性。槽位被提前清空 ⇒ `XObject_thread()` 恒返回 NULL ⇒
  **posted 事件清队被整段跳过** ⇒ 对象析构后队列残留悬垂 receiver。
- 反汇编佐证（`uf VXObject_deinit`）：`+0x3b` load `[obj+0x48]` → `+0x61`
  store NULL → `+0xb8` 才 call `XObject_thread` → `+0xd5 jne` 跳过
  `removePostedEvents`。确系「先清后判」。
- 图表车道不是崩溃源：上一轮把 8 个图表框架文件 `git checkout` 还原后重编
  仍崩（`/tmp/xgui_base.log`）；`test_chart_interaction_contract` 里的
  `int x; int y;` 与 `XChart_mapToPosition` 签名匹配，已排除栈破坏。
- 静态宿主 `--test xlink` 820/0 通过不矛盾：非 GUI 路径不产生带残留 posted 的泵。

**修法（Qt 6.8.3 对标）**：D 盘 Qt 源码
`/d/Qt/6.8.3/Src/qtbase/src/corelib/kernel/qobject.cpp` 的
`QObjectPrivate::~QObjectPrivate()`（:184-206）标准答案是：
开头只 `auto thisThreadData = threadData.loadRelaxed();`（**只 load 快照，不 store**），
中段用它判断线程亲和性做 `unregisterTimers` + `removePostedEvents`，
末尾才 `thisThreadData->deref()`；**整个析构从不把 threadData store 成 nullptr**
（全文件仅 :953 构造 `storeRelaxed`、:1789 `moveToThread` 的 `storeRelease`）。
`QObject::thread()`（:1599）就是 `threadData.loadRelaxed()->thread.loadAcquire()`，
依赖槽位有效。`removePostedEvents`（qcoreapplication.cpp:1980）注释明写
「the QObject destructor calls this function directly」。

本框架修法 = 保留开头「读快照到局部 `deinitTd`」（守住 HsfClient 退出时
`XThreadData_deref` 读脏指针那个修复），把 `store NULL` + `deref(deinitTd)`
**挪回函数末尾**。仅 `Src/XCore/XClass/XObject.c` 两处 Edit，架构不变。
已评估但不做的 Qt 式硬化：`XObject.c:55/:66` 与 `:50` 同处「内存必然完好」
窗口、早于 `:70` 级联；`removePostedEvents` 自身不 deref receiver 的
threadData；级联期间补投由 `m_was_deleted` + `XThreadData_postEvent`
「濒死接收者拒收」（XThreadData.c:419-433）兜住。扩大 diff 收益小于成本。

**验证**：`cmd //c /tmp/build_reg.bat` build=0（23:21:23 重编，含图表车道 +
本修复）→ `XGuiRegression_Test.exe` **EXIT=0 / FAIL=0 / `XGui regression tests passed`**。

### 2. `test_vfd_combo.py` 4 项异常

**现象**：`操作 38 步 × 2 轮，异常 4 次`；两轮各重复
`[FAIL] 再启动（备点动断言） 无法进入运行态` 与
`[FAIL] 运行中点动置灰 model running=False fresh=True 数据龄=156ms out=-1.0Hz`。
更早（11:05 / 12:58）该脚本是 0 异常。

**根因（C 侧 VFD 设备层运行位死锁）**：
- `Src/Industry/XVfd/XVfdDevice.c:673-685` 本轮新增「停机斜坡期强制
  `st->m_running=false`」：`m_stopRequested==true` 且输出 > 0.15Hz 时，
  每拍 decode 强制报 `running=false` + `runState=Decelerating(8)`。
- `m_stopRequested` 仅由 `stop`(:915)/`quickStop`(:930) 置 true，仅在
  `deriveRunPhase:686`（输出降到 ≤0.15Hz）清除；**`XVfdDevice_start`
  (:889) 原来不清它**。
- 测试序列「（运行中）点停止 → 很快点启动」：STOP 置位，START 把输出重新
  拉向给定（25~40Hz）却不清标志 ⇒ 输出恒高于死区、标志永远清不掉 ⇒
  运行位被永久锁在 False。于是 `_ensure_running()` 等不到 running、
  点动钮因 `running=False` 不置灰。
- `out=-1.0Hz` 是 `test_vfd_combo.py:146-147` 的哨兵值
  （`st.output_freq_hz if st.running else -1`），**非真实负频率**。

**证据链（对照实验）**：

| 对照 | 结果 |
|---|---|
| 6100 共享实例连跑 2 轮 | 稳定 4 FAIL（步骤 34→35→36 / 74→75→76） |
| 全新 6101 实例**立刻**跑 | 同样 4 FAIL，`fresh=True 数据龄=31/156ms` → 排除「长跑状态污染」与「485 注入自愈漏覆盖」 |
| 全新 6102 最简序列 STOP→立即 START | 死锁：`running` 恒 False、`out` 爬到 25、`runState=8` |
| 全新 6103 对照组 STOP→等归零→START | 正常进入运行态 → 坐实死锁唯一条件 |
| **Python 参考服务端 6200 同一份脚本** | **0 异常通过** → 根因在 C 侧 |
| Python `devices.py:602` | OP_START 分支有 `self._stop_requested = False`，C 侧缺这一句 → 两端口径漂移 |

**修法**：`XVfdDevice_start()` 开头补 `dev->m_stopRequested = false;`
+15 行注释（对齐 Python `apply_control` 的 OP_START 分支），仅 1 个文件
+16 行。`jog/freeStop/resetFault` 保持与 Python 一致（均不清该位），未动。
注意：该修复 23:23 落盘，**晚于 22:38 的服务端构建**，故 6100/6101 旧
二进制上的复现是预期；必须重编才生效。

**验证**：`build_hsf.bat` build=0（HsfServer.exe 23:30:37 重编）→ 重启
`--sim` 6100 → `test_vfd_combo.py --port 6100` **连跑 2 次均
「38 步 × 2 轮，异常 0 次 / ===== 通过 =====」**；`test_client.py`
**105 passed / 0 failed**。
