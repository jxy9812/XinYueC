## 1. 任务 A：X11 fd 并入 ring 等待集（风险最高，单独立项）

### 1.1 现状（代码实测，非推测）

三处相关代码：

| 位置 | 职责 |
|---|---|
| `Drive/Posix/Graphics/XPlatformNativeWindow_posix.c:2445` `xpwn_x11WakeWatch` | **常驻监视线程**：`poll(X11 fd, -1)` 阻塞；可读即 `XAbstractNetIoRing_wakeUp_base(ring)`（写 ring 的 wake eventfd）唤醒主循环 |
| 同文件 `:7023` `XPlatformNativeWindow_waitForEvents` | **双源 poll**：`poll{X11 fd, ring event fd}`——但**只有 `XGuiApplication_waitForEvents` 自绘主循环可达** |
| `Src/XCode/XEvent/XAbstractEventDispatcher.c:823` | **exec 标准主循环**的唯一阻塞点：`XAbstractNetIoRing_waitForEvents_base(ioRing, timeoutMs)` → POSIX 侧 `epoll_wait(m_epollFd, …)` |

**关键事实（决定了本任务不是简单替换）**：

1. **exec 主循环只 poll ring 的 epoll fd，X11 fd 不在其中**
   （`XNetIoRingPosix.c:1275` 起的 `epoll_wait` 等待集 = epoll fd 自身）。
   X11 输入要唤醒 exec 主循环，**当前唯一手段就是监视线程写 wake eventfd**。
   文件头 `:435-455` 的方案说明写明了这个取舍，并说
   「dispatcher 侧增加『额外等待 fd』通道超出本文件所有权」。

2. **双源 poll 那条路在 demo 里是死的**。全仓 `XGuiApplication_waitForEvents`
   无调用者；demo 走 `XGuiApplication_exec()` → `XCoreApplication_exec()`
   → `XEventLoop_exec` → dispatcher → **ring 的 `waitForEvents`**。
   ⇒ 「等 ring 唤醒」这条路是**活的且唯一**，不能绕。

3. **X11 事件的真正消费点不在 ring 里**。`XPlatformNativeWindow_processPendingEvents`
   （`:6965`）才是泵空 X11 事件的地方，它由 `XGuiApplication_pumpNativeEvents`
   经 `XAbstractEventDispatcher_addPollCallback`（`XGuiApplication.c:540`）
   注册进 dispatcher 的**轮询回调链**，在**事件循环圈边界**执行。
   监视线程只负责「唤醒」，**不碰 `Display*`**（Xlib 单线程约定）。

4. **X11 fd 是 level-triggered**。监视线程为此专门做了 4ms 限幅再武装
   （`:2440` 注释：避免主线程未泵空期间重 poll 立即返回造成空转，
   把重唤醒频率封顶在 250 次/秒）。**任何新方案都必须继承这个限幅语义**，
   否则 X11 fd 常驻可读会把 ring 等待集变成忙转。

5. **被动 fd 机制已存在且有先例**：`Drive/Posix/Graphics/XPlatformFbInput_posix.c:1375`
   把 evdev 触摸 fd 注册进 ring（`registerPassiveOsFd_base`），注册失败时
   保留轮询回调兜底；POSIX 串口 `:371` 同理。**本任务是同一机制的第三次应用**，
   机制本身已被真机验证（触摸唤醒通道，见
   `docs/xgui/2026-10-26-fbdev-touch-wakeup-diagnosis.md`）。

6. **被动 fd 的分派只在阻塞路径发生**：`epDispatchPassive` 仅在
   `VXNetIoRingPosix_waitForEvents` 的 `epoll_wait` 之后调用
   （`XNetIoRingPosix.c:1331`）；**非阻塞的 `epPollPlatform`（`:919`）不分派被动 fd**。
   ⇒ 被动 fd 的回调只在「ring 真正阻塞等待」时触发，这正是我们要的语义，
   但也意味着**回调必须自己把 X11 事件泵空**（否则 level-triggered 反复触发）。

7. **容量与引擎**：`XNET_PASSIVE_MAX = 8`（`XNetIoRingPosix.c:108`），
   触摸 fd 已占 1、串口已占 1，X11 再占 1 ⇒ 仍有富余。
   Windows 侧 `registerPassiveOsFd` **恒返回 false**
   （`XNetIoRingWin32.c:218`：IOCP 无「只读设备 fd 挂进完成端口」原语），
   ⇒ **本任务天然是 POSIX-only**，Windows 侧无需改动、也不受牵连。
   引擎：RK3568 内核 5.10.209 ⇒ 走 **io_uring**（版本门 ≥5.10）；
   桌面亦可能走 io_uring。**两条引擎路径都要测**（`XNET_FORCE_EPOLL=1` /
   `XNET_FORCE_IOURING=1`）。

### 1.2 目标形态

```
X11 fd 可读
   ⇒ ring 的 epoll_wait / io_uring POLL_ADD 直接返回（不再经监视线程 + eventfd）
   ⇒ 被动 fd 回调在主线程上被调用
   ⇒ 该回调把 X11 事件泵空并注入框架（复用 processPendingEvents 语义）
   ⇒ 删掉 xpwn_x11WakeWatch 线程
```

收益：
- **少一个常驻线程**（用户诉求：「统一走框架自己的 ring，线程多了容易数据竞争」）。
- 唤醒路径少一跳（原来：X11 → 线程 poll → eventfd → epoll_wait → 主循环）。
- 与触摸唤醒通道、串口通道**同构**，架构一致。

### 1.3 关键设计约束（实施时必须逐条守住）

| # | 约束 | 理由 |
|---|---|---|
| C1 | **Xlib 单线程约定不破**：新回调只能在主线程触碰 `Display*` | 监视线程的现状是刻意如此（`:2440` 注释）。ring 的被动 fd 回调在哪个线程执行，取决于引擎与路径，**必须先确认** |
| C2 | **level-triggered 限幅必须保留**：回调内泵空后若 fd 仍可读，需限幅重试，不得忙转 | 否则 ring 等待集变成忙转，实测会吃掉板端 CPU（板端基线 CPU 仅 8~9%） |
| C3 | **回调不得在 ring 内部重入 ring**（如在被动 fd 回调里再调 `processReady`） | 阻塞等待路径上重入 epoll 语义未定义 |
| C4 | **连接死亡检测不能丢**：监视线程现在监控 `POLLERR/POLLHUP/POLLNVAL` 并退出（`:2459`） | X11 连接断开后若仍留在等待集，`epoll_wait` 会**立即返回**（HUP 恒可读）⇒ 忙转。替代方案：注册失败/连接异常时**注销**该 fd |
| C5 | **fd 生命周期**：注册前确认 X11 fd 稳定（`XConnectionNumber` 在连接建立后不变）；连接重建时须先注销旧 fd 再注册新 fd | 等待集里留将失效的 fd ⇒ EBADF / fd 号复用（fbdev 侧已有同样的告警注释） |
| C6 | **Windows 零影响**：`registerPassiveOsFd` 在 Win32 恒 false ⇒ 走原有路径 | Windows 输入本就由窗口消息驱动 |
| C7 | **被动 fd 表容量**：8 槽，当前占 2（触摸/串口），X11 占 1 | 需确认 `XNET_PASSIVE_MAX` 未被其它用途占满 |

### 1.4 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **R1 输入延迟劣化**：X11 事件要多走一层 CQ/回调才派发 | 中 | **高**（键盘/鼠标手感） | 主验收门槛；见 §1.5 的 `[wake][ring] enterToWakeUs` p95 对比 |
| **R2 忙转**：X11 fd 常驻可读（level-triggered） | 中 | 高（板端 CPU 飙升 + 事件循环空洞 → **可能反向制造 485 尖刺**） | C2 限幅 + CPU 门槛 + `[ILOOP]` 无高频短等待 |
| **R3 连接死亡后忙转** | 低 | 高 | C4：HUP/ERR 时注销 fd |
| **R4 引擎差异**：io_uring（板端）与 epoll（可强制）语义不一致 | 中 | 中 | 两条引擎各跑一遍完整验收 |
| **R5 回调在非主线程执行**（某些引擎/路径下） | 中 | 高（Xlib 崩溃） | C1：实施前先确认回调执行线程；必要时在回调内只置标志、由主循环泵空 |
| **R6 既有 `XPlatformNativeWindow_waitForEvents` 双源 poll 与新机制重复等待** | 高 | 低 | 该路径 demo 不可达；本次**不动它**，或在实现时评估删除 |
| **R7 输入回归**（时序敏感功能） | 中 | 高 | §1.5 全套门禁 |

## 2. 任务 B：从站页 `MbSlaveRoot` 启动帧整块标脏（启动期优化，低优先级）

### 2.1 现状（代码实测）

- `:3397` `mb_slaveSyncViewport()` 在「列数或点数真变」时调
  `mb_slaveRebuildGrids()`；紧凑/宽档切换时先置 `gridCols = -1` 强制重建。
- `MbSlaveRoot`（`:4859`）是**滚动内容根**（1007×2284），其 `resizeEvent`

**实测数据**（§17.1，板端 rprof 画像）：

### 2.2 边界（**重要：不是尖刺来源**）

§18.1 已用板端画像定案：

- 该 2.3M 像素**只出现在启动帧**；稳态帧的单笔入队最大只有 10,752
  （`XLabel` 192×56）。
- 尖刺根因是**框架脏区口径**（多矩形→外接矩形），已在 `XWidget.c` 修完；
  485 尖刺归零**与本项无关**。

⇒ **别再把它当尖刺源追**（§18.1 与交接文档都已明写）。

### 2.3 收益上界（诚实评估）

- 内容根 1007×2284 ≈ 2.3M 像素，其中**视口外**部分（内容高 2284 vs 视口 ~774）
  本来就不可见。
- 但**绘制阶段已按父客户区逐级裁剪**
  （`XWidget_paintTree` 的 `visibleRect` 相交 + surface clip 收窄），
  且上屏时 `XPlatformBackingStore_flush` 会按 image 尺寸裁剪
  （`xpbs_clipRegion`，`XPlatformBackingStore.c:1099`），
  `XImage_fillRect` 也会自裁（`XImage.c:5626`）。
  ⇒ **实际多画的像素远小于 2.3M**。

**结论**：本项的收益**上界是启动帧的一次性开销**（首帧多画/多算的量，
量级估计为「视口外内容高度」对应的一块），**不会改变稳态帧率，
不会改变 485 时延**。收益有限、风险不低 ⇒ 优先级低，**排在任务 A 之后**，
且**不要与任务 A 同一个分支**。

### 2.4 候选方案（三选一，实施时定）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **B-1（推荐先评估）** | 灯格重建时**只标脏受影响的灯格矩形**，不整块标内容根 | 改动局限 demo 层；收益直指目标 | 需框架提供「按矩形标脏」入参（`XWidget_updateRect` 已有）；要确认布局重排本身是否仍会标根 |
| B-2 | 灯格**不重建**，改为复用 + 只改几何/文本 | 根治重建诱发的整块失效 | 改动大；灯格是 `XCheckBox` 子类，复用语义要逐个核 |
| B-3 | 框架层：`XWidget_addDirtyRegion` 按**可见区域**裁剪入队（已有 `XWidget_visibleRegion()`） | 一处改动全局受益 | **框架层**，风险最高，且影响面远超「启动期优化」定位 ⇒ 不建议在本项做 |

### 2.5 验收门槛

| 指标 | 工具 | 门槛 |
|---|---|---|
| 启动帧最大单笔入队 | `XGPU_W_FRAME_PROF=1 XGUI_RPROF_BT_MIN_PIX=200000` | `enq max` 从 2,299,988 降到**视口量级**（~10^6 以下，具体目标值实施前定） |
| 启动帧总耗时 | 同上 `[wprof] tot=` | 相对基线改善可测（≥20%） |
| **稳态帧率/帧面积** | 同上 `[rprof] sumAvg=` | **不得劣化**（稳态本来只有 10,752，若变大即回归） |
| 视觉一致性 | `verify/ab_render_diff.py`（桌面 7 页：1,2,3,4,5,17,18） | 静态差异 **必须为 0** |
| 从站页交互 | `XGuiWindowDemo_Test --autotest` + 板端手风琴/翻档/滚轮 | 无新增失败 |

## 3. 排期与依赖

```
任务 A（高风险，输入回归为主门槛）        任务 B（低优先级，启动期）
├─ S1 开关骨架（可独立上线）              └─ 先做「收益上界」实测
├─ S2 注册 + 回调泵空（与旧路径并存）        （B-1 原型 → 画像对比）
├─ S3 全门禁（含板端 CPU/485）              └─ 视觉 A/B + 稳态无回归
├─ S4 删监视线程 + 清理 pthread              
└─ S5 复门禁 + 板端 485 + 像素 A/B          
```

- **不并行**：A 与 B 都触碰 XGui 输入/渲染时序（A 碰输入等待，B 碰脏区/重绘），
  且 B 的验收指标（`sumAvg`/`enq` 画像）会被 A 的改动干扰 ⇒ **串行，A 先 B 后**。
- **A 必须单独分支**（用户明确要求「单独立项做输入回归」）。
- **B 可在 A 收口后另起分支**，或直接降级为「只做收益上界实测，暂不实现」
  —— 鉴于 §2.3 的收益上界分析，**降级是合理选项**。
