## 2. 根因一：从站把「解析帧」绑死在帧间静默定时器上（板端，最大头）

文件：`Src/XProtocol/XModbus/XModbusRtuSerialServer.c`

原实现 `onReadyRead` 只做两件事：把字节读进缓冲、`receiveBufferTimerStart(server)`
起一个 `(帧间延迟 + 1ms)` 的 CoarseTimer。**只有这个定时器到期才调
`processReceiveBuffer` 解析帧**，即从站必须等「静默窗到期」才应答。

而这个定时器在主循环里兑现。板子主循环一圈 60~200 ms（见 §5），于是
8 字节、传输仅 9 ms 的请求，从站要 139 ms 才回应答。

修法：新增 `tryProcessCompleteFrameNow()`，在 `onReadyRead` 末尾追加调用。
RTU 请求的帧长是自描述的（`calculateRtuFrameLength`：0x01~0x06 恒 8 字节，
0x0F/0x10 由字节数字段给出，其余同理），所以**只要缓冲里凑满一帧且 CRC 正确
就直接解析应答**，不再等静默。

```c
/* Src/XProtocol/XModbus/XModbusRtuSerialServer.c:635 */
static bool tryProcessCompleteFrameNow(XModbusRtuSerialServer* server);
```

静默定时器**保留**，职责收窄为：半帧、坏帧、未知功能码的回退扫描。
两条路径对 `processReceiveBuffer` 幂等（缓冲空则空跑），即时兑现成功会消费掉
该帧，定时器到期只剩空缓冲，**不会重复应答**。

## 3. 根因二：主站「撞拍空等整拍」

文件：`Test/XGuiDemo/xgui_demo_page_modbus.c:2027`

原逻辑是纯「定时器拍 + 在途门控」：`mb_masterPollTimerCb` 每 50 ms 触发一次，
若上一请求还在途（`pendingReply` 非空）就 `SKIP`。问题在于——**应答若在拍边界
之后才回来，这一拍整拍空转，下一拍要再等满 50 ms**。实际周期退化成 2× 设定值。

实测证据：修复前请求间隔分布呈 `47 / 94 / 110 ms` 三簇并存，正是「撞上边界」
与「错过边界等整拍」的混合。

修法：应答收口后，若本拍已耗时 ≥ 设定周期就直接续拍（相位由应答对齐）；
未到周期仍交给定时器在边界兑现（不打破限速语义）。

```c
/* Test/XGuiDemo/xgui_demo_page_modbus.c:2027 [应答驱动续拍] */
if (!s_mb.pendingReply && !s_mb.deferredWriteUnit && s_mb.device) {
    double expectMs = s_mb.pollSpin ? XSpinBox_value(s_mb.pollSpin) : 200.0;
    if (mb_traceLastSendT > 0.0 &&
        (mb_pollTraceNow() - mb_traceLastSendT) * 1000.0 >= expectMs)
        mb_masterPollOnce();
}
```

安全前提（已在代码注释写明）：本槽处于 reply `finished` 同步链内，client 的
收口路径在 `if (!client->m_currentReply) startNewRequest()` 之后才返回；此处
提交新请求会被 `sendRawRequest` 的内层泵立即发出并由 `m_currentReply` 占位，
不会与「外层再泵」抢同一条队列（与既有 deferredWrite 写让路同款论证）。

## 4. 根因三：`XTimer_setInterval` 运行中改周期不生效

文件：`Src/XTimer/XTimer.c:60`

```c
/* 原实现 */
void XTimer_setInterval(XTimer * timer, size_t value)
{
    if (timer) XTimerData_setInterval(&timer->m_timerData, value);  /* 只赋值 */
}
```

为什么这不生效：
1. 时间轮节点在 `create_timer_node` 里对 `XTimerData` 做的是**值拷贝**
   （`XTimeWheelGroup.c:158` `timer_data->m_data = *data`），周期重装读的是
   节点副本的 `m_interval`，改对象字段不影响节点；
2. `VXObject_timerEvent` 只在 `m_firstTrigger == false` 的**首拍**按字段值重装
   一次，之后节点自持周期副本，不再回读对象。

后果：**连接后再改「轮询(ms)」完全不生效**，仍按建连时的周期跑。这解释了
「设 50 结果还是 1 秒」的一部分现象——断开重连会重建定时器读到新值，所以该
现象时好时坏、容易被当成偶发。

修法：运行态走 `stop` + `start` 重装（`XTimer_start_base` 会按新字段值重新
注册、时间轮按新周期重新落槽）；未运行时只存字段，等 start 生效。

```c
/* Src/XTimer/XTimer.c:60 [改周期重装 2026-10-29] */
void XTimer_setInterval(XTimer * timer, size_t value)
{
    bool wasRunning;
    if (!timer) return;
    XTimerData_setInterval(&timer->m_timerData, value);
    wasRunning = timer->m_isRun && timer->m_timerData.timerId != XTIMER_INVALID_ID;
    if (wasRunning) XTimer_start_base(timer);
}
```

## 5. 板端主循环为什么那么慢（背景，未修）

不是 Modbus 的问题，但它是「从站 139 ms」的放大器：

- 板端日志长期刷 `[WHEEL] lag=…`，3000 样本统计 **p50=108 / p90=155 / max=200**
  （即时间轮 handler 每拍被滞后 100 ms 量级）。
- 从站进程 strace：8 秒内 1634 次 `writev` 到 X11，合计 **214 MB**（约 27 MB/s、
  约 204 次/秒），单次中位 178 KB、最大 255 KB —— 基本是整窗在反复提交。
- CPU 分布：`XGuiWindowDemo` ~38%、`Xorg` ~54~68%。
- 板端截图 HUD 读数：**FPS 6.6、CPU 76%**。

已验证但**未采纳**的手段：`XGUI_REPAINT_MAX_FPS=10` 能把 X11 流量压到约 1/4，
但 `lag` 仍 110~230 ms 不降 —— 说明存在与渲染负载无关的固定节拍（handler 约
每秒被真正推进一次、每次推进约 1000 拍）。这条线索留给后续，**本次未动**。

> 注意：即使主循环慢，§2 的修法已让从站应答脱离主循环节拍（0.6 ms），
> 所以这个问题对 485 轮询不再是阻塞项。

## 6. 剩余上限：78 ms 是波特率的物理下限

修复后 `SEND→RECV` 仍是 p50 78 ms，这已经**不是 bug**：

| 项 | 9600 bps 下耗时 |
|---|---|
| 请求 8 字节（含 3.5 字符静默） | ~9 ms |
| 应答 37 字节（IR/HR 相，20 寄存器） | ~42 ms |
| 串口 RX 轮询（`XSerialPort_DefaultRxPollIntervalMs` = 2 ms）+ 主循环节拍 | 余量 |
| **合计** | **~78 ms** |

要再快只能提高波特率，而这卡在 §7。

## 7. 已修（2026-10-29 晚，换机接手当天闭环）：板端从站 115200 不生效

**真根因：应用层把 `XString*` 对象指针直接喂 `atoi`，解析恒败 → 永远走 9600 兜底。**

- `Test/XGuiDemo/xgui_demo_page_modbus.c` 的 `mb_slaveApplyChannelParams`（以及
  主站 RTU 分支、启动失败诊断日志共 **3 处**）原写法：
  `baud = atoi(XComboBox_currentText(combo));`
- `XComboBox_currentText` 返回的是**新建 `XString*` 堆对象**（UTF-16 存储，
  首成员是 `XContainer parent` = vtable 指针），不是 C 字符串。`atoi` 把
  对象头当文本解析，首字节非数字 ⇒ 恒返回 0 ⇒ 撞上 `if (baud <= 0) baud = 9600`
  兜底。**下拉/环境变量选什么波特率都不生效，恒 9600**；
- 这同时解释了本节现象的全貌：页面日志用的是 `XComboBox_currentText_2`
  （正确 UTF-8 文本）打出 `baud=115200`，而 open 实际拿到的连接参数是兜底
  9600 —— 日志与 termios 读回不一致正是「解析环节坏了」的指纹；
- 顺手修掉：原实现每读一次 `currentText` 漏一个 `XString`（新建副本无人删）。

§7 原「下一步怀疑点」逐条作答：
1. `VXModbusRtuSerialServer_open` 先 close 再 open 与双开守卫 **无关**（本次
   未触发，且 close 会先恢复原 termios 再按新参数重开，顺序正确）；
2. 从站页参数时序 **无关**（`mb_slaveApplyChannelParams` 在 connect 前执行，
   参数确实写进了 `SerialBaudRateParameter`——写进去的值是错的 9600 而已）；
3. `posixApplyConfig` 前后日志确认：**参数「传到了」但值本身就是 9600**。
   平台层（`Drive/Posix/Device/XSerialPortPosix.c`）与设备层全程无辜，与
   原「已核对为正确」结论一致。

修法：新增 `mb_parseBaudCombo()` 助手——`XString_toInt(text, NULL, 10)`
（XString 自带转数字 API）+ 显式删除 `currentText` 新建副本；三处调用点
（主站 RTU 参数 ~2200 / 从站参数 ~3447 / 失败诊断 ~3614）统一走助手。

验证（桌面 Xvfb + pty 端到端，走的与板端同一条
`VXModbusRtuSerialServer_open → XSerialPort → posixApplyConfig → tcsetattr`
链路，平台无关）：
- `XGUI_DEMO_MB_SLAVE_BAUD=115200` → `stty -F <pty>` 读回 **speed 115200**；
- `XGUI_DEMO_MB_SLAVE_BAUD=9600` → 读回 speed 9600（波特率真正跟随选择）；
- 门禁：`XGuiRegression_Test` 0 失败、`XGuiWindowDemo_Test --autotest` 0 失败
  （与 HEAD 逐字节一致；首跑见到的 6 失败+退出段错误为拉取前旧回归二进制
  假象，重编后消失）。

**注意：主站页同款 bug 一并修掉** —— 此前主站 RTU 的波特率选择同样恒
9600（§7 试验里「主站用 115200」若经下拉/env 设置，实际也未生效过）。

**不是 Linux 平台限制**（保留原结论）：板子 `stty -F /dev/ttyS3 115200` 直接
有效，UART/内核支持 115200；框架自 init 的 19200 默认值也非现场所见 9600
的来源（9600 只能来自本次的兜底分支）。

RK3568 真机复验状态：本机（Linux）无 aarch64 交叉链、板端 22 端口不通，
**改在 mcgs 屏（192.168.1.252，armel 同一代码）上真机复验**，结果见 §12。

> **换机静态复验对照（2026-10-29，另一台机 D:\code\CMake\XinYueC 独立复核，
> 随 35d601ec 入库）**：该机对上述怀疑点 1/2/3 的低层链路（Server open 时序、
> 页面参数时序、设备层字段传递）复核结论「均为正确」，与本节逐条作答一致；
> 其对 9600 来源的推断（「只能来自 XSerialPort_init 默认值 ⇒ 目标进程没跑
> 当前代码」）因未审计到应用层 `atoi(XString*)` 这一步而被本节根因取代——
> env 确实生效了（字符串进了参数），坏在解析环节。其板端三查
> （pgrep/environ/exe 时间戳）仍是排查「服务没拉起新二进制」的通用首查，
> 保留备查。

## 13. 第二层根因（2026-10-30 续）：RK3568 上 115200 仍不生效

### 13.1 为什么 §7 的结论在 RK3568 上不成立

§7 的根因（应用层 `atoi(XComboBox_currentText(combo))` 把 `XString*` 对象头当
C 字符串解析 ⇒ 恒 0 ⇒ 永远走 9600 兜底）是**真实且必须修**的，远端修得对，
并已在 mcgs 屏（armel）真机验证通过。

但 §7 之后 RK3568 上仍测出 `stty -F /dev/ttyS3` 恒读回 **9600**。加打点
（应用层 `BAUDDIAG` + 平台层 `BAUDDIAG`）后实测：

```
BAUDDIAG slave idx=7 text=115200 parsed=115200
BAUDDIAG posix req=115200 speed_t=115200 ispeed=13 ospeed=13 set_rc=0 get_rc=0
```

⇒ **应用层参数已经是 115200**（§7 的修复生效），但**平台层落盘后 termios 仍是
13（B9600）**，且 `tcsetattr` 返回 0（“成功”——因为内容根本没变）。

### 13.2 真根因：`cfsetispeed` 的编码值与目标 libc 不匹配，且**静默失败**

交叉编译命中的头文件是**宿主 glibc**（gcc 内建 `/usr/aarch64-linux-gnu/include`
优先于 `-I sysroot/usr/include`——正是工具链文件注释里那条老坑），而运行目标是
**板端 glibc 2.31**，两者的 `B*` 常量取值不同：

| | `B115200` |
|---|---|
| 宿主 glibc 2.39（编译期命中） | `115200` |
| 板端 glibc 2.31（运行期） | `0x1002` = `4098` |

`posixBaud()` 原来直接 `return B115200;`，编出来的是宿主口径的 `115200`；
板端 libc 收到不认识的编码值 ⇒ `cfsetispeed` 返回 `-1`（EINVAL）且**不改字段**，
而原实现**忽略返回值** ⇒ termios 保持旧速率 ⇒ 表现为「选什么波特率都停在 9600」。

这也解释了 §12 的不对称：mcgs 屏用 armel 工具链，其编译期头与运行期 libc 同源，
`B*` 取值一致 ⇒ §7 的修复单层就够；RK3568 的 aarch64 工具链跨了 glibc 版本，
必须再修平台层这一层。

### 13.3 修法（`Drive/Posix/Device/XSerialPortPosix.c`）

不再依赖编译期 `B*` 宏，改为**候选序列 + 以 `cfsetispeed` 返回值判定**：

1. 首选**内核传统编码**（自备常量，与各 glibc 版本一致、也是内核 termios 期望
   的编码）：`B9600=13 / B19200=14 / B38400=15 / B57600=0010001 /
   B115200=0010002 / B230400=0010003 / B460800=0010004 / B921600=0010010`；
2. 若目标 libc 拒绝该编码（`cfsetispeed` 返回非 0），回落到编译期 `B*` 宏口径
   ——覆盖「目标 libc 用新编码」的平台；
3. 两者都以 `cfsetispeed`/`cfsetospeed` 的**返回值**为准，杜绝静默失败。

> 旁证：板端 `stty -F /dev/ttyS3 115200` 一直有效（stty 用板端 libc 的
> `B*` = 4098），与本修法首选值一致。

### 13.4 顺带修掉的两个「构建/工程」问题

1. **`XHeaderView_setSectionSize` 缺声明 ⇒ Windows 端编译失败**
   远端提交在 `XHeaderView.c:647` 调用了它，但 `XHeaderView.h` 里没有声明
   （同族 `XHeaderView_sectionSize`/`_resizeSection` 都有）⇒ C99 隐式声明与
   定义冲突，MSVC 报 `C2371: 重定义；不同的基类型`。
   已在 `Src/XGui/Widget/XHeaderView.h` 补声明（含 Qt 语义说明）。
   **这条会挡住桌面端联调**，换机后先编 Windows 目标。
2. **交叉链 `isoc23_shim.o` 自递归 ⇒ 应用启动后 100% CPU 空转**
   远端新增 `Test/XDeviceTest/XESP8266DeviceTest.c` 用了 `scanf`，交叉链接报
   `undefined reference to __isoc23_scanf`（原垫片只覆盖 sscanf 家族）。
   补齐后发现更隐蔽的问题：glibc 用 `__REDIRECT` **属性**重定向声明（不是宏，
   `#undef` 无效），若垫片自己命中宿主头 ⇒ `__isoc23_strtol` 转发给自己 ⇒
   **无限递归且不耗栈**（表现为应用启动后空转、不崩溃、无任何输出——本次真机
   排查踩过，现象是「进程 134s CPU、无 X 连接、无 tty fd」）。
   已把垫片改成用 `__asm__` 别名强制绑定真符号
   （`extern ... __asm__("strtol");`），与编译期命中哪套头文件无关。
   垫片源码 `/root/isoc23_shim.c`（WSL 侧，非仓库文件）。

## 14. 串口接入框架事件循环（去掉 2ms 定时器轮询）

> 2026-10-30 续：按「接入框架、统一走框架 ring」的要求，把串口接收从
> **毫秒级定时器轮询**改为**事件驱动**，两个引擎（epoll / io_uring）都支持。

### 14.1 改造前的形态

`XSerialPort` 用一个 2ms 的 CoarseTimer 拍轮询接收缓冲：

```c
/* Src/XIO/XSerialPort/XSerialPort.c（改造前） */
port->m_rxTimer = XObject_startTimer_ms((XObject*)port,
    (uint64_t)port->rxPollIntervalMs, XTimerType_CoarseTimer);
```

定时器拍只在**事件循环的下一圈**才被兑现 ⇒ 板端主循环一圈 100+ms 时，
串口数据的感知延迟同量级（这正是 §5 记录的 `[WHEEL] lag` p50=108ms）。

### 14.2 改造后：进框架异步后端等待集（与网络套接字同一套机制）

框架既有的等待集接入点有两个，本次串口走的是**被动可读 fd**通道
（与 fbdev 触摸唤醒通道同一机制，socket notifier 走 `registerEvent`）：

- `XAbstractNetIoRing_registerPassiveOsFd_base(ring, osFd, notify)`
  —— POSIX 侧：epoll 引擎 `epoll_ctl(ADD)`；io_uring 引擎 `POLL_ADD`；
  Windows 侧恒 false（IOCP 无「只读设备句柄挂进等待集」的原语）。
- 数据到达 ⇒ 内核唤醒阻塞中的事件循环 ⇒ 回调属主发射 `readyRead`，
  **不再等下一圈边界**。

X11 平台的等待桥已把 ring 事件 fd 作为 **poll 源 1** 纳入
（`XPlatformNativeWindow_waitForEvents`：源 0 = X11 连接 fd，源 1 = ring 事件 fd），
所以「串口 fd 进 ring 等待集 ⇒ ring 事件 fd 可读 ⇒ poll 立即返回 ⇒
`XAbstractNetIoRing_processReady` 收割 ⇒ 通知串口」这条链是通的，
**串口与网络套接字共用同一个等待集与同一套唤醒路径**（无额外线程）。

### 14.3 io_uring 引擎补齐 5.10~5.12（一次性 POLL_ADD + 完成后重挂）

原实现只支持 multishot（内核 ≥5.13）：5.10 上 `IORING_POLL_ADD_MULTI`
被内核拒（res=-EINVAL）⇒ 该 fd 在 io_uring 引擎上**注册成功但永不触发**
（静默失聪）⇒ 调用方只能回落轮询兜底 ⇒ 串口无法接入。

修法（`Drive/Posix/Core/XNetIoRingPosix.c`）：

- 首次按 multishot 挂载；内核拒绝 ⇒ 置 `m_multiUnsupported`，
  **改用一次性 POLL_ADD**，每次完成后在**通知属主之后**重挂
  （属主先读空 ⇒ 重挂不会立即就绪 ⇒ 无 CQ 风暴）；
- multishot 形态下若完成未带 `IORING_CQE_F_MORE`，同样判定为一次性并转入重挂。

⇒ 5.10（RK3568）与 5.13+ 行为一致，与 epoll 引擎语义统一
（都是「就绪 ⇒ 通知 ⇒ 重挂/维持」）。

### 14.4 改动清单

| 文件 | 改动 |
|---|---|
| `Drive/Posix/Core/XNetIoRingPosix.c` | io_uring 被动 fd：一次性 POLL_ADD + 完成后重挂（支持 5.10~5.12）；新增 `m_multiUnsupported` 字段；完成分派带 CQE flags |
| `Src/XDevice/XDeviceSerialPort.h/.c` | 新增「串口可读事件源」平台钩子 `platformArmReadable/platformDisarmReadable`（裸机 RTOS 回落默认实现） |

⇒ 该尖刺属演示程序的 GUI 负载问题，与本次「串口接入框架」改造无关，

### 14.7 关于「统一走框架 ring」与线程

- 本次改造**未新增任何线程**：串口 fd 进框架 ring 等待集，与网络套接字
  共用同一等待集与同一唤醒路径（X11 泵的 poll 源 1 即 ring 事件 fd）。
- 板端现状主循环用 `poll(X11fd, ringfd)`（**一次 poll 两个源**），不是
  「多处 poll」；框架 ring 引擎自己的 `epoll_wait` 只在 dispatcher 的
  ring 阻塞分支（非 GUI 自绘主循环）使用。
- POSIX 平台层另有一个 **X11 fd 监视线程**（`xpwn_x11WakeWatch`），
  是既有实现（2026-10-26 触摸唤醒通道引入），用于在 X11 事件泵阻塞时
  唤醒 ring 的阻塞等待；本次未改动它，也不建议在本次一并动
  （涉及 GUI 输入时序，风险面大）。若要收敛，应单独立项：
  把「X11 fd 等待」也并入 ring 等待集，删掉该线程。

## 15. Windows 侧串口接入框架 IOCP + 计时源粒度根治（2026-10-30）

§14 完成了 POSIX 侧（串口 fd 进框架 ring 等待集）。本节把 Windows 侧补齐
到同一套架构，并修掉一个此前一直没被发现的**跨平台计时源粒度不一致**
根因——它是本轮「卡一下」误判的源头。

### 15.1 一个必须先纠正的测量假象

§14.5/§14.6 的结论建立在 MBTRACE 打点之上，而当时打点函数在 Windows 上是：

```c
/* 修复前：xgui_demo_page_modbus.c */
return (double)GetTickCount64() / 1e3;
```

`GetTickCount64()` 的粒度是**系统时钟中断周期 15.625ms（64Hz）**。用它做
「发送→应答」差值，样本值只能是 **0 或 15.625 的整数倍**。于是真机日志里
出现「dt 100% 落在 15.625ms 整数倍上（16/31/125/141/156/172/188/203/234ms）」，
一度被判定为「链路被系统节拍量化」。

**这是打点工具自身的量化，不是链路时延。** 换成 pyserial 直连同一链路
（`verify/mb_rtt_latency.py` / `verify/mb_rtt_poll.py`）实测：

| 方式 | p50 | p90 | 15.625ms 整数倍占比 |
|---|---|---|---|
| pyserial 阻塞读 | 2.84ms | 3.42ms | 2.5% |
| pyserial 1ms 轮询 `in_waiting` | 3.98ms | 4.22ms | 2.5% |
| XinYueC 主站（打点修复前） | 16.0ms | 109ms | **100%** |
| XinYueC 主站（打点修复后） | **5~8ms** | 90~134ms | 2.1% |

⇒ 打点改为框架统一单调时钟 `XDateTime_currentMSecsSinceEpoch()`
（Windows 已改 QPC，POSIX 是 `CLOCK_MONOTONIC`）后，量化假象消失，
主站真实在途时延是 **5~8ms**，与 pyserial 的 2.9ms 同量级。

> 教训：跨平台统一到**同一个时间源**，否则诊断数据本身会带平台偏置。

### 15.2 真正的跨平台根因：Windows 毫秒计时源粒度

`XDateTime_currentMSecsSinceEpoch()` 是全库统一的「当前毫秒」计时源
（时间轮 tick / IO 超时 / 轮询拍 / 限流测量全用它）。两平台实现却是：

| 平台 | 实现 | 粒度 |
|---|---|---|
| POSIX | `clock_gettime(CLOCK_MONOTONIC)` | 1ms |
| Windows | `GetTickCount64()` | **15.625ms** |

⇒ Windows 上框架的**所有**毫秒级行为都被量化到 15.625ms：
时间轮 tick 粒度、串口 2ms 轮询拍、50ms 轮询周期、应答超时判定、UI 限频。

**修复**（`Drive/windows/Core/XDateTime_win32.c`）：改用
`QueryPerformanceCounter`（恒定频率、纳秒分辨率、不受校时影响），
与 POSIX 的 `CLOCK_MONOTONIC` 语义与粒度对齐；取不到频率时回落
`GetTickCount64`。这一步是「两个引擎行为统一」的**前提**：POSIX 侧
1ms 精度的轮询节奏，在 Windows 侧此前根本达不到。

### 15.3 Windows 串口接入框架 IOCP（与 POSIX 等待集同构）

`Drive/windows/Device/Serial/XSerialPortWin32.c`：

- 串口句柄以 `FILE_FLAG_OVERLAPPED` 打开，**关联到框架的 IOCP 完成端口**
  （`XNetIoRingWin32_assocHandle`），与文件设备共享内存通道同一套做法；
- **常驻一个 OVERLAPPED ReadFile**：数据到达 ⇒ 内核把完成包投进框架完成
  端口 ⇒ 主循环（`MsgWaitForMultipleObjects` 把 IOCP 句柄列入等待集）
  被唤醒 ⇒ 完成回调 `xspw32_readCompletion` 把数据搬进接收环并通知属主
  发射 readyRead；
- 读到的字节落在设备层 `XDeviceSerialPortContext::m_readBuffer`（XRingBuffer），
  `platformRead` 优先消费该环——**与 POSIX 侧同一套数据落地契约**；
- 写也必须带 OVERLAPPED（句柄以 OVERLAPPED 打开的必然结果）：写完成包由
  `xspw32_writeCompletion` 消费，关闭前经 `CancelIoEx` + 有界等待回收，
  保证不出现指向已释放上下文的悬垂完成包；
- 无 IOCP 后端（网络模块裁剪 / 全局环不可用）⇒ 句柄退回同步打开，
  走原 `ReadFile` 路径，调用方保留毫秒级轮询兜底，**行为与改造前逐位一致**。

踩过的坑（记下来别再犯）：**不能用 `FILE_SKIP_COMPLETION_PORT_ON_SUCCESS`**。
该标志会让「成功完成」的 overlapped 读**不投完成包**，而串口驱动的读完成
恰好以 `STATUS_SUCCESS` 回报 ⇒ 完成包被吞 ⇒ 常驻读永远收不到通知，
真机实测应答延迟劣化到 **4s 级**（第一版就是这样翻车的）。

现场诊断开关：`XSERIAL_WIN32_SYNC=1` 强制走同步读 + 毫秒轮询路径，
用于对照（两种路径实测在途时延无显著差异）。

### 15.4 配套：系统定时器分辨率

Windows 的等待超时按系统定时器节拍对齐（默认 15.625ms）。串口打开期间
用 `ntdll!NtSetTimerResolution`（动态取址，免链接 winmm.lib）把分辨率提到
**1ms**，关闭时还原（引用计数，多串口安全）。真机确认实际值 1.000ms。

## 16. 板端「双缓冲+脏区上屏后仍有卡顿」的复测与新发现（2026-10-30 续）

本节是针对该反馈的复测结论。

### 16.1 复测基线（pyserial 直连，绕开框架，只测链路）

`verify/mb_rtt_poll.py --mode block --n 300 --gap-ms 50`（同一块板、同一条 485）：

| 指标 | 值 |
|---|---|
| p50 | **2.87ms** |
| p90 | 3.22ms |
| p99 | **213ms** |
| max | 236ms |
| 尖刺占比 | ~2.7%（130~240ms） |

⇒ 链路基线极好（3ms），**卡顿是 2% 的 ~150ms 尖刺**，不是整体慢。

### 16.2 新发现一：全局时间轮的 count 门是真缺陷（已修）

`Src/XDevice/XDeviceTimer.c` 的 `XDeviceTimer_process` 原本是：

```c
if (wheel && XTimeWheelGroup_count(wheel))      /* ← count 门 */
    XTimeWheelGroup_handler_base(...);
```

**问题**：全局时间轮的刻度 `m_current_tick` 是**绝对时间轴**（刻度源=单调毫秒）。
带 count 门意味着「轮里没有定时器就不消费时间轮」⇒ 刻度**冻结**在旧值。
而定时器到期刻度按 `expire_ticks = m_current_tick + timeout_ticks` 计算
⇒ **刻度落后多少，定时器就晚多少兑现**。

真机证据（板端，`XGUI_WHEEL_TRACE=1` 每 500ms 打印 behind）：

```
修复前 behind:  195 左右稳态（[WHEEL] lag=154~254，而 cur 与 tick 仍 1:1 跟随
                ⇒ 是「冻结」不是「失速」）
修复后 behind:  587(冷启动) → 0 → 18/20/21/21/18/20/…（≈一个事件循环周期）
```

⇒ **修复：去掉 count 门**，每圈按真实刻度推进（成本仅槽链表原子交换 + 空槽扫描）。

这条缺陷是**跨平台**的：Windows 主站因为轮里常驻定时器（count>0）没暴露，
板端「Modbus 从站页没有 CoarseTimer」⇒ 长期 count==0 ⇒ 暴露。

### 16.3 新发现二：板端仍有「每秒一次 ~150ms 的事件循环空窗」

修复后 behind 常态 ≈20ms（一个 20ms poll 周期），但**每秒仍出现一次
behind 冲高到 102~239**（`[WHEEL] lag=` 每秒一条）。这说明：

- 主循环每秒有一次 ~150ms 的**不消费时间轮**的窗口；
- 但板端 CPU 只有 **8%**（`/proc/PID/stat` 精确采样 10 秒：890ms CPU/10s），
  系统 92% idle ⇒ **不是算力不足**；
- `strace -T -f`（含 futex/read/write/ioctl/ppoll/nanosleep）**10 秒内没有任何
  >50ms 的系统调用** ⇒ **不是阻塞在系统调用上**；
- 板端主循环等待点是**一处**：X11 桥的「一次 poll 两个源」
  （`ppoll([{fd=3,X11},{fd=4,ring事件fd}], 2, 20ms)`），每圈必超时返回；
  框架 ring 引擎在 GUI 场景不额外阻塞（epoll 引擎的 `epoll_wait` 只在非 GUI
  阻塞分支用）。板上另有一个线程 `xpwn_x11WakeWatch`（X11 fd 监视，唤醒 ring
  阻塞等待用，2026-10-26 引入）—— 这是「另外开的」一处，可并入 ring 等待集后删除。

### 16.4 新发现三：上屏量并未因双缓冲而下降（用户治理的靶心）

板端 10 秒 X11 写出 **39,996,730 字节（4MB/s）**，单次最大 **261,144 字节**
= `1280 × 51 × 4` 字节（24bpp ARGB）⇒ **整宽条带**。

- 宽度 1280 = **整个窗口宽度**：脏区在**宽度维度没有被收窄**；
- 4MB/s ≈ 每次整窗（1280×800×4 = 4.1MB）**每秒重绘一次**；
- 推论（待用户治理侧确认）：每秒一次的整窗重绘 ⇒ X11 写阻塞
  （socket 缓冲满，等 Xorg 软件光栅化消费）⇒ **与 16.3 的 ~150ms 空窗同源**，
  也是 485 应答 2% 尖刺的最后一环。

⇒ **治理要点**：双缓冲只解决「撕裂/闪烁」，**不减少上屏带宽**。
要让 485 链路稳，需要把上屏的**宽度**和**频率**一起降：
① 脏区不必整宽（顶栏时钟、HUD 悬浮层等按实际控件范围取脏区）；
② 1Hz 的整窗重绘改成小脏区或降频（内容没变就不重绘）；
③ 目标：上屏量从 4MB/s 降到百 KB/s 量级。

### 16.7 仍未定位的一点

16.3 的「每秒一次 ~150ms 空窗」已排除：算力不足、慢系统调用、时间轮冻结。

验证方法（需在板端做）：整窗重绘时刻对 X11 连接 fd 抓 `write` 的阻塞时长，
或临时把重绘频率降到 0.1Hz 看 485 尖刺是否随之消失。

### 16.8 决定性实验：整窗级上屏与页面无关（治理靶点）

用**同一个板端二进制**跑从站服务，只换显示页（`--page 18` 从站页 ↔ `--page 1`
静态选择演示页），量 8 秒 X11 写出量：

| 显示页 | 8 秒写出量 | 折算 |
|---|---|---|
| page 18（Modbus 从站页） | 39,996,730 B | **4.0 MB/s** |
| page 1（静态选择演示页） | 31,997,311 B | **4.0 MB/s** |

⇒ **完全不同的页面，上屏量一模一样** ⇒ 这不是某个页面的控件在重绘，
而是**全局每帧/每周期把整窗推上屏**（单次 261,144 B = 1280×51×4 的**整宽条带**，
16 条带 ≈ 整窗 1280×800×4 = 4.1MB ⇒ 每秒一次整窗）。

⇒ **推论（治理方向）**：现有实现的「脏区」在**宽度维度**恒为 1280 ⇒ 任何局部
更新都退化成整宽条带；再叠加静态场景缓存若以**整窗**为粒度，任何标脏都会让
整窗缓存失效 ⇒ 每秒推一整窗。

⇒ **要让 485 链路稳下来，需要三件事（按性价比排序）**：
1. **上屏带宽降到百 KB/s 量级**：脏区按控件实际矩形取（不跨整宽），
   静态场景缓存改为分块/按区域失效，而不是「一脏全窗重画」；
2. **每秒一次的整窗重绘降频或消除**（顶栏时钟等按需局部更新）；
3. 剩下的 ~150ms 空窗（§16.3）在 1、2 落地后复测——它高度疑似 **X11 写阻塞**
   （整窗重绘时 socket 缓冲满，等 Xorg 软件光栅化消费 4MB）。

⇒ 验证 3 的最快办法：把上屏量临时压到 ~0（停掉所有周期刷新），
看 pyserial 直连的尖刺率（当前 2.7%、130~240ms）是否归零。

### 18.1 取证：稳态尖刺的真凶不是从站页，是「多矩形脏区被压成外接矩形」

板端（RK3568，X11，DIRECT 模式）跑 Modbus 从站页，框架自带画像给出决定
性数据：

```
[wprof] tot=6 (92.424ms) … soft=56ms flush=55.9ms paint=35.2ms … gap=833ms
[rprof] frm=6 sumAvg=499690 sumMax=990720 bboxAvg=499690 bboxMax=990720
        | enq=15 avg=10060 max=10752@XLabel(192x56)
```

读法（三个量必须一起看）：

| 指标 | 含义 | 实测 |
|---|---|---|
| `enq max=10752@XLabel(192x56)` | **单笔**入队最大的只有 192×56 | 脏区很小 |
| `sumMax=990720` | 本帧**实际绘制+提交**面积 | 1280×774 = **整窗** |
| `flush≈56~80ms` / `paint≈35ms` | 上屏腿 / 绘制腿单帧耗时 | 合计 ≈100ms/帧 |

⇒ 脏区本身只有几 KB，**帧面积却是整窗**：因为框架把多矩形脏区收拢成了
**外接矩形**。零散的小脏区（顶栏时钟右上 + 右下悬浮层 + 页内读数）跨越
全窗 ⇒ 外接框 = 整窗 ⇒ 每帧整窗重绘（35ms）+ 整窗上屏（56~80ms），
2 帧/秒 ⇒ 事件循环每 0.5~1s 空洞 150~240ms ⇒ 485 应答 2% 的 149~250ms
尖刺。旁证：上屏量直方图 12 秒 45.8MB（3.8MB/s），单次写 220~260KB
（X11 按最大请求长度拆的整窗条带）。

**§17.4 的「从站页 `MbSlaveRoot` 整块标脏」只是启动帧**（`max=2299988`
出现在第一帧），稳态帧的 `max` 只有 10752 —— 修它对尖刺**零收益**。

### 18.2 框架层修法：保留多矩形 ⇒ 逐矩形绘制 + 逐矩形提交

改动全部在 `Src/XGui/Widget/XWidget.c`（框架层，**不动 demo**）：

| # | 位置 | 改动 | 作用 |
|---|---|---|---|
| 1 | `XWidget_flushBackingStore` 帧区域收拢处 | **删除**「多矩形 → 外接矩形」的收拢 | 帧区域保持多矩形 |
| 2 | 同上，脏区回退分支 | 脏区回退也保留多矩形（原为 `boundingRect`） | popup/menu 的 `flush(NULL)` 同口径 |
| 3 | `XWidget_paintTree` 的 `count>1` 拆分分支 | 逐块表面裁剪改用**设备坐标**（局部 + `XWidget_paintOffset`）；拆分后**原样恢复调用方的裁剪** | 逐块派发时像素严格落在块内；旧口径在深层拆分时用局部坐标包围盒恢复，与表面裁剪的设备坐标口径不同源（潜在缺陷，一并修） |

平台侧无需改动：`XPlatformNativeWindow_present` 本就**逐矩形**出
`XPutImage`；`XPlatformBackingStore_flush` 本就逐矩形拷贝到另一块缓冲。

**不变量「绘制像素集 == 提交像素集」**是这次修复的关键：
- 逐块派发时表面裁剪收窄到该块 ⇒ 块间隙像素**既不被重画也不被上屏**；
- 提交区与绘制区同为那批矩形 ⇒ 双缓冲两块内容不��叉 ⇒ 无残影/无陈旧像素。

**口径变化（须知）**：顶层控件的 `paintEvent` 变为**每矩形一次**（原为每
flush 一次）⇒「绘制活动率」口径（每 paintEvent 计一帧）按矩形数放大，
HUD 的 FPS 读数不再等于 flush 率——这是绘制活动的真实计数，不是回归。

## 19. 后备存储缓冲形态定案：桌面单缓冲（2026-10-30 第五轮）

§18 把脏区口径修好后，剩一个独立问题：桌面（Windows/X11）的后备存储该
用双缓冲还是单缓冲。结论是**单缓冲**，且结论不是拍脑袋——先把三种缓冲
形态在两平台的实际实现逐条核对，再上板实测。

### 19.1 三种缓冲形态的跨平台实情（代码核对）

框架里其实是三种形态，各自的触发条件与平台覆盖**并不对称**：

| 形态 | 机制 | Windows | Linux/POSIX |
|---|---|---|---|
| ① 软件双缓冲 | 两块全窗 XImage 交替；flush 把提交区拷进另一块 + 翻帧 | **仅兜底**（native DIB 创建失败时） | X11 常态（本次改前）；fbdev 影子缓冲 |
| ② native 直写缓冲 | 绘制目标=平台共享表面（Windows=`CreateDIBSection` 内存 DIB；present 逐矩形 `BitBlt` 到窗口 DC） | **常态**（`getNativeBuffer` 给 DIB ⇒ `m_nativeBufferMode` ⇒ 第二块被释放 ⇒ 天然单缓冲） | **已被有意关闭**：fbdev 的 `getNativeBuffer` 恒返回 NULL（影子缓冲架构：painter 直写可见 fb 会把中间态扫上屏，昆仑通态 A7 白屏一闪即此）；X11 无「客户端可写的窗口表面」概念 |
| ③ 软件单缓冲降级 | 驱动自带硬件轮换（`m_softwareSingleBuffer`）∨ 换轴 90/270 旋转态（`xpbs_rotationSingleBuffer`） | 旋转钳制**被平台门裁掉**（`#else` 分支恒 false）；驱动轮换判据只对 fbdev 驱动注册生效 ⇒ 实际不触发 | fbdev 驱动硬件轮换 ✓；90/270 旋转态 ✓ |

⇒ 结论：**Windows 桌面早就是单缓冲（形态②），X11 桌面却是双缓冲（形态①）
——同一台机器的两个桌面栈，缓冲语义相反**。这不是 bug，是历史演进：
形态② 只在 Windows 有可共享表面时成立。

### 19.2 为什么 X11 也不需要双缓冲

关键事实：**桌面的绘制目标从来不是可见表面**。
- X11：painter 画进软件 XImage → present 逐矩形 `XPutImage` 到服务器；
- Windows：painter 画进内存 DIB → present 逐矩形 `BitBlt` 到窗口 DC。

⇒ 绘制期的中间态不会被屏幕看到 ⇒ **双缓冲在本框架里不提供任何撕裂防护**
（present 与绘制读的是同一块缓冲，见 flush 的 active 读取路径）。
而双缓冲的唯一作用是「把提交区同步进第二块 + 翻帧」，全库检索确认
**第二块缓冲没有任何"从它恢复"的用途**（仅 flush 的 inactive 拷贝与翻帧
两处引用）⇒ 对桌面纯属开销：一块全窗缓冲 + 每帧提交区拷贝。

§18 的逐矩形上屏之后，每帧提交区只有几十 KB ⇒ 拷贝成本几乎归零，但那块
全窗缓冲仍在（板端 1280×800 ARGB32 = 4.1MB）。

### 19.3 实测（RK3568 板端，同一份代码只改缓冲数）

| 指标 | 双缓冲（改前） | 单缓冲（改后） |
|---|---|---|
| 进程 RSS | 50,908 kB | **44,748 kB（-12%）** |
| 单帧耗时 | 8.7ms | 7.7~12.0ms（持平） |
| 上屏量 | 1.58MB/12s | 1.58MB/12s（持平） |
| 485 RTT（n=400） | p99 7.4ms | p50 2.91 / p90 3.19 / **p99 3.52ms** / max 10.2ms（0 尖刺） |
| 画面 | — | 逐像素一致（板端截图核对无残影/无空白） |

⇒ 单缓冲在桌面上是**纯赚**：省一块全窗缓冲 + 每帧拷贝，代价为零。

### 19.4 落地

- `Src/XGui/XGuiConfig.h`：删除「桌面（DIRECT 且非 fbdev）强制双缓冲」规则，
  缓冲数默认 1；需要双缓冲时构建期 `-DXGUI_BACKINGSTORE_BUFFER_COUNT=2`。
  外部缓冲绑定 API（`setBuffers`）**本就按缓冲数分叉**（双缓冲要求
  buffer2、单缓冲要求 buffer2 为 NULL），回归套件同样按缓冲数分叉 ⇒
  契约不破。
- `Src/XGui/Platform/XPlatformBackingStore.c`：flush 的 inactive 同步块加
  `#if XGUI_BACKINGSTORE_BUFFER_COUNT > 1` 编译期门（单缓冲时第二块恒空，
  原是每帧每矩形一次空操作）。
- fbdev 直写面**不变**：仍走影子缓冲架构，其单缓冲钳制判式（驱动硬件
  轮换 ∨ 90/270 旋转态）保留在平台层，与缓冲数量无关。

**坑（已踩）**：改公共头 `XGuiConfig.h` 后 **Ninja 不会触发全量重编**
（主库 obj deps 缺失，Windows 构建树已知缺陷）⇒ 库按新口径（单缓冲）
而 `xgui_regression_test.c` 仍按旧口径（双缓冲）编译 ⇒ 4 条外部缓冲
断言假失败。**验证公共头改动必须先全量重编**（删 `CMakeFiles/XinYueCS.dir`
等 obj 目录再构建），全量重编后回归套件回到**同一处既有失败**（XKeyboard
长按连删 4 条断言），无新增失败。

## 20. 三种缓冲形态的跨平台功能与行为统一（2026-10-30 第六轮）

§19 把桌面定案为单缓冲，但遗留一个问题：**三种形态在 Windows / Linux 上
并不是同一套实现**——形态是「平台各自涌现」的结果，不是框架的一等概念。
本轮把它收敛成**显式模型 + 跨平台同源判定 + 跨平台契约门禁**。

### 20.1 统一模型：两个正交维度

形态不再是三个并列的名字，而是「绘制表面归属 × 是否交替帧」的组合：

| 形态 | 表面归属 | 交替 | 典型平台 |
|---|---|---|---|
| ② `platform-surface` | **平台提供**（Windows `CreateDIBSection` 内存 DIB） | 否 | Windows 桌面 |
| ① `software-double` | 框架自分配两块全窗帧 | 是（提交区同步进另一块后翻帧） | 缓冲数=2 的构建 |
| ③ `software-single` | 框架自分配一块全窗帧 | 否 | X11 桌面 / fbdev 影子缓冲 |

**三形态的可观测契约完全一致（平台无关）**：
1. 绘制目标始终持有完整窗口内容（脏区外的像素是上一帧最新值）；
2. present 提交的像素集**恰等于**本次脏区（不多不少）；
3. 可见表面看不到绘制期中间态（绘制目标不是可见表面）。

### 20.2 落地改动

- `Src/XGui/Platform/XPlatformBackingStore.h/.c`：
  - 新增 `XPlatformBackingStoreBufferMode` 枚举与
    `XPlatformBackingStore_bufferMode()` / `_bufferModeName()`（**可查询**，
    形态成为一等概念，不再靠平台涌现）；
  - 判定集中到一处、**两平台同源**：平台提供绘制表面 ⇒ ②；否则驱动硬件
    轮换 ∨ 换轴 90/270 旋转态 ⇒ ③；其余 ⇒ ①（缓冲数=1 时恒 ③）；
  - flush 的「提交区同步进另一块」与三处「翻帧」判据统一改为
    「当前形态 == ①」（原先是散落的 `!native && !softwareSingle` 标志位组合，
    两平台各写各的）；
  - 形态定案时打一行诊断 `[xpbs] buffer-mode=... size=... surface=...`
    （走 XPrintf 通道：Windows 演示是 GUI 子系统程序，stderr 无效）。
- `xgui_regression_test.c`：新增 `test_backingstore_buffer_mode_contract`
  ——**同一组断言**在两平台都必须成立（不按平台分叉）：
  形态名稳定；形态与可观测行为一致（① 交替 / ②③ 不交替，判据=提交后
  绘制目标地址是否互换）；present 收到的提交区恰等于脏区；脏区外像素保持；
  外部缓冲绑定后形态必为软件侧。

### 20.3 两平台实测（同一份代码，形态由判定得出）

```
Windows 桌面： [xpbs] buffer-mode=platform-surface size=1000x700 surface=platform
RK3568/X11 ： [xpbs] buffer-mode=software-single  size=1280x800 surface=framework
```

⇒ 形态差异来自**平台能力**（Windows 有可共享表面；X11 没有；fbdev 有意
不提供——直写可见 fb 会把中间态扫上屏），而不是平台各自硬编码的行为。
契约在两平台一致：板端 RSS 44.7MB（单缓冲省一块全窗缓冲）、帧耗时
7.7~12.0ms、上屏 1.58MB/12s、485 RTT p50=3.77ms / p99=4.73ms /
max=6.06ms（0 尖刺）、画面逐像素一致。

### 20.4 勘误（前一版的误判）

§19 表格里「旋转态单缓冲钳制被平台门裁掉（Windows 恒 false）」是**误读**：
该 `#else` 分支是 `XGUI_BACKINGSTORE_BUFFER_COUNT == 1` 的编译期分支，
**不是平台门**——旋转钳制在两平台一致生效（本轮逐行核对确认）。
真正的平台差异只有一处：Windows 常态走 ②（native DIB），X11 无共享
表面故走 ③。

### 20.5 本轮遗留

形态已统一为显式模型，但 **② 在 X11 上仍不可达**（X11 协议没有
「客户端可写的窗口表面」），这是平台能力限制而非实现缺口；若将来要
在 X11 上提供 ②，需要的是「共享 Pixmap 作为绘制目标 + CopyArea 提交」
的驱动改造，属独立立项。

## 21. 缓冲形态统一后的冗余 API 清理（2026-10-30 第七轮）

形态统一（§20）后做了一次**全仓 API 引用审计**，把只服务于旧口径、
现已无调用者的接口清掉。

### 21.1 审计方法（可复用）

对后备存储两层的公开头（`XBackingStore.h` / `XPlatformBackingStore.h`）
逐个 API 统计「**定义以外**」的引用数，统计范围必须覆盖**仓库根目录**
（`xgui_regression_test.c` 等顶层测试文件不在 `Test/` 下）——首轮审计漏了
根目录，误判「静态内容特性整链无人消费」并删除了 6 个 API，编译即报
`C2440`（`XBackingStore_size` / `XBackingStore_staticContents` 在用），
已全部还原重做。

### 21.2 清理结果：删 8 个（全仓零引用）

框架层 `XBackingStore`：
- `XBackingStore_reinit`（无调用者；`init` 已覆盖重建语义）
- `XBackingStore_paintDevice`（`XPaintDevice*` 版；在用的是
  `XBackingStore_paintImage`）
- `XBackingStore_flushTile`（PARTIAL 逐片提交走平台层的
  `XPlatformBackingStore_flushTileBatched`）

平台层 `XPlatformBackingStore`：
- `XPlatformBackingStore_hasPendingTiles`（攒批状态无人查询）
- `XPlatformBackingStore_hasStaticContents`（框架层同名接口在用，平台层
  这个变体零引用）
- `XPlatformBackingStore_surfaceFormat`（表面格式协商在驱动内部完成）
- `XPlatformBackingStore_setNativeTargetWindow`（目标窗口改由驱动侧设置）
- `XPlatformBackingStore_requestPanelClear`——**跨平台口径不一致的半 API**：
  头文件在公共层声明，实现却只在 `Drive/Posix/.../XPlatformBackingStore_posix.c`
  （Windows 下无实现）且零调用者 ⇒ 头文件声明与 POSIX 定义一并删除。

### 21.3 保留（经审计**不是**冗余）

- `XBackingStore_window` / `_size` / `_scroll` / `_setBuffers` /
  `_requiredBufferSize` / 静态内容三件套：虽只有回归用例在用，但它们是
  **Qt 对标 API**（`QBackingStore::window/size/scroll/setStaticContents`），
  属对外能力面，保留。
- `XPlatformBackingStore_window` / `staticContents` / `setStaticContents` /
  `flushTile` / `flushPendingTiles` 等：有真实调用者。
- `XBackingStore_class_init`：与全仓各类 `*_class_init` 同族的虚表工厂。

### 21.4 验证

- 桌面：全量重编（头文件改动 ⇒ 必须全量）后 **20+ 目标全部链接通过**；
  `XGuiRegression_Test` 仍只剩那一处既有失败（XKeyboard 长按连删）。
- 板端：交叉编译通过、部署后形态上报 `software-single`、RSS 44.9MB、
  485 RTT p50=3.94ms / p99=6.03ms / max=10.85ms（**0 尖刺**）。
- **既有缺口已收口**（见 §22）：`XDeviceIoUPassiveProbe`/`XModbusAndroidProbe`
  无条件进 Windows 构建 ⇒ 本轮加平台门/换跨平台计时源，Windows 全量构建
  首次全绿。
- **勘误**：本节初稿把「共享库目标 `XinYueC`（DLL）的 `__create_def` 导出
  步骤不可用」记成既有缺口——**是本轮自己造成的**：为强制全量重编而删除
  `CMakeFiles/XinYueC.dir` 时，连带删掉了 CMake 生成的导出对象清单
  `exports.def.objs`（它就放在目标 obj 目录里）；重新配置补回清单后 DLL
  立即正常链接（`bin/XinYueCd.dll` 18.3MB + `out/build/x64-Debug/XinYueCd.lib`
  4.0MB）。教训：**删目标 obj 目录做强制重编时，要留意 CMake 生成在其中的
  中间产物**（导出清单/响应文件），否则下一次链接会以「找不到清单」失败，
  看起来像环境不支持。

## 22. 收口两个长期存在的 Windows 构建缺口（2026-10-30 第八轮）

§17.5 记下的两个 Windows 构建缺口（两个 POSIX 专属探针无条件进 Windows
构建 ⇒ **Windows 全量编译必挂**），本轮收口。

### 22.1 两个探针的处置（按「是否本质属 POSIX」分开处理）

| 探针 | POSIX 依赖 | 处置 | 理由 |
|---|---|---|---|
| `XDeviceIoUPassiveProbe`（io_uring/epoll 被动 fd 通道） | `pipe/read/write/setenv`（unistd.h）+ io_uring/epoll 引擎 | **加平台门**：目标只在 `if(UNIX)` 下创建（Windows 侧打一行 STATUS 跳过） | 本质属 POSIX：Windows 无对应异步后端，Windows 上跑它没有意义 |
| `XModbusAndroidProbe`（Modbus TCP 主站轮询） | 仅 `clock_gettime(CLOCK_MONOTONIC)` | **换跨平台计时源**：改用框架统一单调时钟 `XDateTime_currentMSecsSinceEpoch()` | 只差一个计时源；改后 Windows 也能编译运行（Windows 侧走 IOCP 后端，本就是「另一条异步路径」的对照组） |

顺带：`XModbusAndroidProbe` 去掉 `<time.h>`（不再需要），引入 `XDateTime.h`。

### 22.2 结果

- **Windows 全量构建首次全绿**：`ninja -k 0` 跑完 27 个目标，**零 FAILED**；
  `XModbusAndroidProbe.exe` 正常产出（4.0MB），`XDeviceIoUPassiveProbe`
  按平台门跳过（Windows 上本就没有对应后端）。
- 共享库目标 `XinYueC`（DLL）正常链接：`bin/XinYueCd.dll` 18.3MB +
  `out/build/x64-Debug/XinYueCd.lib` 4.0MB。
- 回归套件仍只剩那一处既有失败（XKeyboard 长按连删）。
- POSIX 侧不受影响：io_uring 探针在 UNIX 下照常创建，板端交叉编译通过。
