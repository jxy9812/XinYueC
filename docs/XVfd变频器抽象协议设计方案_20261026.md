        │   · 挂接总线链路接口 XVfdLink（attach(link, slaveAddr)，10-27 三修）
        │   · 编帧/解帧/语义映射（子类实现）· 信号 · XVfdError 错误码体系
        │
        ├─ XVfdModbusBase  基于 XModbusClient 的 FC 助手中间基类
        │      （帧封装/队列/超时/广播回合由总线主站承担；本层只做：
        │       FC03·06·16 请求构建 + 应答解析 + 异常帧(0x83·0x86)→XVfdError 映射
        │       + 寄存器点表驱动的字段读写）
        │      ├─ XVfdAtv61   逻辑地址点表 + CiA402 状态机 + 109 条故障表
        │      │              （资产平移自 XModbusAtv61）

        │                     Err01~51 故障表 + 非标准模式开关
        │
        └─ XVfdM3          自定义帧协议，独占总线直挂 XIODevice 自编帧

链路层：XVfdLink 窄接口（每条物理链路一个实例 = 仲裁 + 轮询计划表 + 从站健康；10-27 三修）
        │   · 轮询计划表 XVfdPollScheduler 传输无关：登记制统一排拍/从站离线退避/

        │     · RTU 串口（485）：薄壳包 XModbusRtuSerialClient——单飞 m_currentReply/
        │       请求队列 m_queue/按波特率帧间延迟/广播回合/超时重试**全部复用主站

        │     · TCP：包 XModbusTcpClient（Modbus/TCP，全双工无仲裁，可并发）；
        │       RTU-over-TCP 网关 = RTU client 开外部 IO 注入口（复用 XModbusDevice
        │       m_ioDevice 定式）后同一适配器跑在 XTcpSocket 上
        ├─ XVfdCanLink（二期）包 XCanBusDevice（Src/XProtocol/XCan 已有栈）——

        ├─ XTcpSocket    Modbus/TCP · RTU-over-TCP 网关

设计三原则（对应"尽量通用兼容大部分品牌"）：

1. **接口一律工程单位**（Hz/V/A/rpm/°C/s/%），定点标度换算（0.1Hz/0.01A/±10000%…）全部下沉子类；接口上不出现"原始码"，原始值只经 `readParam` 原样进出。
2. **品牌差异用两张表消化**：通讯点表（抽象语义 ↔ 协议地址编排）+ 参数描述表（范围/单位/小数位/出厂值/可改性元数据）。虚函数面保持稳定，新品牌=新子类+两张表。
3. **仲裁与排程上移链路层**（2026-10-27 三修）：XVfdLink 窄接口每条物理链路一个实例；**传输无关的三件套**=业务接口（XVfdDevice）+轮询计划表（XVfdPollScheduler）+健康模型（slaveLost/slaveAlive/错误码）；**传输相关的只有仲裁原语**，而每种传输的仲裁原语本来就有且不同——485=XModbusRtuSerialClient 队列串行化（薄壳复用）、TCP=全双工无仲裁、CAN=硬件仲裁。设备不持轮询定时器、不直抢 IO；子类只写"编帧/解帧/语义映射"。

- `readParam(paramId)` / `writeParam(paramId, raw)`：异步，回 `paramReadDone/paramWriteDone` 信号。
- **参数描述表** `XVfdParamDesc{ id, group, name(中文), unit, decimals, min, max, default, access(RW/RO/RunLocked/Factory), enumTexts? }`：子类提供 const 数组；父类提供 `paramCount/paramDesc_const/paramIdOf(group, index)` → **通用参数页 UI 可自动生成**（含 ☆★●▲ 可改性的运行约束提示）。
- 地址编排全部封在子类：511M 的 F0xxH(写EEPROM)/0xxxH(仅RAM)/4x xxH(RAM)/7000H(U组) 规则、ATV61 逻辑地址直用、M3 Pxxx。
- 写参数受描述表 access 约束：运行禁改（★）项在运行态直接拒绝并报 `XVfdError_ParamRunLocked`，不发帧。

### 3.5 轮询与事务调度（2026-10-27 三修：计划表传输无关，仲裁在各链路）

> 传输无关的三件套：业务接口（XVfdDevice）、轮询计划表（XVfdPollScheduler）、
> 健康模型（slaveLost/slaveAlive + XVfdError）。传输相关的只有仲裁原语，
> 而每种传输的仲裁原语本来就有且不同（485=主站队列串行化，TCP=全双工无仲裁，
> CAN=硬件仲裁）。父类不持有 IO、不开轮询定时器。

- 挂接：`XVfdDevice_attach(link, unitId)`。Modbus 链路内部持有 XModbusClient——RTU 串口=共享总线多从站（仲裁复用 XModbusRtuSerialClient 队列），TCP=点对点/网关（无仲裁）；M3 类自定义帧=RawLink 独占口自管单飞。
- 设备轮询：向链路**轮询计划表**登记（读单元组 + 周期，见 §7.2），计划表统一排拍、错峰轮转；RTU 链路的顺延策略=主站忙碌（在途或队列非空）则顺延——**动作天然优先，主站队列结构零改动**；TCP 链路无仲裁（可并发，串行开关可选）；父类 `setPollItems/setPollInterval` 变为登记参数。
- 设备动作：经链路 submit 直发（启停命令不排在长轮询后面）。
- 错误码体系照旧：`XVfdError{ OK, NotAttached, Busy, Timeout, CrcError, InvalidFrame, SlaveError(code), ParamRejected, ParamRunLocked, NotSupported, … }`，Modbus 异常帧（0x83/0x86+01~04）与 M3 错误帧（01~04）统一映射。

## 7. 总线主站：复用 XModbusRtuSerialClient（2026-10-27 二修，撤销 XBusChannel）

> 用户裁定：`XModbusRtuSerialClient` 本身就可以看成 485 的主站——撤销昨日 XBusChannel
> 新类方案：仲裁复用既有主站，只补"总轮询控制器"缺口。

### 7.1 既有主站的仲裁原语（代码核实）

| 原语 | 落点 |
| --- | --- |
| 单飞（同一时刻一帧在途） | `m_currentReply` |
| 总线级请求队列（FIFO，容量 50） | `m_queue`（XCircularQueue of XModbusReply*） |
| 帧间延迟（按波特率自动计算） | `m_interFrameDelay` |
| 广播回合窗口 | `m_waitingForTurnaround` / `m_turnaroundDelay` |
| 超时重试（超时即清收帧缓冲重发） | `m_timeoutTimer` + 超时路径 `XByteArray_clear_base`（:627-628） |
| RX 收流 | XSerialPort RX 轮询发 readyRead（10-26 根修），`readAll` 累积 |

→ **总线竞争在主站队列层已天然消解**：N 台从站（多品牌 VFD + 其他 Modbus 设备）共用一个
主站实例（`attach(client, unitId)`，XModbusAtv61 既有模式），所有请求 FIFO 串行化。
昨日对 Hub 的 7 缺口审计中，#1/#2（无总线层、串口独占）在此框架下不再是缺口——
client 就是总线层、独占就是主站语义；#3（M3 帧）不适用（见 §7.3）；余下转为补强清单。

### 7.2 补强清单（补齐"总轮询控制器"角色）

| # | 缺口 | 补强方案 |
| --- | --- | --- |
| 1 | 无统一轮询排程 | **轮询计划表组件**（XVfdPollScheduler，传输无关，挂链路层，见 §7.5）：`registerPollPlan(owner, unitId, 读单元组, intervalMs)` 统一排拍、错峰轮转；RTU 链路拍子时刻主站忙碌（在途或队列非空）则顺延——**动作天然优先，主站队列结构零改动** |
| 2 | 无从站级离线退避 | 计划表层记账：连续超时≥N → 该从站计划退避/暂停 + `slaveLost(unitId)`，周期探活恢复 `slaveAlive`；client 按事务报成败即可（沿用 Hub 的 pollOk/pollErr 统计风格） |
| 3 | 迟到应答跨事务毒化 | 超时清缓冲已有；补强=最终失败切换下一事务时，收帧解析按 `m_currentServerAddress`/事务序丢弃不匹配帧（先核实 `processReceivedFrame` 是否已按地址过滤，缺则补） |
| 4 | 广播写回合窗口 | `m_waitingForTurnaround` 已有，计划表拍子尊重该窗口即可 |
| 5 | 轮询/写结果路由到登记者 | 计划表条目带 owner 与完成回调（镜像场景回填缓存、VFD 场景回填 XVfdStatus） |

~~落点二选一~~ 已被三修取代（§7.5）：计划表抽为传输无关组件挂 XVfdLink 链路层——
485/TCP/CAN 三形态共用同一计划表与同一设备挂接面。

### 7.3 Hub 与 M3 的落位

- **XModbusHub（二期，不阻塞 VFD）**：镜像槽支持共享主站（`addSlave(busClient, unitId)`），
  轮询可迁主站计划表或保留槽定时器（队列已串行化，无碰撞，仅公平性）；届时数据镜像与
  VFD 控制**同总线共存**。Hub 原审计中的 #4（从站级离线）随计划表补齐。
- **M3 族（自定义帧）**：无法走 Modbus 主站；混协议共线不现实（波特率/帧格式不同）
  → M3 独占总线、直挂 XIODevice、自管单飞（N=1 无竞争）。

### 7.4 方案勘误记录

- ~~XBusChannel 新类~~（一版）撤销：与既有主站的队列/延迟/回合能力重复造轮子。
- ~~"计划表内建 XModbusRtuSerialClient"~~（二版）修正：计划表绑死 RTU 主站使设计偏向
  485 单一传输——三修把计划表抽为传输无关组件挂 XVfdLink 链路层，485 适配器仍是
  主站薄壳（仲裁零重复）。
- "操作走 XIODevice"收敛为"操作走 XVfdLink（Modbus 链路内持 XModbusClient）"；
  XIODevice 直挂仅剩 M3 独占口（RawLink）场景。

### 7.5 多传输形态（2026-10-27 三修）：485 / TCP / CAN 统一挂接面

**传输无关的三件套**：业务接口（XVfdDevice 全部语义虚函数/信号/能力位图）、轮询计划表
（XVfdPollScheduler：排拍/错峰/离线退避/结果路由）、健康与错误模型（slaveLost/slaveAlive
+ XVfdError）。**传输相关的只有仲裁原语**，各形态本就不同：

| 传输 | 仲裁原语 | 链路适配器 | 说明 |
| --- | --- | --- | --- |
| 485 串口 | 主站队列串行化（单飞+FIFO+帧间延迟+广播回合，XModbusRtuSerialClient 既有） | XVfdModbusLink·RTU | 薄壳包主站，仲裁零重复；计划表"忙碌顺延"=动作天然优先 |
| Modbus/TCP | 无（全双工，可并发 pipelining） | XVfdModbusLink·TCP | 包 XModbusTcpClient；每从站一连接或网关一连接多 unitId |
| RTU-over-TCP 网关 | 同 485（网关背后就是 485 总线） | XVfdModbusLink·RTU 跑在 XTcpSocket 上 | RTU client 开**外部 IO 注入口**（复用 XModbusDevice m_ioDevice 定式）即解锁 |
| CANopen | CAN 硬件仲裁（ID 优先级）+ SDO 客户端排队 | XVfdCanLink（二期） | 包 XCanBusDevice（Src/XProtocol/XCan 栈已有）；SDO 承载参数/命令、PDO 承载高频遥测；CiA402 drive profile 与 ATV61 CMD/ETA 状态机同源，语义映射自然 |
| M3 自定义帧 | 独占口 N=1 自管单飞 | XVfdRawLink（二期） | 混协议共线不现实 |

**语义层与传输层解耦的实际收益**：同一台 ATV61 从 485 换到 TCP 网关，只换链路实例，
XVfdAtv61 子类与业务层零改动；CANopen 是新语义子类（OD 映射），业务接口不变。

**submit 载荷的配对约定**：link 接口不追求跨协议统一载荷（Modbus=FC 单元、CAN=SDO
描述、M3=原始帧）——每个 XVfdDevice 子类只与配对链路组合（XVfdModbusBase↔XVfdModbusLink、
XVfdCanOpen↔XVfdCanLink），载荷类型标签运行期断言防错配；轮询计划表/健康模型/信号面
才是跨协议共享面。

## 9. 待裁定项

1. **命名**：`XVfd*` 前缀与目录 `Src/XProtocol/XVfd/` 是否认可（或 XInverter）；511M/512M/513M 族与 M3 族的厂商名，用于子类定名（如 `XVfdM512` → `XVfd<品牌>`）。
2. **XModbusAtv61 去留**：资产平移进 XVfdAtv61 后废弃旧类（推荐，面板页同步切换），或过渡期并存。
3. **M3 族是否本期立项**：首版建议只落 XVfdModbusRtu + XVfdAtv61 + XVfdM512（验证抽象覆盖两类标准 Modbus 形态），M3 自定义帧作为第二传输形态二期验证"连接无关"。

6. **快照字符串形态**：型号/序列号/版本用固定 char 数组（值语义零分配）还是 XString——建议前者。
