# HSF 会话压测与泄漏回归（实施记录）

> 日期：2026-11-08（重绘脏源根修之后的联调验收批次）
> 目的：确认本批改动**无功能回归、无内存泄漏**，并回答「多客户端连接断开
> 反复上万次」的稳定性。
> 结论：**20,000 次连接/断开 0 失败；服务端/客户端堆计数均回落到基线
> （无泄漏）；句柄数只在首轮载荷中 +4、第二轮 0 增长；全部单测与跨端
> 联调全绿。**

---

## 1. 新增诊断开关（env 门控，未设零开销）

| 变量 | 进程 | 输出 | 用途 |
|---|---|---|---|
| `HSF_HEAP_TRACE=1` | HsfServer | 每 5 秒 `[heap] sys=<字节> sessions=<n> t=<ms>` | 服务端堆计数 + 当前会话数 |
| `XHSF_HEAP_TRACE=1` | HsfClient | 每 5 秒 `[heap] sys=<字节> link=<0/1> t=<ms>` | 客户端堆计数 + 链路就绪位 |

口径：`XMemory_statistics_2(XMEMORY_TYPE_SYSTEM).systemBytes`（AGENTS
红线：泄漏看**堆计数**，不看工作集）。`sessions` 用于把「堆随连接数线性涨」
（正常缓存）与「每轮会话后回不到基线」（泄漏）区分开。

实现位置：
- `HighSpeedFilter/server/HsfServerApp.c` `hsfAppHeapTrace()`（挂在
  `hsfAppTick` 首段，5s 节流）
- `HighSpeedFilter/client/ui/HsfUi.c`（挂帧泵尾部，5s 节流）

## 2. 压测脚本

`HighSpeedFilter/client_py/tests/test_stress_reconnect.py`

```bat
bin\HsfServer.exe --sim                    :: 终端 A
set HSF_HEAP_TRACE=1

python HighSpeedFilter/client_py/tests/test_stress_reconnect.py ^
    --port 6100 --clients 8 --cycles 1250
```

压测前/后由脚本**自动**经远端配置（`CMD_CONFIG_GET/SET` 的 `login` 节）
打开同账并发（`loginAllowConcurrent=true`、`loginMaxSessions=0`），结束时
按开场读到的原值恢复——与客户端「远端设置 → 登录策略（账号）」同一条
链路，不再需要手改 JSON。`--no-policy` 可跳过这一步（服务端策略已放开
时用）。`bin/cfg/hsf_login_policy.json` 只是服务端把策略**落盘**的产物。

单轮 = 完整会话生命周期：**连接 → Hello → 登录（HMAC 10k 轮派生）→
订阅全部 9 个推送主题 → 拉一帧设备健康快照 → 主动断开**。
worker 是**独立进程**（登录派生是 GIL 绑定的 CPU 计算，多线程不能真并发）。

> 为什么必须放开同账并发：服务端缺省登录策略是「同账并发关」（root 单
> 会话语义）。开 8 个 root 客户端时第 2 个起会被「该账户已登录」拒绝——
> 那是策略，不是缺陷。脚本收尾（含异常/中断）会恢复开场读到的策略；
> 恢复失败（服务端已停等）会打印警告，此时可在「远端设置 → 登录策略
> （账号）」里改回（管理员），或删掉 `bin/cfg/hsf_login_policy.json`
> 后重启服务端（`test_client.py` 的权限/策略用例按缺省口径断言）。

## 3. 压测结果（20,000 次）

| 指标 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 规模 | 8 客户端 × 1250 轮 = **10,000** | 同上 |
| 成功/失败 | **10000 / 0** | **10000 / 0** |
| 吞吐 | 76.7 次/秒 | 77.0 次/秒 |
| 用时 | 130.4 s | 129.9 s |
| 服务端堆（结束后 sessions=0） | 700,662 / 700,702 / 701,862 | 703,030 / 701,982 |
| 服务端句柄数 | 145 → **149**（首轮载荷后） | **149 → 149** |
| 策略拒绝/错误日志 | 0 | 0 |

判读：
- 两轮合计 20,000 次会话后服务端堆稳定在 **~702 KB**（与压测前
  698.5 KB 相差 ~3 KB，属日志/缓冲的常驻增量，不是每会话泄漏——
  若按会话泄漏，10k 轮至少是 MB 级）。
- 句柄第二轮 **0 增长** ⇒ 首轮 +4 是线程/定时器池的一次性载荷，不是泄漏。
- 压测中 `sessions` 峰值到 24（8 客户端 + 关闭中的在途会话），
  空闲后回 0 ⇒ 会话回收路径正确。

## 6. 注意事项

- 压测必须**单实例**服务端：多开会表现为 bad password / 控制权被占的
  假失败（旧会话占着 root）。
- 登录策略可从客户端「远端设置 → 登录策略（账号）」（管理员）或配置 API
  （`CMD_CONFIG_SET` 的 `login` 节）修改；压测脚本用完自动恢复原值。
  `bin/cfg/hsf_login_policy.json` 只是服务端落盘产物，现场按需保留/删除。
- `[heap]` 采样 5s 一次，压测 2 分钟量级足够看趋势；更长的浸泡测试
  （小时级）建议把间隔调到 30s 并把日志写文件。

## 7. 已知微漏（未闭环，量级可忽略）

排查 CONFIG_GET 时顺带定位到 SQL 通用层的一处**每次查询 +40 字节**残余：

- 复现：单连接连发 100 次 `CMD_CONFIG_GET`，`[heap]` 逐次 +40B 且稳定
  （非启动一次性缓存）；`HsfServerStore_rowCount` 内按段打点显示
  `exec=+1584 / delq=-1544`，差额正好 40B。
- 影响面：配置读取（设置页进入/应用后）与历史分页（每请求 4 次 COUNT/MIN/MAX
  ⇒ ~160B/请求）。压测 1 万次会话不触发（会话路径不查库）。
- 处理建议：单独一批在 `XSqlQuery`/`XSqliteResult` 生命周期上定位（优先怀疑
  query/result 内部某个 40B 小分配未随 deinit 释放），修后补一条
  「N 次查询堆差分 = 0」的单元断言；本次不夹带进登录策略批次。
