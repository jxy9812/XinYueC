## 3. 回归分析（下一步的起点）

### 3.1 失败用例的特征

两个失败都在**同一个用例组**（激进双泵回归锁，`xfile_test_double_pump` 一带，`XLinkTest.c:4560` 附近）的 **Force 模式上传阶段**：

- 前置的 Auto 模式上传/下载用例**通过**（包括"Auto 下载后会话仍 Ready"）；
- 切到 `ForceSessionPump` 后上传不终局（状态 != Done），且会话掉出 Ready；
- Force 与 Auto 的唯一差别是 `XLinkFileClient_pump` 是否**代泵承载会话**（测试以 `XLinkFileClient_pump(fc, 0u)` 每约 1ms 一圈驱动）。

### 3.2 嫌疑排序（按可能性）

1. **修复 #2 的时间戳归零与 Force 代泵的交互**。归零后第一拍 pump 里心跳基准 `base = m_lastSendTick ? : m_lastReceiveTick` 两项均为 0 → `base == 0` 分支**立即发一帧 Heartbeat**。Auto 模式会话由内建定时器驱动、节拍 250ms，洪水不明显；Force 模式下 `XLinkFileTransfer_pump` 在 `Opening` 态**不调 keepAlive**（keepAlive 只在 Active 态之后），若 OpenAck 迟迟不到（Windows IOCP 停滞窗口，§14.3），`base == 0` 的心跳分支可能持续成立，心跳帧与 Open 重发帧挤占同一发送队列。建议先用二分确认。
2. **修复 #2 中 `m_nowTick = 0`**：`sendRequest` 打戳、`sendWithPrefix` 的 `m_lastSendTick` 更新都引用它；上传路径虽不走 sendRequest，但 `XLinkSession_send` 成功后会写 `m_lastSendTick = m_nowTick`——归零后的第一帧会把 `m_lastSendTick` 写成 0，使上述 `base == 0` 分支**反复成立**。此交互值得单独验证（把 `m_lastSendTick = self->m_nowTick` 改为仅当 `m_nowTick != 0` 时更新，或归零时只清 `m_lastReceiveTick`）。
3. **修复 #5 新增的拒绝帧**：只影响槽满/受理失败路径，Force 上传走正常受理，嫌疑低。但注意它的新回归锁用例（不存在子目录）依赖"拒绝后会话断开"的既有行为，确认它自身在 635 里是通过的。
4. 修复 #1/#3/#4：与上传路径无交互，嫌疑最低（#4 只在认证失败路径，本组用例未启用认证）。
