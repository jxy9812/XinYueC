## 1. 模块结构

```
hsfsrv/
  proto.py     线协议常量 + 帧头编解码       ← 线格式唯一权威
  bson.py      BSON 编解码（标准库）         ← 零第三方依赖
  auth.py      登录认证 + 账户库
  xlink.py     XLink 服务端会话层
  modbus.py    Modbus RTU/TCP 主站
  devices.py   设备驱动
  app.py       业务层
  config.py    部署配置
  __main__.py  入口
```

**分层原则**：

```
__main__.py  装配（配置 → 设备 → 服务端 → 事件循环）
    app.py   业务（命令路由 / 推送节拍 / 健康 / 闸门）
 devices.py  设备（取数 → 解工程值 → 健康判定）
  modbus.py  总线（帧收发 / CRC / 各设备协议怪癖）
  xlink.py   会话（握手 / 认证 / 订阅 / 发布 / 心跳）
```
`proto.py` / `bson.py` 是纯数据层，被所有层引用；
`config.py` 只被 `__main__` 和 `app` 读。

**不让下层反向依赖上层**：`devices.py` 不认识 BSON 键名，
`app.py` 不认识寄存器地址。这样换协议（BSON→JSON）只动 `app`，
换设备型号只动 `devices`。

## 2. 关键设计决策

### 2.1 为什么纯 asyncio 单线程、无锁

所有 I/O 都是低频（每设备 ≤ 10Hz），单线程 + 协程完全够用。
好处：**没有锁就没有锁的 bug**。任何"状态改到一半被切走"的风险都不存在
——`await` 前后状态由代码自己保证一致性。

写 socket 用 `drain()` 但状态在写之前就定好，所以不会有半更新状态。

### 2.2 为什么自己写 BSON 而不用第三方库

- 板上**没有 pip**，只能 apt；Debian bullseye 的 `python3-bson` 是老的
  pymongo 2.x 独立包，API 不确定。
- 协议只用 5 种类型，标准库 `struct` 足够。
- **零依赖 = 零部署风险**。

代价：BSON 规范里没有实现的类型（二进制、日期、正则等）一律抛
`ValueError`。这是**故意的**——静默跳过会让调用方拿半份数据做决策。

### 2.3 为什么不用 pymodbus

- bullseye 里是 `python3-pymodbus 2.1.0`（极老，API 与 3.x 完全不同，
  同步模型也不合 asyncio）。
- 现场三个设备各有协议怪癖（M512 的 8 字节错误帧、温湿度静默丢弃、
  数字量 FC0F 重发应答），**改库比写库更费**。

### 2.4 为什么每台设备一个采集任务

一台设备慢（数字量 0.4~0.8s）不应该拖累另一台（模拟量 1.8ms）。
`app.start_polling()` 给每台设备起一个独立的 `_poll_loop` 协程。

失败退避：连续失败时周期拉到 1s，日志只打第 1 条和每 60 条
（约 1 分钟一条）——板上 journald 有 50M 上限，无抑制会灌满。

### 2.5 推送为什么按「主题 × 设备」双维计时

同一主题有几台设备就推几帧。单闸管一个主题会让多设备共享计时，
实际每台间隔被台数除短（实测过：温湿度两路共用一闸，
配 1000ms 实测 473ms ≈ 1000/2）。

### 2.6 健康为什么是事件驱动

设备状态大部分时间不变。周期推等于每秒重复同一份包。
改为「状态变化才推」+「首连/首订阅补发」，流量降一个量级，
而客户端观感不变（首连立刻有数据）。

## 3. ⚠ 已踩过的陷阱

### 3.1 协议层

| 坑 | 表现 | 修法 |
|---|---|---|
| **`_maybe_await` 不返回值** | 订阅补发时 `TypeError: cannot unpack NoneType`，**会话直接被打崩** | 协程回调必须 `return await value` |
| **三元表达式优先级** | `X if c else (None,None), DATATYPE` 变成三元组 `(...)` | 返回值恒为二元组，显式 `return` |
| **用 msgCode 补发主题** | 客户端整帧丢弃（「发了但收不到」） | 一律以载荷首 4 字节 u32 为准 |
| **空 Hello 载荷即断链** | 老客户端/探针连不上 | 与 C 侧同口径：解不出就忽略，不断链 |
| **认证态被 HelloAck 覆盖** | 二次 Hello 把 Authenticating 打回 Ready，认证门控失效 | 握手分流只在 `CONNECTED` 时执行一次 |
| 心跳只发不判 | 对端死了不知道 | 静默 6s 判死 |

### 3.2 设备层

| 坑 | 表现 | 修法 |
|---|---|---|
| **有效掩码没置遥测位** | 页面永远显示 `--`（键根本不写进 BSON） | `_mark_telemetry_valid()` 按原始数据置位 |
| **`has_field` 查 valid_mask** | 置位过程自证，永远置不上 | 只看原始寄存器是否存在 |
| **0x1001 用 ÷10** | 频率差 10 倍（15Hz 报 150Hz） | **÷100** |
| **0x1000 当绝对 Hz** | 差 10 倍 | × P0.10（缺省 50Hz 兜底） |
| **0x1000 无符号读** | 负给定被钳成 0，反转静默失效 | int16 补码解 |
| **M512 错误帧当正常读** | 错误被当数据 | 显式识别 8 字节形态 |
| **温湿度等异常码** | 永远等不到 | 只能靠超时判失败 |
| **数字量 FC0F** | 应答重发，ties 配错 | 整组写用 FC05 逐点 |
| **超时就断连** | 数字量模块被打进数分钟不应答 | 只在流不可用时断连 |
| **迟到帧张冠李戴** | 上拍超时帧被当本拍应答 | 逐帧校验 MBAP 长度 + tid |

### 3.2b 串口层（**默认路径，最容易漏测**）

| 坑 | 表现 | 根因与修法 |
|---|---|---|
| **`_make_rtu` 根本不存在** | 开启串口时立刻 `NameError`，设备全采不到 | 所有端到端测试都跑 `--no-serial`，串口分支**从未被执行过**。已补 4 条装配层单测（`TestBuildDevices`） |
| **同总线两个从站各建 master** | 变频器能开串口，温湿度报「串口不可用」 | 串口是排他资源，第二个 `open` 必失败；且 RTU 半双工单主站，多 master 并发会踩帧。改为**按 (串口号,波特率) 共享一个 RtuMaster**，从站号 per-call 传入 |
| **装配期就打开串口** | 板上 demo 占着 ttyS3 时服务端起不来 | 改**懒打开**：首次 `poll` 才 `open()`，失败后 5 秒退避（别每拍戳十次） |
| 错误提示笼统 | 分不清"串口没开"与"从站不应答" | 分开报：`串口 X 不可用（5s 后重试）` vs `无应答（0 字节）`。后者说明**串口通了，是总线上没人** |

#### 最恶劣的一个：数据区切片错位（真机才暴露）

```python
# 错：把 byte_count 字节本身也当成数据
return frame[2:2 + byte_count]
# 对：数据从偏移 3 开始（站号1 + 功能码1 + 字节数1）
return frame[3:3 + byte_count]
```

真机现象：`0x1000` 那 9 个寄存器读出来是
`[4619, 47104, 21, 10496, 0, ...]`，正确应为 `[3000, 0, 5417, 0, ...]`
——**每个值都错，而且错得有规律**（整体后移一字节）。

为什么一直没发现：所有端到端测试都跑 `--no-serial`，串口分支从未执行。
一旦真机读到一帧完整应答，CRC 却**恰好还是对的**（CRC 覆盖整帧，
切片错不影响校验），于是错数据被当成好数据一路送进工程值换算。

**锁死它的测试**：`tests/test_rtu_framing.py`
用内存假串口喂手工构造的合法 RTU 帧，并用 `chunk=1..N` 覆盖
"逐字节到达"的极端分片——分片越小越能暴露偏移/错位类缺陷。

**验证串口层的工具**：`tools/serial_probe.py`

```sh
python3 tools/serial_probe.py --port /dev/ttyS3 --baud 115200,9600 --units 1,2,3,4,5
```

它分三层回答：① 串口能否打开/配置/写入 ② 总线上哪些站号在哪波特率应答
③ 命中的从站打印原始帧。**全无应答 + 串口层 OK = 物理线或从站电源问题**，
不要再改代码。

> **RS485 半双工不会自发自收**——"发出去收不到"本身是正常的，
> 判断链路只能看有没有**从站**应答。

### 3.3 部署层

| 坑 | 表现 | 修法 |
|---|---|---|
| **`cfg/` 目录不存在** | 缺省账户永远落不了盘 | 落盘前 `makedirs` |
| **日志块缓冲** | 重定向到文件时看不到现场 | 统一 `flush()` |
| **`get_event_loop()` 弃用** | 3.10+ 发 DeprecationWarning | 改 `asyncio.run()` |
| **deploy.sh 内联 Python 插值** | shell 的 `false` 变成 Python 的 `false` → NameError | 改 `sys.argv` 传参 |
| **采集失败刷爆日志** | 板端 journal 吃满内存 | 两级抑制 + 退避 |

### 3.4 测试自身的坑（别被绿色骗了）

| 坑 | 表现 |
|---|---|
| **假设备状态不反映命令** | `FakeVfd.poll()` 只看 `_reverse`，停机永远"不生效" → 误判服务端有 bug |
| **假设备不响应点动** | 只处理启停，`JOG` 命令改了 `_running` 但假设备 `poll` 不读 → 看门狗测试假红 |
| **测试脚本的断言写反** | CRC 字节序：文档写"8A 7B"是**线上字节**，我一开始按"CRC 值 0x8A7B"写，断言反了 |
| **拿假设备预设值测真机** | 对着真实 `.12` 断言 DI=0b0101（那是假设备的值）→ 6 项假红 |

**判据**：测试失败时先问"是服务端错了，还是期望值错了"。
真机测试的断言应该只断言**结构**（有字段、类型对、范围合理），
不断言**具体数值**。

```sh
python tests/run_all.py            # 单元 + 端到端（自动起停假服务端）
```


### 4.3 测试覆盖

| 文件 | 项数 | 覆盖 |
|---|---|---|
| `test_units.py` | 79 | 帧头/BSON/CRC/认证/设备解码/配置/**串口装配路径** |
| `test_rtu_framing.py` | 6 | **RTU 帧解析**（模拟从站，含逐字节分片） |
| `test_vfd_ops.py` | 66 | 变频器全部 op + 闸门 + 边界 + 点动看门狗 |

| `verify_hsf_server.py` | 21 | C 客户端口径的协议兼容性 |

当前实测：**全部通过**（79 + 6 + 66 + 68 + 21）。

### 4.4 加新测试的原则

1. **单元测试优先**：纯函数（解码、换算、CRC）用 `unittest`，
   不依赖 socket、不依赖真机，跑得快。
2. **端到端测行为而非实现**：断开言书"START 后 running==true"，
   不要断言"收到了命令字 1"（那是内部细节）。
3. **测"不支持"也要测**：`SET_SPEED` 必须**明确拒绝**，
   不能静默成功——静默成功是最危险的失败模式。
4. **安全相关必测**：点动看门狗、自动模式闸、角色门禁。
   这三处任何一个失效都是安全事故。
5. **负向用例**：畸形载荷、越界值、错误类型、空载荷。

### 4.5 假设备怎么写

`tests/fake_devices.py` 提供 `FakeVfd` / `FakeTempHum` / `FakeAnalog` / `FakeDigital`。
它们继承真实驱动类，只覆写 `poll()` / `send_command()` / `write_do()`。

**关键**：假设备的 `poll()` 必须**反映收到的命令**。否则服务端明明执行对了，
测试却报"命令无效"——这是最容易误判的地方（已经踩过两次）。

### 5.1 从开发机测板上的服务端

```sh
# 起了服务端（Python 版 6200 / C 版 6100）后，从 Windows 侧连：
python -c "
import sys; sys.path.insert(0,'.')
sys.path.insert(0,'tests')
from hsfsrv import proto, bson
from test_vfd_ops import login_as
c,_ = login_as('192.168.0.10', 6200, 'root', 'root')   # Python 版
r = c.request(proto.CMD_DEVICE_HEALTH, b'')
print(r[1])
c.close()
"
```

### 5.2 真机 DO 写入验证

**能写就必须验证能读回**——只断言 `ok=true` 是不够的
（服务端受理了但设备没执行，是最危险的假成功）。

```python
c.request(proto.CMD_DIGITAL_CONTROL, bson.encode({"dev":0,"mask":0x00A5}))
r = c.request(proto.CMD_DIGITAL_SNAPSHOT, bson.encode({"dev":0}))
assert r[1]["do"] == 0x00A5          # 读回必须一致
```

已用此方法在真实 `.12` 模块上验证通过（写 `0x00A5`，回读 `0x00A5`）。

## 6. 代码约定

### 6.1 注释

- 每个模块顶部写**它解决什么问题**，不是它包含什么函数。
- **每个非显然的常量/分支都要写"为什么"**，尤其是从实测得来的值
  （如「600ms = 3× 重发间隔」）。
- 陷阱用 `[为什么...]` / `[实锅]` / `⚠` 开头，便于搜索。
- 不写「获取xx」「设置xx」这种废话注释。

### 6.2 命名

- 内部函数/变量：`snake_case`
- 常量：`UPPER_SNAKE`（协议常量集中在 `proto.py`）
- 私有：前缀 `_`
- 与 C 侧对应的类：保持 C 侧语义名（`VfdM512`、`TempHum`）

### 6.3 异常

- **可预期的通讯失败**（超时、异常码）→ `ModbusTimeout` / `ModbusException`，
  采集循环捕获后记日志、退避、继续。
- **协议违例**（畸形 BSON、非法 op）→ 回 `ok=false` 包络，不抛到顶层。
- **真的 bug**（AttributeError 之类）→ 让它在 `handle_request` 的兜底
  `except` 里被记下来并回 `ok=false`，绝不静默。

### 6.4 改动检查清单

改代码后至少跑：

```sh
python tests/run_all.py                 # 单元 + 端到端
python -m hsfsrv --diag --no-serial     # 真机连通性
```

改了协议面（键名/命令号/主题号）**必须**同时更新
[02 线协议规格](02-线协议规格.md)，并对 C 客户端做兼容性验证。

## 7. 性能参考

| 指标 | 实测值 | 场景 |
|---|---|---|
| 模拟量单帧 RTT | **1.8 ms** | 192.168.0.11:8234 |
| 数字量单帧 RTT | **0.4~0.8 s** | 192.168.0.12/13（设备本身慢） |
| 温湿度单帧 RTT | 5.8 ms | 115200 8N1 |
| 遥测推送 | 100ms/主题 | 4 个主题并发 |
| 板上 CPU | 很低 | 纯 asyncio + 低频轮询 |

瓶颈全在设备侧，服务端本身不是瓶颈。
