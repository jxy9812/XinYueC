## 1. 模块结构

```
hsfsrv/
  proto.py       线协议常量 + 帧头编解码       ← 线格式唯一权威
  bson.py        BSON 编解码（标准库）         ← 零第三方依赖
  auth.py        登录认证 + 账户库
  xlink.py       XLink 服务端会话层
  modbus.py      Modbus RTU/TCP 主站
  devices.py     设备驱动
  app.py         业务层
  config.py      部署配置
  autocontrol.py 自动运行控制层（**骨架，逻辑待扩展**）
  valves.py      电磁阀设备层（点位映射 + 状态判读 + 告警事件）
  pumps.py       进水泵设备层（DO 输出 + 幂等 + 外部改动接管；**无反馈故无超时**）
  virtualdev.py  虚拟设备层（`--sim`：只换 master，业务层全真实）
  __main__.py    入口
```

外部工具（不在包内）：

```
server_py/tools/  运维脚本（net_selfheal / fix_module_ip / serial_probe /
                  mt3a_config）
sim/hsf_sim.py    **独立设备模拟器**（假服务端，C 端客户端也能连；见 §5.3）
```

**分层原则**：

```
__main__.py  装配（配置 → 设备 → 服务端 → 事件循环）
    app.py   业务（命令路由 / 推送节拍 / 健康 / 闸门 / 自动控制调度）
 devices.py  设备（取数 → 解工程值 → 健康判定）
  modbus.py  总线（帧收发 / CRC / 各设备协议怪癖）
  xlink.py   会话（握手 / 认证 / 订阅 / 发布 / 心跳）
```
`proto.py` / `bson.py` 是纯数据层，被所有层引用；
`config.py` 只被 `__main__` 和 `app` 读。

**不让下层反向依赖上层**：`devices.py` 不认识 BSON 键名，
`app.py` 不认识寄存器地址。这样换协议（BSON→JSON）只动 `app`，
换设备型号只动 `devices`。

### 1.1 自动运行控制层（`autocontrol.py`，骨架）

两种运行模式：手动（人在客户端点）、自动（**服务端自己驱动设备**，
远程控制全拒）。自动模式原先只是一个门禁开关，`autocontrol.py` 把
"服务端自己怎么动设备"这层单独拆出来：

- **`AutoContext`** —— 自动逻辑访问设备的**唯一通道**
  （`read_di/read_do/write_do`、`valve_state/open_valve/close_valve`、
  `analog_ma`、`vfd_snapshot`、`temphum`、`throttle`）。
  设备下标、点位映射、缓存新鲜度口径全挡在这层后面。
- **`AutoController`** —— `start/stop/step(now_ms)`。**`step()` 当前是空实现**
  （刻意的安全默认）：哪怕误开自动模式又没写逻辑，行为也只是"不动作"，
  不会因为半成品逻辑乱动现场设备。

配套约束（都是踩过的）：

| 约束 | 原因 |
|---|---|
| `step()` 外层**必须**包 try（`app._auto_step`） | 工艺代码崩了不能把整个服务端 tick 带死（那会连遥测推送和设备健康一起停，界面全黑）。日志限频 1 分钟一条 |
| 异常限频**不能用** `now - last > 60000` | `last` 初值 0、单调毫秒从进程启动算起 ⇒ 启动后 1 分钟内第一次异常被判"刚记过"而吞掉。现场表现是"自动逻辑明明崩了却一条日志都没有"。要用 `not last` 显式判"从未记过" |
| 控制器启停只挂在 `apply_mode_to_devices()` 一处 | 放多处会出现"模式变了控制器还在跑" ⇒ **手动模式下的设备被自动逻辑偷偷驱动**（安全事故） |
| `restore_run_mode()` 不落盘但必须同步模式 | 值本来就来自磁盘；不同步会"恢复成自动后控制器不启动"，表现是"模式显示自动却什么都不做" |

有一条测试 `test_step_does_nothing_in_this_version` 锁住"空实现"这个默认值：
谁要往里填逻辑，必须同步改那条测试——"动设备"不能悄悄发生。

## 2. 关键设计决策

### 2.1 为什么纯 asyncio 单线程、无锁

所有 I/O 都是低频（每设备 ≤ 10Hz），单线程 + 协程完全够用。
好处：**没有锁就没有锁的 bug**。任何"状态改到一半被切走"的风险都不存在
——`await` 前后状态由代码自己保证一致性。

写 socket 用 `drain()` 但状态在写之前就定好，所以不会有半更新状态。

### 2.2 为什么自己写 BSON 而不用第三方库

- 板上**没有 pip**，只能 apt；Debian bullseye 的 `python3-bson` 是老的
  pymongo 2.x 独立包，API 不确定。
- 协议只用 5 种类型，标准库 `struct` 足够。
- **零依赖 = 零部署风险**。

代价：BSON 规范里没有实现的类型（二进制、日期、正则等）一律抛
`ValueError`。这是**故意的**——静默跳过会让调用方拿半份数据做决策。

### 2.3 为什么不用 pymodbus

- bullseye 里是 `python3-pymodbus 2.1.0`（极老，API 与 3.x 完全不同，
  同步模型也不合 asyncio）。
- 现场三个设备各有协议怪癖（M512 的 8 字节错误帧、温湿度静默丢弃、
  数字量 FC0F 重发应答），**改库比写库更费**。

### 2.4 为什么每台设备一个采集任务

一台设备慢（数字量 0.4~0.8s）不应该拖累另一台（模拟量 1.8ms）。
`app.start_polling()` 给每台设备起一个独立的 `_poll_loop` 协程。

失败退避：连续失败时周期拉到 1s，日志只打第 1 条和每 60 条
（约 1 分钟一条）——板上 journald 有 50M 上限，无抑制会灌满。

### 2.5 推送为什么按「主题 × 设备」双维计时

同一主题有几台设备就推几帧。单闸管一个主题会让多设备共享计时，
实际每台间隔被台数除短（实测过：温湿度两路共用一闸，
配 1000ms 实测 473ms ≈ 1000/2）。

### 2.6 健康为什么是事件驱动

设备状态大部分时间不变。周期推等于每秒重复同一份包。
改为「状态变化才推」+「首连/首订阅补发」，流量降一个量级，
而客户端观感不变（首连立刻有数据）。

## 3. ⚠ 已踩过的陷阱

### 3.1 协议层

| 坑 | 表现 | 修法 |
|---|---|---|
| **`_maybe_await` 不返回值** | 订阅补发时 `TypeError: cannot unpack NoneType`，**会话直接被打崩** | 协程回调必须 `return await value` |
| **三元表达式优先级** | `X if c else (None,None), DATATYPE` 变成三元组 `(...)` | 返回值恒为二元组，显式 `return` |
| **用 msgCode 补发主题** | 客户端整帧丢弃（「发了但收不到」） | 一律以载荷首 4 字节 u32 为准 |
| **空 Hello 载荷即断链** | 老客户端/探针连不上 | 与 C 侧同口径：解不出就忽略，不断链 |
| **认证态被 HelloAck 覆盖** | 二次 Hello 把 Authenticating 打回 Ready，认证门控失效 | 握手分流只在 `CONNECTED` 时执行一次 |
| 心跳只发不判 | 对端死了不知道 | 静默 6s 判死 |

### 3.2 设备层

| 坑 | 表现 | 修法 |
|---|---|---|
| **有效掩码没置遥测位** | 页面永远显示 `--`（键根本不写进 BSON） | `_mark_telemetry_valid()` 按原始数据置位 |
| **`has_field` 查 valid_mask** | 置位过程自证，永远置不上 | 只看原始寄存器是否存在 |
| **0x1001 用 ÷10** | 频率差 10 倍（15Hz 报 150Hz） | **÷100** |
| **0x1000 当绝对 Hz** | 差 10 倍 | × P0.10（缺省 50Hz 兜底） |
| **0x1000 无符号读** | 负给定被钳成 0，反转静默失效 | int16 补码解 |
| **M512 错误帧当正常读** | 错误被当数据 | 显式识别 8 字节形态 |
| **温湿度等异常码** | 永远等不到 | 只能靠超时判失败 |
| **数字量 FC0F** | 应答重发，ties 配错 | 整组写用 FC05 逐点 |
| **超时就断连** | 数字量模块被打进数分钟不应答 | 只在流不可用时断连 |
| **迟到帧张冠李戴** | 上拍超时帧被当本拍应答 | 逐帧校验 MBAP 长度 + tid |
| **32 点读 `IncompleteReadError`** | 整条流永久错位、后续全废 | 模块把一帧拆多个 TCP 段发；`readexactly` + 外层 `wait_for` 超时会**取消并丢掉已缓冲的半帧**。改成只按"还差多少字节"反复 `read()`，EOF 才认失败（`_read_upto`） |
| **按 16 点写死** | 32 点模块的上半区永远看不见（服务端明明在发） | 点数一律取配置 `channels` / 快照 `count`，客户端动态重建灯阵 |
| **调了不存在的方法** | 6 路阀永远"无有效反馈"，看着像行程开关没接 | `valves.py` 调 `di_bit()` 而 `DigitalIo` 没这个方法，异常被外层 except 吞掉置 `valid=False`。补齐并让越界**显式抛 IndexError**（静默返回 False 会把"点位配错了"伪装成"这个开关没通"） |
| **`AnalogChannelScale(idx, **item)`** | 加载配置时 `TypeError: got multiple values for argument 'index'` | `item` 自带 `index` 键 ⇒ 位置参数与关键字撞车。只传关键字，下标以解析值为准 |
| **4~20mA 零点按严格门限判** | 最正常的工作点天天报"断线" | 活零点实测 3.996mA（995mV/249Ω）。留 0.05mA 容差 |
| **阀控制应答带命令前的旧状态** | 点「开阀」界面毫无变化，**要再点一次才动** | `_h_valve_control` 里在 `set_valve()` 后只调 `valve_bank.poll()`，而它读的是**数字量模块缓存**（命令前那拍）。修法：`refresh_valve_sources(force=True)` 绕过节流强制现读一帧再判读 |
| **反复点同侧把超时无限推后** | 卡住的阀**永远不报警**（实测连点 8 次，0 告警） | `set_valve` 无条件 `cmd_at_ms = now`。改成按处置分支：已到位→`ignored`（不写 DO）、同目标动作中→`repeated`（重发但**不重置计时**）、反向→`reversed`（重新计时） |
| **外部写 DO 绕过阀状态机** | 从数字量页翻 DO16，阀页那 10 秒显示"**无到位反馈（检查行程开关接线）**"，20s 超时也不判 | 数字量页走 `_h_digital_control → write_do`，不经 `set_valve` ⇒ `cmd_at_ms` 没置位。修法：`poll()` 里比对模块实际 DO 与 `item.known_do`，不一致就接管为新动作 |
| **动作中"停在原位置"被当成到位** | 命令刚下发就报"检查接线"、计时器被清零、20s 永不超时 | `refresh_state` 的到位分支**无条件** `cmd_at_ms = 0`。命令刚发时反馈必然是旧位置 ⇒ 判成"已到位"。修法：只有**到位位置 == 命令目标**才结束计时，否则仍算动作中 |
| **首拍校准吃掉外部改动** | 服务端重启后阀页凭空显示"动作中"，20s 后误报超时 | `known_do` 在数字量模块还没采过一帧时就校准（那时 `dev.do` 全 0）⇒ 真数据一到就"检测到外部改动"。修法：等 `module.last_ok_ms > 0` 才校准 |
| **停机下发给定产生假运行** | 界面显示"停机"却是 25Hz / 720rpm | `VirtualVfd.write_single(0x1000)` 无条件设 `target_hz`，`on_access` 不看 `running` 就爬坡。修法：① 停机时给定只记值不下发；② `on_access` 在非运行态直接归零；③ 服务端闸门拒绝停机时的调速（`_VFD_SETPOINT_OPS`） |
| **流量计页永远 `--`** | 以为设备没接，其实是服务端没实现 | Python 服务端只有 `TOPIC_FLOWMETER_STATUS` 常量，**没有设备类/虚拟模型/装配**（C 端有 `XFlowMeter`）。已补 `devices.FlowMeter` + `virtualdev.VirtualFlowMeter`；`--sim` 时自动补挂（现场配置默认关） |

### 3.2b 串口层（**默认路径，最容易漏测**）

| 坑 | 表现 | 根因与修法 |
|---|---|---|
| **`_make_rtu` 根本不存在** | 开启串口时立刻 `NameError`，设备全采不到 | 所有端到端测试都跑 `--no-serial`，串口分支**从未被执行过**。已补 4 条装配层单测（`TestBuildDevices`） |
| **同总线两个从站各建 master** | 变频器能开串口，温湿度报「串口不可用」 | 串口是排他资源，第二个 `open` 必失败；且 RTU 半双工单主站，多 master 并发会踩帧。改为**按 (串口号,波特率) 共享一个 RtuMaster**，从站号 per-call 传入 |
| **装配期就打开串口** | 板上 demo 占着 ttyS3 时服务端起不来 | 改**懒打开**：首次 `poll` 才 `open()`，失败后 5 秒退避（别每拍戳十次） |
| 错误提示笼统 | 分不清"串口没开"与"从站不应答" | 分开报：`串口 X 不可用（5s 后重试）` vs `无应答（0 字节）`。后者说明**串口通了，是总线上没人** |

#### 最恶劣的一个：数据区切片错位（真机才暴露）

```python
# 错：把 byte_count 字节本身也当成数据
return frame[2:2 + byte_count]
# 对：数据从偏移 3 开始（站号1 + 功能码1 + 字节数1）
return frame[3:3 + byte_count]
```

真机现象：`0x1000` 那 9 个寄存器读出来是
`[4619, 47104, 21, 10496, 0, ...]`，正确应为 `[3000, 0, 5417, 0, ...]`
——**每个值都错，而且错得有规律**（整体后移一字节）。

为什么一直没发现：所有端到端测试都跑 `--no-serial`，串口分支从未执行。
一旦真机读到一帧完整应答，CRC 却**恰好还是对的**（CRC 覆盖整帧，
切片错不影响校验），于是错数据被当成好数据一路送进工程值换算。

**锁死它的测试**：`tests/test_rtu_framing.py`
用内存假串口喂手工构造的合法 RTU 帧，并用 `chunk=1..N` 覆盖
"逐字节到达"的极端分片——分片越小越能暴露偏移/错位类缺陷。

**验证串口层的工具**：`tools/serial_probe.py`

```sh
python3 tools/serial_probe.py --port /dev/ttyS3 --baud 115200,9600 --units 1,2,3,4,5
```

它分三层回答：① 串口能否打开/配置/写入 ② 总线上哪些站号在哪波特率应答
③ 命中的从站打印原始帧。**全无应答 + 串口层 OK = 物理线或从站电源问题**，
不要再改代码。

> **RS485 半双工不会自发自收**——"发出去收不到"本身是正常的，
> 判断链路只能看有没有**从站**应答。

### 3.3 部署层

| 坑 | 表现 | 修法 |
|---|---|---|
| **`cfg/` 目录不存在** | 缺省账户永远落不了盘 | 落盘前 `makedirs` |
| **日志块缓冲** | 重定向到文件时看不到现场 | 统一 `flush()` |

| **`tests/` 被根 `.gitignore` 挡掉** | 仓库根有 `Tests/` 规则，Windows 上大小写不敏感 ⇒ 整个 Python 测试目录**从未入库** | 子目录 `.gitignore` 加 `!tests/` `!tests/*.py` 反忽略 |

### 3.3b 启动与入口层（2026-11-05）

| 坑 | 表现 | 修法 |
|---|---|---|
| **直接运行 `__main__.py`** | 控制台**一闪而过**（`ImportError: attempted relative import with no known parent package`）。看起来像程序坏了，其实只是启动方式错 | `__package__` 为空时把包父目录塞进 `sys.path` 再以包方式重入；或用 `.bat` 走 `python -m` |
| **`.bat` 用纯 LF** | cmd 的行缓冲按 CRLF 切，`goto`/标签解析出问题 | 转 CRLF |
| **`.bat` 混中文** | cmd 按 OEM 码页读，注释变乱码甚至当命令执行 | 保持纯 ASCII；中文日志靠 `chcp 65001` + `PYTHONIOENCODING=utf-8` |
| **只查 `where py`** | launcher 存在但没装 Python 3 | 用 `py -3 -c "import sys"` 实际执行验证 |
| **重复日志** | `auth.load()` 与 `setup_users()` 各打一条"账户库已加载" | 留一处，否则排查时误以为加载了两次 |

### 3.4 测试自身的坑（别被绿色骗了）

| 坑 | 表现 |
|---|---|
| **假设备状态不反映命令** | `FakeVfd.poll()` 只看 `_reverse`，停机永远"不生效" → 误判服务端有 bug |
| **假设备不响应点动** | 只处理启停，`JOG` 命令改了 `_running` 但假设备 `poll` 不读 → 看门狗测试假红 |
| **测试脚本的断言写反** | CRC 字节序：文档写"8A 7B"是**线上字节**，我一开始按"CRC 值 0x8A7B"写，断言反了 |
| **用例间事件循环污染** | 某用例跑过 `asyncio.run()`（它会关闭并清空线程的当前循环），后面的 `get_event_loop().run_until_complete()` 直接抛 `RuntimeError`（Python 3.12 上无当前循环就报错）。**一律用 `asyncio.run()`** |
| **断言用错数据** | 阀"双到位同时有效"用例只置了一个 DI（另一个上一拍已清 0），得到"已关"而不是"故障"。置双高要**两个都设**，别只改一个 |
| **拿假设备预设值测真机** | 对着真实 `.12` 断言 DI=0b0101（那是假设备的值）→ 6 项假红 |

**判据**：测试失败时先问"是服务端错了，还是期望值错了"。
真机测试的断言应该只断言**结构**（有字段、类型对、范围合理），
不断言**具体数值**。

## 4. 测试

### 4.4 加新测试的原则

1. **单元测试优先**：纯函数（解码、换算、CRC）用 `unittest`，
   不依赖 socket、不依赖真机，跑得快。
2. **端到端测行为而非实现**：断开言书"START 后 running==true"，
   不要断言"收到了命令字 1"（那是内部细节）。
3. **测"不支持"也要测**：`SET_SPEED` 必须**明确拒绝**，
   不能静默成功——静默成功是最危险的失败模式。
4. **安全相关必测**：点动看门狗、自动模式闸、角色门禁。
   这三处任何一个失效都是安全事故。
5. **负向用例**：畸形载荷、越界值、错误类型、空载荷。

### 4.5 假设备怎么写

`tests/fake_devices.py` 提供 `FakeVfd` / `FakeTempHum` / `FakeAnalog` / `FakeDigital`。
它们继承真实驱动类，只覆写 `poll()` / `send_command()` / `write_do()`。

**关键**：假设备的 `poll()` 必须**反映收到的命令**。否则服务端明明执行对了，
测试却报"命令无效"——这是最容易误判的地方（已经踩过两次）。

### 5.2 真机 DO 写入验证

已用此方法在真实 `.12` 模块上验证通过（写 `0x00A5`，回读 `0x00A5`）。

### 5.4 虚拟设备 `--sim`（**推荐**：业务层全为真实实现）

```sh
python -m hsfsrv --sim                    # 虚拟设备 + 真实业务层
python -m hsfsrv --sim --sim-flaky 0.1    # 顺带模拟数字量模块抖动

# ---- 电磁阀动作行程（验证"动作中"与 20s 超时告警）----
python -m hsfsrv --sim                          # 缺省 10s 行程（现场真实节奏）
python -m hsfsrv --sim --sim-valve-move 25      # 25s 行程 > 20s 阈值 ⇒ 会报警
python -m hsfsrv --sim --sim-valve-move -1      # 阀卡死，永不动作
python -m hsfsrv --sim --sim-valve-no-feedback  # 行程开关没接（DI 恒 0）
```

**只替换设备物理层**：`devices.py` 与 `app.py` 一行不改，**全部真实运行**。

```
app.py（闸门/看门狗/阀定时器/告警/健康）   ← 真实
      ↓
devices.py（换算/状态字解码/故障表/写命令字）← 真实
      ↓
modbus.py（真实总线）  │  virtualdev.py（内存寄存器）   ← 只换这一层
```

`VirtualMaster` 只需实现 `read` / `write_single` / `close` 三个方法
（设备类只调这三个），就能顶替真实的 `TcpMaster`/`RtuMaster`。

**真实设备完全不碰**：不开串口、不建 TCP。设备拆了能跑，接回来不用改代码。

| 虚拟模型 | 模拟的寄存器 |
|---|---|
| `VirtualVfd` | 0x1000 给定（int16 百分比）/ 0x1001 输出频率（0.01Hz）/ 0x1002 母线 / 0x1003 电压 / 0x1004 电流 / 0x1005 功率 / 0x1006 转矩 / 0x2000 命令字 / 0x3000 状态字 / 0x8000 故障码 |
| `VirtualTempHum` | FC04 0x0000 ×2（各 ×0.1） |
| `VirtualFlowMeter` | FC03 0x1010 ×22（22 槽，高字在前；累积量按真实时间积分） |
| `VirtualTurbidity` | FC03 0x0000 ×2（32 位整数 ÷100 = NTU；两台基准/相位不同） |
| `VirtualAnalog` | FC04 0x0000 ×N（**毫伏**口径；通道0 = 2985mV 压差计） |
| `VirtualDigital` | FC01/FC02 读、FC05 写；**行程开关带动作时间**（见下）；DO22 = 进水泵 |

**行为细节（都踩过）**：

| 细节 | 原因 |
|---|---|
| **频率爬坡**（25Hz/s） | 瞬跳的话界面上永远看不到"加速中"，也验证不了"给定变了但还没跟上" |
| **电磁阀行程时间**（缺省 10s，见下） | 瞬发到位的话，状态机的「动作中」与「20s 超时」两条分支**永远走不到** —— 功能写了却无法观察/验证 |
| **未建模寄存器返回 0，不抛异常** | 初版对 0x1007 抛 `KeyError` → `READ_GROUPS` 整拍读失败 → **设备永远离线**。真机对"存在但不关心"的寄存器（0x1009 AI1、0x1010 PID…）正常回 0 |

#### 5.4.1 虚拟电磁阀的动作行程

现场阀满开满关约 **10s**，服务端 **20s** 判超时。虚拟数字量模块按这个
时间尺度建模：

```
写 DO → 进入「动作中」：两个到位 DI 都断开（0/0）
      → 经过 move_ms（缺省 10000）→ 目标侧到位
```

| 参数 | 行为 | 用途 |
|---|---|---|
| 缺省（10s） | 10s 到位 | 现场真实节奏：界面能看到「动作中」 |
| `--sim-valve-move 25` | 25s 到位 | **超过 20s 阈值 ⇒ 验证超时告警链路** |
| `--sim-valve-move -1` | 永不动作 | 阀卡死（验证故障判读与文案） |
| `--sim-valve-no-feedback` | DI 恒 0 | 行程开关没接（"无到位反馈"那条分支） |

> **瞬发模型为什么不行**：原来 `di_mask()` 直接由 `do_mask` 推导，写完 DO
> 的下一拍（200ms）就「到位」了，`cmd_at_ms` 立刻被清零 ——
> 20s 分支是**死代码**，用户上报"超时报警没设计"其实是"看不见"。

**实测时间线（缺省 10s）**：

```
命令应答  v0_state=3 (动作中)
+1s ~ +10s  动作中   openFb=False closeFb=False
+11s        已开     openFb=True
告警数: 0
```

**实测时间线（`--sim-valve-move 25`）**：

```
+ 0.2s  动作中   告警数=0
+20.1s  故障     告警数=1   → kind=1(超时) 动作超时未到位（20s）
+25.1s  已开     告警数=2   → kind=3(恢复) 已到位（开）
```

**能验证 / 不能验证**：

| ✅ 能 | ❌ 不能 |
|---|---|
| 自动模式拒绝全部远程控制 | 设备协议怪癖（FC0F 重发、应答分片） |
| 点动看门狗 600ms 超时停机 | 真实换算精度（压差计零点、转速滑差） |
| 电磁阀 20s 定时器 + 告警去重 | 真实行程时间（液压/气压负载差异） |
| **阀动作中 / 超时 / 恢复全过程** | 真实的阀体卡滞模式 |
| 重复点击不重置计时、在途反向 | — |
| 外部写 DO 的接管与超时 | — |
| 流量计 22 寄存器拼装与累积量 | 真机单位码/量程标定 |
| 浊度两台独立取值 + 离线降级 | 浊度真机寄存器口径（未确认） |
| 进水泵写 DO / 幂等 / 外部改动接管 | 泵真实是否转动（**没有反馈点，原理上测不了**） |
| 健康推送、推送节拍、命令路由 | — |
| 全部设备驱动的换算与解码 | — |

> **最后一行值得单独说**：泵的"是否真的在转"**不在能验证的清单里**，
> 因为现场没有运行反馈点。虚拟模型能验证的是"命令写下去了、回显对得上"，
> 仅此而已 —— 别把 `--sim` 通过当成"泵能转"的证明。

### 5.5 独立模拟器 `sim/hsf_sim.py`（C 端联调用）

⚠ **与 §5.4 是两种不同的东西，选错会白查一轮**：

| | `sim/hsf_sim.py`（本节） | `--sim`（§5.4） |
|---|---|---|
| 替换范围 | **整个服务端**（会话+业务+设备自己写） | **只换设备物理层** |
| 业务层 | **假**（简化命令处理） | 真实 `app.py` |
| 自动模式闸门 | **不生效**（永远能控） | 生效 |
| 点动看门狗 | **不生效**（不会自动停） | 生效 |
| 阀定时器/告警 | **不生效** | 生效 |
| 适合 | C 端纯协议+界面联调、不装服务端环境 | **验证业务逻辑** |

**要验证控制闸门/看门狗/阀告警 → 必须用 `--sim`。**

**设备没到位时也能把界面/交互跑起来**。它是一个**假服务端**：只实现 XLink
会话层 + HSF 业务命令的最小子集，数据全合成，不碰任何真实设备。

```sh
python sim/hsf_sim.py                          # 起假服务端（6288）
python sim/hsf_sim.py --port 6100              # 模拟 C 版服务端端口
python sim/hsf_sim.py --show                   # 同时开客户端看实窗
python sim/hsf_sim.py --show --page-name vfd   # 指定起始页
python sim/hsf_sim.py --no-shot                # 只起服务端，前台保持
python sim/hsf_sim.py --check                  # 校验协议常量与服务端一致
```

**C 端客户端也能直接连**：协议面完全一致，`--port 6100` 就是 C 版服务端的
缺省端口，`HsfClient.exe` 连它无需任何改动。

**合成数据的形状**：刻意在**上半区**（bit16..31）放信号
（`DI=0x00FF00FF`、`DO=0x8000000F`）——任何一环按 16 点截断，界面上
CH16..CH31 会全灭或只画 16 个格，一眼可见。

**三条实现约定**（都是踩过的）：

| 约定 | 原因 |
|---|---|
| 只**借用** `xlink/bson/auth` 三个纯协议模块（`sys.path` 引用，**不复制**） | 复制一份必然漂移，症状是"模拟器发的帧客户端解不开" |
| 协议常量**自带一份** + `--check` 与服务端 `proto.py` 逐项比对 | 常量是两份定义，漂移后果是"某字段收不到"极难查。`--check` 曾立刻抓出 3 处真错误（见下） |
| **三处钩子必须给**：`on_ready` / `dispatch` / `on_publish_now` | 缺任一处都在"登录成功后"抛异常把会话打死，表现统一为"登录成功但立刻断开、一直接不到数据" |

> `on_publish_now` 必须对**所有**主题返回二元组。客户端还会订阅温湿度/健康
> 等全局主题，对未支持主题返回 `None` 会在
> `payload, dtype = await ...` 处抛 `cannot unpack non-iterable NoneType`。

**`--check` 抓出的真实错误**（这就是它存在的价值）：

| 常量 | 写错的 | 实际 |
|---|---|---|
| `OP_SET_FREQUENCY` | 10 | **2** |
| `OP_SET_SPEED` | 11 | **3** |
| `CMD_VFD_SNAPSHOT` | 0x0101 | **0x0102**（0x0101 是 CONTROL） |

第三个正是"变频器页一进去就报'控制已禁用：不支持的动作 op=0'"的根因——
快照请求被当成控制命令处理了。

> **排查提示**：模拟器验收时"名字/字段一直为空"，先查**端口是否被旧的
> 模拟器进程占着**（新进程绑不上，客户端连的是旧版）。这与项目里已记录的
> 「HSF 假性无数据＝旧服务端占端口」是同一个坑。

## 6. 代码约定

### 6.1 注释

- 每个模块顶部写**它解决什么问题**，不是它包含什么函数。
- **每个非显然的常量/分支都要写"为什么"**，尤其是从实测得来的值
  （如「600ms = 3× 重发间隔」）。
- 陷阱用 `[为什么...]` / `[实锅]` / `⚠` 开头，便于搜索。
- 不写「获取xx」「设置xx」这种废话注释。

### 6.2 命名

- 内部函数/变量：`snake_case`
- 常量：`UPPER_SNAKE`（协议常量集中在 `proto.py`）
- 私有：前缀 `_`
- 与 C 侧对应的类：保持 C 侧语义名（`VfdM512`、`TempHum`）

### 6.3 异常

- **可预期的通讯失败**（超时、异常码）→ `ModbusTimeout` / `ModbusException`，
  采集循环捕获后记日志、退避、继续。
- **协议违例**（畸形 BSON、非法 op）→ 回 `ok=false` 包络，不抛到顶层。
- **真的 bug**（AttributeError 之类）→ 让它在 `handle_request` 的兜底
  `except` 里被记下来并回 `ok=false`，绝不静默。

### 6.4 改动检查清单

改代码后至少跑：

```sh
python tests/run_all.py                 # 单元 + 端到端
python -m hsfsrv --diag --no-serial     # 真机连通性
```

改了协议面（键名/命令号/主题号）**必须**同时更新
[02 线协议规格](02-线协议规格.md)，并对 C 客户端做兼容性验证。
