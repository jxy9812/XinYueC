# 01 · 部署与运维

本文只讲「怎么把它跑起来、怎么看着它、出问题怎么办」。
协议细节见 [02 线协议规格](02-线协议规格.md)，设备寄存器见
[03 设备与寄存器口径](03-设备与寄存器口径.md)。

## 1. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| Python | **3.7+**（板端 3.9.2，开发机 3.12 均验证） | 只用标准库 + 可选 pyserial |
| pyserial | 3.4+（**仅采串口时需要**） | 只跑 TCP 设备可以不装 |
| 网络 | 能到 `192.168.0.11/12/13` | 三个 Modbus TCP 设备 |
| 串口 | `/dev/ttyS3`（仅采变频器/温湿度时需要） | 必须独占 |

### 1.1 板上装 pyserial

板子（RK3568 / Debian 11）**没有 pip**，用 apt：

```sh
ssh root@192.168.0.10 'apt-get install -y python3-serial'
# 验证
ssh root@192.168.0.10 'python3 -c "import serial; print(serial.VERSION)"'
```

板子能连清华镜像（`mirrors.tuna.tsinghua.edu.cn`），apt 源已配好。

> **IPv6 假故障**：板上 `ping`/DNS 会先返回 IPv6 地址，若网络无 IPv6 会表现为
> 「连不上镜像」。实际 IPv4 是通的——判断连通性用 `getaddrinfo(..., AF_INET)`
> 而不是默认解析。

## 2. 部署

### 2.1 一键部署

```sh
cd HighSpeedFilter/server_py

sh deploy.sh --no-serial     # 串口关（推荐先这样验证 TCP 三个设备）
sh deploy.sh --serial        # 串口开（需先停掉占串口的 demo）
```

可选参数：`--host <ip>`（默认 192.168.0.10）、`--dir <远程目录>`、`--port <端口>`。

脚本做的事：

1. 打包 `hsfsrv/` + `tests/` 传上去（排除 `__pycache__` 和已有 `cfg/`）
2. 检查 pyserial（缺失只提示，不中断）
3. **首次**生成 `cfg/hsf_server_py.json`（已有则保留不改）
4. 写 `/etc/systemd/system/hsfserverpy.service` 并 enable
5. 跑一轮设备自检
6. 重启服务并确认端口在听

### 2.2 手工部署（不想用脚本时）

```sh
scp -r hsfsrv tests root@192.168.0.10:/root/Desktop/XinYueC/hsf_server_py/
ssh root@192.168.0.10 'cd /root/Desktop/XinYueC/hsf_server_py && python3 -m hsfsrv --diag'
```

### 2.3 systemd 单元

`deploy.sh` 写入的内容：

```ini
[Unit]
Description=HSF Server (Python, XLink over TCP)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/root/Desktop/XinYueC/hsf_server_py
ExecStart=/usr/bin/python3 -m hsfsrv
Restart=on-failure
RestartSec=3
StandardOutput=journal
StandardError=journal
SyslogIdentifier=hsfserverpy

[Install]
WantedBy=multi-user.target
```

日志走 journald——板上 journald 已封顶 50M（`/etc/systemd/journald.conf.d/limit.conf`），
不会吃满内存。

## 3. 串口与板上 demo 的冲突

**这是部署时最容易踩的坑。**

板上 `run_test.service` 启动的 GUI demo 会以 **Modbus 从站模式**独占
`/dev/ttyS3`（标志文件 `/root/Desktop/XinYueC/slave485.mode`。
变频器（站 2）和温湿度（站 4）也在这条 485 上。）

两个进程抢同一个串口的结果：打开失败，或互相把对方的帧踢掉。

### 要采串口时的完整步骤

```sh
# 1. 停 demo（释放 ttyS3）
ssh root@192.168.0.10 'systemctl stop run_test.service'

# 2. 打开配置里的串口开关
ssh root@192.168.0.10 "sed -i 's/\"serial_enabled\": *false/\"serial_enabled\": true/' \
    /root/Desktop/XinYueC/hsf_server_py/cfg/hsf_server_py.json"

# 3. 重启服务
ssh root@192.168.0.10 'systemctl restart hsfserverpy'

# 4. 确认变频器/温湿度从"未装配"变成 OK
ssh root@192.168.0.10 'journalctl -u hsfserverpy -n 20 --no-pager'
```

### 要恢复 demo

```sh
ssh root@192.168.0.10 'systemctl stop hsfserverpy && systemctl start run_test.service'
```

**两者不能同时采同一条 485。** 如果现场确实需要「demo 显示 + 服务端采集」
并存，只能二选一：让 demo 别占串口（删 `slave485.mode` 后重启 demo），
或者让服务端把数据转给 demo（当前未实现）。

## 4. 配置文件

路径：`<程序根>/cfg/hsf_server_py.json`
（程序根 = `server_py/`，按本文件位置反推，**不依赖当前工作目录**——
systemd 从别的目录拉起来也不会读错配置。）

完整结构：

```jsonc
{
  "server": {
    "port": 6200,              // 监听端口（Python 版缺省 6200，与 C 版 6100 错开）
    "serial_enabled": false    // 串口总开关（false = 完全不碰 ttyS3）
  },
  "serial": {
    "port": "/dev/ttyS3",
    "baudrate": 115200,        // 变频器 PD-00 与温湿度 000BH 均 115200
    "timeout_ms": 400,         // 单帧请求超时
    "retries": 1,              // 重试次数（≥1 才能把滞留的错误帧冲掉）
    "vfd_poll_ms": 100,        // 变频器采集节拍
    "temphum_poll_ms": 500,    // 温湿度采集节拍（物理更新 30Hz，500ms 够）
    "temphum_push_ms": 500,    // 温湿度推送节拍
    "vfd_enabled": true,
    "temphum_enabled": true,
    "unit_ids": { "vfd": 2, "temphum": 4 }
  },
  "analog": {
    "enabled": true,
    "host": "192.168.0.11",
    "port": 8234,
    "unit_id": 1,
    "channels": 8,
    "poll_ms": 200
  },
  "digital": {
    "enabled": true,
    "poll_ms": 200,
    "stale_ms": 5000,          // 超过即判数据失效
    "modules": [
      { "name": "数字量1", "host": "192.168.0.12", "port": 502,
        "unit_id": 1, "timeout_s": 2.0 },
      { "name": "数字量2", "host": "192.168.0.13", "port": 502,
        "unit_id": 1, "timeout_s": 2.0 }
    ]
  },
  "stale": { "vfd_ms": 5000, "temphum_ms": 5000, "digital_ms": 5000 },
  "runtime": { "run_mode": 0 }   // 0=手动 1=自动（服务自动维护）
}
```

**容错**：缺键用缺省值补齐（老配置加新设备不用重写整份）；
类型不符的键回退缺省值；未知键忽略。

### 4.1 数字量模块 `timeout_s` 要给足

该模块应答实测 **0.4~0.8s**（比其他设备慢一个数量级），
`timeout_s` 缺省 2.0s。设成 0.5s 会频繁超时。

### 4.2 账户库

同目录 `hsf_users.json`，首次运行自动创建：

```json
{ "version": 1, "users": [
  { "name": "admin", "role": 1, "iterations": 10000, "locked": false,
    "salt": "<32 hex>", "hash": "<64 hex>" },
  { "name": "root",  "role": 2, ... } ] }
```

- `role` 1 = 只读（admin），2 = 可控制（root）
- 口令**不落盘**，只存盐 + 10000 轮 HMAC 摘要
- 格式与 C 版账户库**互通**（可互换读取）
- 首次创建：`admin/admin`（只读）、`root/root`（可控制）——**上线前务必改**

改口令：删掉该条目后重启（会按缺省重建），或写个小脚本调
`UserStore.add_user()` + `save()`。

## 4.3 端口：改一处就够（`ports.py`）

**所有端口与串口缺省值都集中在 `hsfsrv/ports.py` 一个文件里。**

```python
# hsfsrv/ports.py
PY_SERVER_PORT = 6200      # ← 改这里：服务端监听端口
C_SERVER_PORT = 6100       # C 版端口（协议规格值，一般不动）
SERIAL_PORT_WINDOWS = "COM17"      # 桌面端缺省串口
SERIAL_PORT_POSIX = "/dev/ttyS3"   # 板端缺省串口
```

**改端口只改 `PY_SERVER_PORT` 一处**，下面这些地方全部自动跟随：
服务端监听、客户端缺省连接、命令行 `--help` 的显示、部署脚本。

> **客户端也有一份 `ports.py`**（`client_py/hsfsrv_client/ports.py`）——
> 两端是独立可部署目录，不能互相 import。**两份内容必须完全相同**，
> `tests/test_ports.py` 会逐字节比对，不一致直接测试失败，不会静静漂移。

### 为什么要和 C 版错开

现场经常需要「C 版服务端 + Python 版服务端」同时跑着做对比调试。
共用 6100 的后果：后启动的那个直接起不来（`address already in use`），
或者客户端连到错误的那一方却毫无察觉（两边协议完全兼容，数据却来自
不同实现）。

错开之后：
- 两套服务端可同机/同网并存
- 客户端用 `--port` 选边：`--port 6100` 连 C 版，`--port 6200` 连 Python 版
- 缺省走 6200（Python 版自己的端口）

**串口号也按平台自适应**：桌面端缺省 `COM17`（USB-485 转换器），
板端缺省 `/dev/ttyS3`（板载 UART）。这样同一份代码两边都能开箱即用。

## 5. 命令行

```
python3 -m hsfsrv [选项]

  --port N          临时改端口（本次生效，不写回配置）
  --config PATH     指定配置文件
  --no-serial       跳过 485 串口（只跑 TCP 设备）
  --no-io           跳过全部设备（只起登录/协议链路，供联调用）
  --diag            起服前先自检一轮设备连通性
  --no-auth         关闭登录（仅调试，生产禁用）
```

### 5.1 `--diag` 自检

不动配置文件、不写任何东西，只逐设备读一拍并打印：

```
[16:25:29] === 设备自检 ===
[16:25:29]   模拟量 192.168.0.11:8234：OK  8 路读取成功，CH1=3.996mA
[16:25:30]   数字量1 192.168.0.12:502：OK  DI=0x0000 DO=0x0000
[16:25:30]   数字量2 192.168.0.13:502：OK  DI=0x0000 DO=0x0000
[16:25:30] === 自检结束 ===
```

`CH1 ≈ 3.996mA` 是 4~20mA 量程的**活零点**（4.0mA），说明模块正常且量程正确。

## 6. 日常运维

### 6.1 看状态

```sh
ssh root@192.168.0.10 'systemctl status hsfserverpy'
ssh root@192.168.0.10 'ss -ltn | grep 6200'
```

### 6.2 看日志

```sh
ssh root@192.168.0.10 'journalctl -u hsfserverpy -f'          # 跟随
ssh root@192.168.0.10 'journalctl -u hsfserverpy -n 100'      # 最近100行
ssh root@192.168.0.10 'journalctl -u hsfserverpy --since "1 hour ago"'
```

关键日志行：

| 日志 | 含义 |
|---|---|
| `XLink 服务端就绪（端口 6200，鉴权开，遥测 100ms）` | 启动成功 |
| `设备：变频器(...)、模拟量(...)、数字量1(...)` | 装配了哪些设备 |
| `会话接入/断开 xxx（当前 N 路）` | 客户端连上/断开 |
| `登录成功（root，角色 2）` | 鉴权通过 |
| `<设备> 采集失败（连续 N 次）：...` | 该设备通讯中断 |
| `<设备> 恢复通讯（此前连续失败 N 次）` | 自动恢复 |
| `设备健康变化（seq=N，M 台）` | 有设备状态变更 |
| `点动心跳超时（Nms 无帧）→ 自动停机` | **看门狗动作了**（安全网生效） |

### 6.3 重启 / 停止

```sh
ssh root@192.168.0.10 'systemctl restart hsfserverpy'
ssh root@192.168.0.10 'systemctl stop hsfserverpy'
ssh root@192.168.0.10 'systemctl disable hsfserverpy'   # 取消开机自启
```

停止时服务会向所有客户端发 `Goodbye(ServerShutdown)`，对端立刻感知，
不用等 6 秒静默超时。

### 6.4 改配置后

改 `cfg/hsf_server_py.json` → `systemctl restart hsfserverpy`。
运行模式（手动/自动）除外：它由客户端命令改，服务自动写回配置。

## 7. 故障处理

### 7.1 端口被占

```
监听 6200 端口失败：[Errno 98] address already in use
```

查是谁占的：

```sh
ssh root@192.168.0.10 'ss -ltnp | grep 6200'
```

常见原因：手工跑过一份 `python3 -m hsfsrv` 没退干净。

### 7.2 串口打不开

```
变频器 采集失败（连续 1 次）：串口 /dev/ttyS3 打开失败：...
```

按顺序排查：

1. **demo 是否占着**：`systemctl is-active run_test.service` → 若是 active，
   它可能正以从站模式占 ttyS3（见 §3）
2. **权限**：`ls -l /dev/ttyS3` 应有 `crw-rw---- root dialout`
   （服务以 root 跑，通常不是权限问题）
3. **适配器在不在**：`ls /dev/ttyUSB*`（USB-485 是 ttyUSB，板载是 ttyS）
4. **参数对不对**：变频器 PD-00=115200、PD-02=2；温湿度 000BH=7(115200)、000AH=4

用 `--diag` 单独试，不启动服务：

```sh
ssh root@192.168.0.10 'cd /root/Desktop/XinYueC/hsf_server_py && python3 -m hsfsrv --diag --no-io'
```

（注意 `--no-io` 会跳过 TCP 设备，只测串口；不想要 `--no-io` 就去掉。）

### 7.2b 串口通但采不到数据（变频器/温湿度都是“--”）

**先分层，别改代码。** 用工具一次测掉前三层：

```sh
ssh root@192.168.0.10 'cd /root/Desktop/XinYueC/hsf_server_py &&     python3 tools/serial_probe.py --port /dev/ttyS3 --baud 115200,9600 --units 1,2,3,4,5'
```

输出会明确告诉你是哪一层：

| 工具输出 | 含义 | 处理 |
|---|---|---|
| `[FAIL] 打不开` | 串口被占 / 权限 / 节点不存在 | 看 §3（demo 占用）；`fuser -v /dev/ttyS3` 查占用 |
| `[OK]` 但`全部无应答` | **串口正常，总线上没有从站** | 查物理线（A/B 是否接到 ttyS3 端子）、从站电源、站号/波特率 |
| `[HIT]` 有应答 | 通信正常 | 把该站号/波特率写进配置 |

服务端日志也会区分这两个层次：

| 日志 | 含义 |
|---|---|
| `串口 /dev/ttyS3 不可用（5s 后重试）：上次打开失败` | **串口层**问题（被占/权限） |
| `无应答（0 字节）` | 串口通了，**从站不应答** |
| `从站失联`（健康条目的 text） | 同上，UI 侧的表述 |

> **RS485 半双工不会自发自收**。发出去收不到是正常的，
> 判断链路只能看有没有**从站**应答。

### 7.3 TCP 设备连不上 / 超时

```sh
# 从板子上逐层测
ping -c1 192.168.0.12
python3 -c "import socket; socket.create_connection(('192.168.0.12',502),2); print('open')"
```

**数字量模块的特殊性**：

- 对**频繁连断极敏感**——被打进数分钟不应答状态（连 ping 都不通）。
  本服务端是长连复用，且**读超时不断连**（只断真正的流错误），
  正常不会触发。
- 但如果你在旁边用别的工具反复连它，可能把它搞僵。此时等几分钟或断电重启。
- 应答慢（0.4~0.8s）是**正常**的，不是故障。

**模拟量模块**：只监听 8234（不是 502）。

#### ⚠ 数字量模块「TCP 能连但 Modbus 没应答」→ 先查是不是配成了主站

MT3A-IO1632 的 Web 配置里有 `ms` 字段：**1=主站 / 0=从站**。

配成主站时它**主动**往 `rip:rport` 推数据，**完全不响应** Modbus 从站请求。
现象极具迷惑性：

```
TCP 502 连接成功 → 立刻被关闭
或连上后发什么都是 0 应答，但耗时长达 800~1000ms
```

**秒判**（免登录读配置）：

```sh
curl http://192.168.0.12/config.js | grep -o '"ms":"[0-9]"'
# 输出 "ms":"1" 就是主站 —— 采不到是正常的，不是故障
```

**现场情况（2026-11-04）**：`.12` 与 `.13` 都是 `ms=1` 主站，
`.13` 正往本机 `192.168.0.243:8080` 推数据（被 `read_analog_gui.py` 接收）。

**要采就改成从站**：模块 Web 界面（`amx666/amx666`）把工作模式改「从站」
保存（约 2 秒软重启），之后本服务端即可正常读写。

> 服务端健康条目会直接写「无 Modbus 应答（检查是否配成主站 ms=1）」，
> 不再笼统报「模块失联」。

#### ⚠ 不要反复探测数字量模块

该模块对**连接 churn 极敏感**：短时间内反复连断会把它打进"数分钟不应答"
状态（TCP 能连、Modbus 无应答）。

实测教训：为一处排查在一分钟内发了十几次裸 socket 探测，之后 `.12`
连续 180 次采集失败，随后 `.13` 也受影响。

**判据**：`TCP 可连 + Modbus 无应答` = 模块被打僵，不是线路/服务端问题。
**处理**：停手等 3~5 分钟（多半自愈），必要时断电重启模块。
**预防**：只留一个采集者；不要用 `--diag` 反复跑。

### 7.4 数据一直是 `--`

按顺序查：

1. **设备健康**：客户端顶栏或 `CMD_DEVICE_HEALTH` 看该设备 `health` 字段
   - `3` = Offline（未装配/失联）
   - `2` = Stale（通讯在但数据过期，超过 `stale_ms`）
   - `0` = Ok
2. **配置里该设备是否 enabled**（`serial_enabled` 是总开关）
3. **是否订阅了对应主题**——不订阅收不到推送（快照请求不受影响）

### 7.5 控制被拒

| 应答 err | 原因 |
|---|---|
| `自动运行中：远程控制已被禁用…` | 运行模式是自动。用 root 发 `CMD_RUN_MODE {mode:0}` 切回手动 |
| `权限不足：控制命令需要 root 账户` | 当前登录的是 admin（只读） |
| `变频器未就绪` | 串口未装配或变频器失联 |
| `设备写入失败：...` | Modbus 写入失败，看具体原因 |

### 7.6 日志被刷爆

不会。采集失败做了两级抑制：连续失败时**只打第 1 条和每 60 条**
（约 1 分钟一条），采集周期退避到 1s。

### 7.7 内存/CPU

实测板上 CPU 占用很低（本服务是纯 asyncio + 低频轮询）。
若发现异常，先看：

```sh
ssh root@192.168.0.10 'top -b -n1 | head -15'
ssh root@192.168.0.10 'systemctl show hsfserverpy -p MemoryCurrent'
```

日志走 journald（已封顶 50M），不会无限增长。

ssh root@192.168.0.10 'systemctl disable --now hsfserverpy'
