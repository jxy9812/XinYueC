# 02 · 线协议规格

XLink v2 + BSON。本文**自包含**——照此可实现客户端，不需要看任何外部头文件。

> 所有多字节整数：**XLink 帧一律小端**，**Modbus 帧一律大端**。
> 字符串一律 UTF-8，**不含**结尾 NUL（长度由字段给出）。

---

## 1. TCP 连接

服务端监听 `0.0.0.0:<port>`。裸 TCP，无 TLS。

> **端口约定**：本 Python 版缺省 **6200**；C 版是 **6100**。
> 刻意错开，好让两套服务端同机并存做对比调试。
> 协议本身完全一致，客户端用 `--port` 选边即可。

建链后由客户端发 `Hello` 开始握手（服务端也会主动补发，见 §2.1）。

---

## 2. 帧格式

### 2.1 帧头（固定 16 字节，小端）

```
偏移  长度  字段        说明
 0     4   payloadLen  载荷字节数（不含帧头），须 <= 16384
 4     2   msgClass    消息类（见下表）
 6     2   msgCode     业务码
 8     4   requestId   Request/Response 关联 id；其余类填 0
12     1   dataType    载荷数据类型
13     3   reserved    发送方写 0，接收方不校验
16     N   payload     载荷
```

**msgClass**

| 值 | 名称 | 语义 |
|---|---|---|
| 0 | Session | 会话管理（Hello/心跳/登录/Goodbye） |
| 1 | Request | 请求，必须收到同 requestId 的 Response |
| 2 | Response | 应答，回带对端 requestId 与相同 msgCode |
| 3 | Publish | 推送，不等应答 |
| 4 | Subscribe | 订阅 |
| 5 | Unsubscribe | 退订 |
| 6 | File | 文件传输（本服务端**不支持**） |

**dataType**

| 值 | 名称 |
|---|---|
| 0 | Raw（未声明，原始字节） |
| 1 | Json（UTF-8 紧凑 JSON） |
| 2 | **Bson**（标准 BSON 文档） |

本服务端：业务载荷一律 `dataType=2`；会话帧一律 `dataType=0`。

### 2.2 版本与兼容

- 协议版本 `0x0200`（**主版本 2**）。
- 帧头宽度只在主版本升级时变化（1.x = 12 字节，2.x = 16 字节）。
- **主版本不符 → 直接断链**。理由：帧头宽度错了之后对方会按错误宽度切帧，
  从此整条字节流错位，它不报错、只把垃圾当帧头继续解析，表现为
  「连着但业务全乱」——不如立刻断。
- 次版本不校验（新增能力位/命令号属兼容扩展）。

### 2.3 载荷上限

`payloadLen > 16384` 即判协议违例（防畸形帧撑爆接收缓冲）。

## 3. 握手

### 3.1 Hello / HelloAck

`msgClass=0`，`msgCode` 1=Hello / 2=HelloAck，`payloadLen=4`：

```
偏移 长度 字段
 0    2   version     协议版本 0x0200
 2    2   capability  能力位
```

**能力位**

| 位 | 名称 | 含义 |
|---|---|---|
| 0x0001 | Zlib | 载荷压缩（本服务端**不支持**） |
| 0x0002 | Tls | 链路已跑在 TLS 上（本服务端不支持） |
| 0x0004 | Snapshot | HelloAck 带全量快照 |
| 0x0008 | RequestTimeout | 支持请求超时通知 |
| 0x0010 | **Auth** | 支持登录认证 |
| 0x0020 | FileTransfer | 支持文件传输 |

本服务端能力位固定 `0x0010`（仅 Auth）。双方取 `&` 作为交集。

### 3.2 握手流程

```
客户端                          服务端
   |  Hello(version, cap)  ------->|
   |<------- HelloAck(version,cap) |
   |                               |  交集含 Auth → 进入认证
   |  AuthRequest(username) ------>|
   |<------ AuthChallenge(...)     |
   |  AuthResponse(mac) ---------->|
   |<------ AuthResult(ok,role)    |  → Ready
```

- **对称**：任一方先发 Hello，对端回 HelloAck。
- 双方自动握手会各收到 Hello 与 HelloAck 两帧，**第二次不重复处理**
  （否则已进入的认证态会被打回 Ready，认证门控失效）。
- **连接建立后服务端会立即主动推一份设备健康快照**（无需订阅、无需先认证）。
  客户端可据此马上显示设备状态。

### 3.3 超时

| 超时 | 值 | 触发后的行为 |
|---|---|---|
| 握手 | 5s | 建链后不发 Hello → `Goodbye(Timeout)` + 断链 |
| 认证 | 5s | 进入 Authenticating 后不发认证帧 → `Goodbye(Timeout)` + 断链 |
| 静默 | 6s | 完全收不到任何帧 → 断链（不发 Goodbye） |
| 主动心跳 | 1s | Ready 态下自身静默达 1s → 发一帧 `Heartbeat` |

**客户端必须回心跳**（或发任意帧），否则 6s 后被判死。

## 4. 登录认证

迭代 HMAC-SHA256 挑战应答。口令与摘要都不上网。

### 4.1 AuthRequest（客户端 → 服务端，msgCode=5）

```
偏移 长度 字段
 0    1   nameLen  用户名 UTF-8 字节数（1..32）
 1    N   name
```

### 4.2 AuthChallenge（服务端 → 客户端，msgCode=6）

```
偏移 长度 字段
 0    1   method      1 = IteratedHmac
 1    1   saltLen     恒 16
 2    2   reserved    0
 4    4   iterations  迭代次数（10000）
 8   16   salt
24   32   nonce
```

### 4.3 AuthResponse（客户端 → 服务端，msgCode=7）

```
偏移 长度 字段
 0    1   method     回显挑战里的 method
 1    1   reserved   0
 2    2   len        摘要长度，必须 32
 4   32   response
```

### 4.4 AuthResult（服务端 → 客户端，msgCode=8）

```
偏移 长度 字段
 0    1   status     结果码
 1    1   role       角色（仅 status=0 有效）
 2    2   textLen
 4    N   text       失败原因文本
4+N  32   serverProof
```

**结果码**

| 值 | 含义 |
|---|---|
| 0 | Ok |
| 1 | BadUser（用户不存在，或 root 单会话被拒） |
| 2 | BadPassword |
| 3 | Locked |
| 4 | Rejected |
| 5 | NoCredential |
| 6 | Timeout |
| 7 | Protocol（畸形载荷） |

**角色**：1 = User（只读），2 = Admin（可控制）。

### 4.5 摘要算法（必须逐字节一致）

```
H        = HMAC-SHA256(password, salt)          第一轮
for i in 2..iterations:
    H    = HMAC-SHA256(password, H)             后续轮，key 恒为口令
response     = HMAC-SHA256(H, nonce)
serverProof  = HMAC-SHA256(H, nonce || 0x01)
```

- `0x01` 是域分离字节，防止 serverProof 与 response 撞用途。
- 服务端用**常量时间比较**校验 response。
- 挑战里的 nonce **一次性**：无论成败，用过即作废（防重放）。
- 失败累计 3 次即 `Goodbye(AuthFailed)` 断链；未达上限允许换用户/口令重试。

### 4.6 root 单会话策略

同一账户（`root`）只允许**一个**在线会话，第二个登录请求被拒为 `BadUser`。
admin 不限。目的：防并行修改互相覆盖。

## 5. 订阅与推送

### 5.1 Subscribe（msgClass=4）

`msgCode` = topicId 低 16 位，**载荷 = 完整 u32 topicId（小端，4 字节）**。

```
偏移 长度 字段
 0    4   topicId   完整主题号，须 >= 0x00010000
```

> **关键**：`msgCode` 只有 16 位，装不下 `0x0001NNNN` 的业务主题号。
> 解析侧**一律以载荷首 4 字节为准**；用 msgCode 会截成 `0x00NN`，
> 客户端按完整号匹配则整帧丢弃（表现为「发了但收不到」）。

**订阅即补发**：订阅成功后服务端立刻向该会话发一拍当前数据，
不用等周期推送。这也意味着「客户端切页时才订阅」的模式下，
页面一打开就有数据。

### 5.2 Unsubscribe（msgClass=5）

格式同上。未订阅的退订静默忽略（不发错）。

### 5.3 Publish（msgClass=3）

`msgCode` = topicId 低 16 位；**载荷首 4 字节 = 完整 topicId**，其后是业务载荷：

```
[ topicId u32 ][ 业务载荷 ]
```

业务载荷类型由 `dataType` 声明（本服务端恒 2 = BSON）。

### 5.4 主题一览

| 主题号 | 名称 | 节拍 | 载荷 |
|---|---|---|---|
| `0x00010001` | VFD_STATUS | 100ms | 变频器遥测（§6.1） |
| `0x00010002` | AI_STATUS | 100ms | 模拟量（§6.3） |
| `0x00010003` | TEMPHUM_STATUS | 500ms | 温湿度（§6.2） |
| `0x00010004` | FLOWMETER_STATUS | 200ms | 流量计（§7.6b） |
| `0x00010005` | DEVICE_HEALTH | **事件驱动** | 设备健康（§6.5） |
| `0x00010006` | DIGITAL_STATUS | 100ms | 数字量，逐模块一帧（§6.4） |
| `0x00010007` | **VALVE_STATUS** | 200ms | 电动球阀 6 路（§7b） |
| `0x00010009` | **TURBIDITY_STATUS** | 500ms | 浊度仪 2 台（§7c） |
| `0x0001000A` | **PUMP_STATUS** | 500ms | 进水泵（§7d） |

> `0x00010008` 是 VALVE_ALARM 事件主题（见 §7b.5），不占节拍槽位。
> 新增浊度/泵时刻意**跳过 8**，两个主题顺着往后排 9、10 —— 主题号是
> 手动登记的编号，跳过已占用的号比"挤进空档"更好查（对照代码常量即可）。

**DEVICE_HEALTH 是事件驱动**：只在设备状态**发生变化**时推，
外加「客户端首连」和「首次订阅」时各补发一份。不变化就完全不推。

**每台设备独立计时**：同一主题有几台设备就推几帧，各自的推送闸独立
（否则多设备共享计时，实际间隔会被台数除短）。

无人订阅时服务端不报错、静默跳过。

## 6. 命令与载荷

### 6.1 通用约定

- 请求：`msgClass=1`，`msgCode` = 命令号，`requestId` 自增。
- 应答：`msgClass=2`，回带**相同** `requestId` 与 `msgCode`。
- 失败应答统一包络：`{"ok": false, "err": "<中文原因>"}`
- **未知命令必须回答**（`ok=false, err="未知命令"`），不能静默——
  否则客户端空等到超时，观感是「服务端死了」。

### 6.2 命令表

| 命令号 | 名称 | 请求载荷 | 应答 | 权限 |
|---|---|---|---|---|
| `0x0101` | VFD_CONTROL | `{op,rev,hz,rpm,val,idx}` | 包络 | **root + 手动** |
| `0x0102` | VFD_SNAPSHOT | `{side}`（可空） | VFD 遥测 | 任意已登录 |
| `0x0103` | AI_SNAPSHOT | 空 | 模拟量快照 | 任意已登录 |
| `0x0104` | TEMPHUM_SNAPSHOT | `{side}`（可空） | 温湿度快照 | 任意已登录 |
| `0x0105` | RUN_MODE | 空=查询 / `{mode}`=设置 | `{ok,mode,auto}` | 设置需 root |
| `0x0106` | FLOWMETER_SNAPSHOT | `{side}` | 流量计快照 | 任意已登录 |
| `0x0107` | DEVICE_HEALTH | 空 | 健康快照 | 任意已登录 |
| `0x0108` | **DIGITAL_SNAPSHOT** | `{dev}`（可空=0） | 数字量快照 | 任意已登录 |
| `0x0109` | **DIGITAL_CONTROL** | `{dev,do,on}` 或 `{dev,mask}` | 包络 + `do` | **root + 手动** |
| `0x0110` | **VALVE_SNAPSHOT** | 空 | 6 路阀状态 | 任意已登录 |
| `0x0111` | **VALVE_CONTROL** | `{index,on}` | 包络 + 快照 | **root + 手动** |
| `0x0112` | **TURBIDITY_SNAPSHOT** | 空 | 浊度 2 台快照 | 任意已登录 |
| `0x0113` | **PUMP_SNAPSHOT** | 空 | 进水泵快照 | 任意已登录 |
| `0x0114` | **PUMP_CONTROL** | `{index,on}` | 包络 + 快照 | **root + 手动** |
| `0x0115` | **AUTO_CONTROL** | `{on}` | 包络 + `{mode,auto,autoRunning}` | **root + 自动**（启动限定） |
| `0x0116` | **CONFIG_GET** | 空 | `{ok,collect,storage,login,storageDbPath,storageStats}` | 任意已登录（只读） |
| `0x0117` | **CONFIG_SET** | `{section,…键}` | 包络（+ 该节回显） | **root（`PERM_ACCOUNT_ADMIN`）** |

加粗项是本 Python 版新增（C 版无数字量/流量计/浊度/泵设备）。

> **`0x0113` / `0x0114` 都要带 `index`**：泵现在是 1 台，但结构上留了多台
> 的位置（`HSF_PUMP_COUNT`）。命令里**从第一天就带泵号**，将来加到 2 台
> 不必改协议（少了这个字段就要做版本兼容）。服务端对越界泵号返回
> `ok=false, err="泵号越界（0~0）"`。

### 6.3 闸门顺序（实现方必须照此顺序）

```
1. 自动模式闸   → 自动运行中拒绝全部远程控制（连 root 也不放行）
2. 角色门禁     → 控制类命令需 role >= 2
3. 载荷解析
4. 设备就绪
```

**顺序不能反**：若先判角色，root 在自动模式下也能动设备，安全性就反了。
遥测与快照**不经过** 1~4，故自动模式下仍可正常监视。

自动模式的拒绝文本固定：
`"自动运行中：远程控制已被禁用（现场切换到手动后可用）"`

## 7. 载荷键表

### 7.1 变频器遥测（VFD_STATUS 推送 / VFD_SNAPSHOT 应答）

文档**恒含** `vm`（有效掩码，int64）。**只有 `vm` 里置位的键才出现**——
未提供的字段不写进文档，客户端按掩码显示 `--`。

| 位 | 键 | 类型 | 单位/换算 |
|---|---|---|---|
| 0 | `runState` | int32 | 见 §7.2 |
| 2 | `running` | bool | |
| 3 | `faulted` | bool | |
| 5 | `reverse` | bool | |
| 7 | `remote` | bool | 通讯在即 true |
| 8 | `jogActive` | bool | |
| 10 | `setFreqHz` | double | Hz（0x1000 百分比 × 最大频率） |
| 11 | `outputFreqHz` | double | Hz |
| 14 | `outputVoltageV` | double | V |
| 15 | `outputCurrentA` | double | A |
| 16 | `busVoltageV` | double | V |
| 18 | `outputPowerKw` | double | kW |
| 20 | `torquePercent` | double | % |
| 21 | `speedRpm` | double | **换算值**（由 outputFreqHz 按额定点算，见 §7.1b） |
| 39 | `faultCode` | uint32 | 故障码原值 |

另附加 `side`（int32，本服务端恒 0）。

**快照额外字段**（仅 `VFD_SNAPSHOT` 应答带，周期推送不带）：

| 键 | 类型 | 含义 |
|---|---|---|
| `ratedRpm` | double | 额定转速（rpm），Hz↔rpm 换算基准 |
| `ratedHz` | double | 额定频率（Hz） |

客户端用它们对齐"转速调速"的输入量程与换算，不必再写死一份。

### 7.1b 转速换算（2026-11-05 新增）

变频器**没有转速寄存器**，`speedRpm` 是派生量：

```
speedRpm = outputFreqHz / ratedHz × ratedRpm      （缺省 50Hz → 1440rpm）
```

**有效位与 outputFreqHz 同步**（位 21 与位 11 同条件）：只要读到输出频率，
转速就可给出。

> **这是估算值**：滑差随负载变化。界面必须标注"换算值"，不能当实测转速。
> 用**额定点**而不是极对数公式：极对数算的是同步转速（4 极=1500），
> 异步电机有滑差，实测 1440。

**转速给定**（`OP_SET_SPEED`）由服务端按同一式子反解成 Hz 再走频率通道；
超出最大频率时明确回 `ok=false`（不静默钳位）。

### 7.2 runState 取值

| 值 | 含义 |
|---|---|
| 0 | Unknown |
| 1 | Stopped |
| 2 | Ready |
| 3 | RunningForward |
| 4 | RunningReverse |
| 5/6 | JogForward / JogReverse |
| 7/8 | Accelerating / Decelerating |
| 9 | ConstantSpeed |
| 10/11/12 | DcBraking / FreeStopping / QuickStopping |
| 13 | **Fault**（有故障码时优先显示此值） |

### 7.3 变频器控制（VFD_CONTROL 请求载荷）

| 键 | 类型 | 用于 |
|---|---|---|
| `op` | int32 | **必填**，取值见 §7.4 |
| `rev` | bool | START / JOG 的方向 |
| `hz` | double | SET_FREQUENCY |
| `rpm` | double | SET_SPEED |
| `val` | double | SET_PID_TARGET |
| `idx` | int32 | SELECT_PRESET_SPEED |

### 7.4 op 取值

| op | 名称 | 本服务端支持 |
|---|---|---|
| 2 | SetFrequency | ✅ 超量程**钳位**而非失败 |
| 3 | SetSpeed | ❌ 明确拒绝（无转速给定口径） |
| 4 | Start | ✅ |
| 5 | Stop | ✅ 减速停机 |
| 6 | FreeStop | ✅ |
| 7 | QuickStop | ✅（复用减速停机，本机无独立快停命令字） |
| 8 | ResetFault | ✅ |
| 9 | Jog | ✅ **手持**，见 §7.5 |
| 10 | SelectPresetSpeed | ❌ 明确拒绝 |
| 13 | SetPidTarget | ❌ 明确拒绝 |
| **101** | **JogRelease** | ✅ 立即停机 |

不支持的动作回 `{"ok":false,"err":"<原因>"}`，**不静默成功**。

### 7.5 点动（Jog）的握手协议

点动是**手持式**操作，安全靠时序保证：

```
客户端按住 → 每 200ms 发一次 op=9
服务端     → 每收到一帧就刷新看门狗
客户端松手 → 发一次 op=101（JogRelease）→ 服务端立刻停机
```

- 服务端看门狗超时 **600ms**（= 3× 重发间隔）→ **自动停机**。
- 容忍连续丢 2 帧仍不停机（现场 485 偶发丢帧）。
- 超时 < 2× 重发间隔会「按住一顿一顿」；> 1s 则链路断了设备还在转。
- 链路断开/客户端崩溃 → 600ms 后设备自动停，不会失控。

**心跳判据不要求写入成功**：同一命令字反复下发时设备层可能把后续帧判
Busy，若此时不刷新看门狗，心跳就被误判丢失而误停机。

### 7.6 温湿度快照

```jsonc
{ "side": 0,
  "temp": 217,        // ×0.1℃（可为负）
  "hum": 648,         // ×0.1%RH
  "tempValid": true,
  "humValid": true,
  "staleMs": 5000 }
```

- **值键只在有效时出现**：客户端据此区分「0」与「无数据」。
- 温度 0.1℃ 精度、可负（`raw >= 10000` 时按 `-(raw-10000)×0.1` 解）。
- 服务端**不换算**成 ℃，客户端按 0.1 单位显示。

### 7.6b 流量计快照（`0x0106` 应答 / `0x00010004` 推送）

```jsonc
{ "side": 0,
  "flow": 36.412,          // 瞬时流量（单位见 flowUnit）
  "speed": 5.1512,         // 瞬时流速 m/s
  "forwardTotal": 0.224,   // 正向累积（数字+小数已拼好）
  "reverseTotal": 0.0,     // 反向累积
  "flowUnit": 5,           // 瞬时流量单位代码：5 = m³/h
  "totalUnit": 1,          // 累积总量单位代码：1 = m³
  "alarms": 0,             // 报警位图：0=上限 1=下限 2=空管 3=系统
  "valid": true,
  "staleMs": 5000 }
```

- **单位是代码不是字符串**：`flowUnit` / `totalUnit` 是**两张独立的码表**，
  客户端各自查表转文本。曾把累积单位填成瞬时表的邻居码 → 界面显示 `?`。
- **`alarms` 是位图**：`(alarms >> 0) & 1` = 上限报警，`>>1` 下限，
  `>>2` 空管，`>>3` 系统。
- **未在线时不写值键**（只有 `valid:false` + `staleMs`）：客户端据此显示
  `--` 而不是 `0` —— `0` 是"真的没流量"，含义完全不同。
- 累积量由服务端**拼装好**再下发（`U32 整数 + F32 小数`），客户端不做拼装。

### 7.7 模拟量快照

```jsonc
{ "n": 8,           // 通道数
  "v": 255,         // 有效位图（bit n = 通道 n）
  "r0": 995,        // 通道0 原始寄存器（毫伏）
  "u0": 3996,       // 通道0 微安（mA × 1000）
  ...
  "r7": 0, "u7": 0 }
```

- `r*` = 原始寄存器值（毫伏口径，排查真相用）
- `u*` = 微安（`mA × 1000`）。换算：`I(mA) = r / 249`
- 客户端按 `u*` 显示，按 `v` 位图判有效

**工程量换算字段**（2026-11-05 新增，仅配了 `analog.scales` 的通道才发）：

```jsonc
{ "e0": 499,        // 换算值 ×1000（定点整数，避免浮点在 BSON 上的精度争议）
  "eu0": "MPa",     // 单位
  "en0": "压差计",   // 通道名
  "ew0": "" }       // 越限说明（断线/超量程；空=正常，缺省不发）
```

换算口径：`p = (I - lowMa) / (highMa - lowMa) × fullScale`（缺省 4~20mA → 0~满量程）。
**换算在服务端做**：量程是现场标定参数，放客户端意味着每台机器各配一遍。

### 7.8 数字量快照（`0x0108` 应答 / `0x00010006` 推送）

```jsonc
{ "full": true,       // 全量帧标志，见下
  "dev": 0,           // 模块下标（0 = 192.168.0.12，1 = .13）
  "name": "数字量",
  "di": 5,            // DI 位图（bit n = 通道 n），0x0005 = 通道0 和 2 通
  "do": 0,            // DO 位图
  "count": 32,        // 该模块实际点数（单模块 16；聚合后 32）
  "valid": true,
  "staleMs": 5000,
  // ↓ 通道名：只发**被占用**的口（服务端由阀门点位映射推导，当前缺省点位）
  "din0": "电动球阀1 开到位", "din1": "电动球阀1 关到位",
  "don0": "电动球阀1 控制" }
```

- `count` **不写死**：客户端按它动态重建灯阵/按钮阵，位宽也随点数走
  （>16 点用 8 位十六进制）。
- 通道名键 `din<n>` / `don<n>`：**只发被占用的口**，未占用的不发，
  客户端只显示 `CH<n>`。名字的唯一事实源在服务端。

#### `full` 标志：全量帧 vs 增量帧

| 帧 | `full` | 带通道名 | 时机 |
|---|---|---|---|
| 全量帧 | `true` | 是 | 首连 / 订阅补发 / 快照应答 |
| 增量帧 | `false` | 否 | 周期推送（100ms） |

> **客户端务必只在"帧里带了名字"时才更新名字表，没有就沿用缓存。**
> 早期 Python 客户端每帧都整表重建名字表 ⇒ 全量帧给的 18 个名字被
> 200ms 后的增量帧擦成空 ⇒ 数字量页只剩 `CH<n>`、电动球阀语义名全丢。
> 现象像"服务端没发名字"，其实是客户端自己擦的（C 端
> `HsfLinkClient.c` 的 `if (full) {...}` 才是正确口径）。
>
> 更保守的做法（Python 客户端已采用）：**帧里没有名字键就一律不动名字表**，
> 连 `full=true` 但没带名字的帧也不擦 —— 少显示总比把接线信息弄丢好。

### 7.9 数字量控制（`0x0109` 请求载荷）

**单点写**：

```jsonc
{ "dev": 0, "do": 3, "on": true }
```

**整组写**（位图）：

```jsonc
{ "dev": 0, "mask": 165 }        // 0xA5 = 通道 0,2,5,7 通
```

也接受 `values`（长度 = 该模块点数的 0/1 数组）。

应答：`{"ok":true,"dev":0,"do":165}` —— `do` 是写后的实际位图。
越界（`do` 不在 `0~channels-1`、`dev` 越界）回 `ok=false`。

### 7.10 运行模式（`0x0105`）

**查询**（空载荷或 `{}`）：

```jsonc
{ "ok": true, "mode": 0, "auto": false }
```

**设置**：载荷 `{"mode": 0|1}`，需 root。0 = 手动，1 = 自动。
应答同上，**另带 `autoRunning`**：

```jsonc
{ "ok": true, "mode": 1, "auto": true, "autoRunning": false }
```

非法值回 `ok=false, err="非法模式值"`。

模式**持久化**（重启保持），服务端写回 `cfg/hsf_server_py.json` 的 `runtime.run_mode`。

#### ⚠ `auto` 与 `autoRunning` 是两件事（2026-11-05 安全订正）

| 键 | 回答的问题 | 谁决定 |
|---|---|---|
| `auto` | 现在是不是**自动模式** | 人切模式（`0x0105`） |
| `autoRunning` | 自动**控制器**有没有真的在跑 | 人按「启动自动运行」（`0x0115`） |

**切到自动模式 ≠ 开始自动运行。** 前者只是**授权**（并禁止远程控制），
控制器仍然停着；要真正驱动设备必须再下发 `CMD_AUTO_CONTROL on=1`。

> **这条是现场安全反馈定的**：初版把两者合成一个动作，切到自动模式控制器
> 立刻启动 —— 操作员只想切个显示状态，设备却开始动。原话：
> 「默认应该是停止状态，不然太危险了」。

**服务端重启后控制器一律为停止状态**（即使配置里是自动模式）：断电重启、
systemd 拉起、升级重启都不该让设备自己动起来。

**单向强制**：退出自动模式时服务端**强制停止**控制器。手动模式下自动逻辑
还在跑 = 设备被偷偷驱动，属硬性安全问题，故不设"确认"也不给绕过路径。

| 组合 | 是否允许 | 说明 |
|---|---|---|
| 手动 + 停 | ✅ | 开机缺省 |
| 自动 + 停 | ✅ | **切模式后的默认态**（已授权未启动） |
| 自动 + 跑 | ✅ | 真正在自动运行 |
| 手动 + 跑 | ❌ **禁止** | 退自动时强制停 |

### 7.10b 自动运行控制（`0x0115`）

| 项 | 值 |
|---|---|
| 载荷 | `{"on": true/false}` |
| 权限 | **root**（启动还要求处于自动模式） |
| 应答 | `{ok, mode, auto, autoRunning}`（与 `0x0105` 同构） |

**闸门顺序**：

1. 角色门禁（`role >= 2`）—— 停机也要求 root（运行决策不开放只读）
2. **启动**要求 `auto=true`，否则回
   `err="当前是手动模式：请先切到自动模式，再启动自动运行"`
3. **停止永远允许**（停机类动作不该被任何闸门挡住）

**幂等**：已在目标状态再请求照样回 `ok=true`（不报错）。

**服务端没有"自动运行"的独立推送主题**：`autoRunning` 随
`0x0105`（查询/设置）与 `0x0115`（启停）的应答下发。客户端切页/重连时
调一次 `0x0105` 即可对齐（模式是低频状态，不值得开一条推送节拍）。

### 7.10c 远端配置（`0x0116` 读取 / `0x0117` 写入）

`section` ∈ `collect` / `storage` / `login`；键名与 C 侧 `HSF_CFGK_*`
逐字一致（两端客户端可互换）。

**`collect` 节（设备开关 / 轮询周期）**

| 键 | 类型 | 语义 |
|---|---|---|
| `vfdEnabled` | bool | 变频器（搅拌泵）采集开关 |
| `temphumEnabled` | bool | 温湿度采集开关 |
| `flowmeterEnabled` | bool | 电磁流量计采集开关 |
| `turbidityEnabled` | bool | 两台浊度的**共同缺省**（旧键，兼容） |
| `turbidity1Enabled` | bool | **浊度仪1（站1）独立开关**（2026-11-10） |
| `turbidity2Enabled` | bool | **浊度仪2（站3）独立开关**（2026-11-10） |
| `analogEnabled` / `digitalEnabled` | bool | 模拟量/数字量模块采集开关 |
| `vfdPollMs` / `temphumPollMs` | int | 周期（毫秒，夹 `50~60000`） |
| `turbidityPollMs` | int | 两台浊度的**共同缺省**（旧键，兼容） |
| `turbidity1PollMs` / `turbidity2PollMs` | int | 逐台周期（毫秒，夹 `50~60000`） |
| `flowmeterPollMs` / `analogPollMs` / `digitalPollMs` | int | 周期（毫秒，夹 `50~60000`） |

**逐台浊度规则（2026-11-10）**

- 回落链：`turbidityNEnabled → turbidityEnabled → 编译期缺省`；
  旧配置/旧客户端只发共同键时两台一起开关（向后兼容）。
- **同一条 SET 里既有逐台键又有共同键时以逐台为准**：新客户端为兼容旧
  服务端会把共同键当「任一启用」一起发；若按键逐个扇出，会把刚停的台
  又盖回开（客户端 B3c 实测红后根修）。
- 停一台只停该从站轮询，另一台照采；周期与开关都是运行期生效
  （开关变化会重启采集任务，周期下一拍生效）。

**`login` 节（账户策略）**

| 节 | 键 | 语义 |
|---|---|---|
| `login` | `loginAllowAnonymous` | bool，允许匿名（只读）登录；缺省 `false` |
| `login` | `loginAllowConcurrent` | bool，同一账户允许多会话在线；缺省 `false`（= root 单会话） |
| `login` | `loginMaxSessions` | int，会话总数上限，`0`=不限（服务端夹到 `0~256`）；缺省 `8` |

**权限**：GET 不设角色门禁（只读回显不涉密）；SET 需管理员
（`PERM_ACCOUNT_ADMIN`，即 root），与 `collect` / `storage` 节同一道闸。

**生效范围**：写入只对**下一次登录**生效，**存量会话不受影响**——把同账
并发关掉不会踢掉已在线的会话。关闭并发时沿用 §4.6 的「root 单会话」
保护（第二个 root 登录被拒为 `BadUser`；admin 只读不限）。

**落点**：Python 服务端写 `config.json` 的 `login` 节（`allow_anonymous`
/ `allow_concurrent` / `max_sessions`）；C 服务端同名键落盘
`bin/cfg/hsf_login_policy.json`。压测脚本 `test_stress_reconnect.py`
就是经这条通道打开并发、收尾恢复原值（与设置页「登录策略（账号）」
同链路，2026-11-08）。

### 7.11 设备健康（`0x0107` 应答 / `0x00010005` 推送）

```jsonc
{ "devCount": 5,
  "seq": 3,                // 变化序号，单调递增
  "ts": 1730000000000,     // 墙钟毫秒
  "d0_name": "变频器", "d0_kind": 0, "d0_side": 0, "d0_health": 0,
  "d0_error": 0, "d0_online": true, "d0_runState": 3,
  "d1_name": "温湿度", "d1_kind": 1, ...
}
```

`d{i}_text`（错误说明）只在非空时出现。

**`d{i}_addr`（连接地址，2026-11-05 新增）** 只在非空时出现，是**给人看的
展示串**（不是机器可解析的格式）：

| 设备 | 示例（缺省接线；以 cfg 为准） |
|---|---|
| 485 从站（搅拌泵/温湿度/流量计/浊度仪） | `COM17 · 115200 · 站 2` |
| Modbus TCP（模拟量/数字量模块） | `192.168.0.13:502` |
| 挂在模块 DO 上的设备（进水泵） | `192.168.0.13:502 · DO6` |
| 挂在模块 DO 段的设备（电动球阀组） | `192.168.0.13:502 · DO0~DO5` |

> **485 必须三项都写**：口接错、波特率不匹配、站号撞车三种故障的现象**都是**
> "通讯不上"，只写其中一两项根本判不出来。
>
> **泵/阀不写站号**：它们没有独立通讯口（线圈接在数字量模块的 DO 上），
> 报站号会让人去总线上找一个不存在的从站；报模块地址 + DO 口才对应得上
> 现场用万用表量的那一路。
>
> **地址变化会 bump `seq`**：健康是"变化才推"，`addr` 纳入变化比对；
> 否则改了配置里的 IP/站号后服务端认为没变化，界面会一直显示旧地址 ——
> 而改这些参数恰恰是在排"连不上"的时候。

**kind**

| 值 | 含义 |
|---|---|
| 0 | Vfd |
| 1 | TempHum |
| 2 | FlowMeter |
| 3 | AnalogIo |
| 4 | Bus |
| 5 | **DigitalIo**（本版新增） |
| 6 | **Valve**（电动球阀组） |
| 7 | **Water**（水质仪表：浊度仪等） |

> **[实锅 2026-11-05]** 浊度仪初版复用了 `kind=1`（TempHum），首页设备表的
> "类型"列把两台浊度仪显示成**温湿度** —— 数据对，但类别完全误导（现场会
> 以为那是电箱里的温湿度变送器）。为此新增 `7 = Water`。
> **教训**：`kind` 是给操作员看"这是什么设备"的，不是内部实现细节；
> 给新设备复用一个不相关的既有值，等于在界面上撒谎。

**health**

| 值 | 含义 |
|---|---|
| 0 | Ok |
| 1 | Warning |
| 2 | Stale（通讯在但数据过期） |
| 3 | Offline（失联/未装配） |
| 4 | Fault（设备报故障） |

> 客户端若遇到未知 `kind`（比如老客户端见到 5），应按「未知设备」降级显示，
> 不要因为不认识就丢弃整条健康包——其余条目是有效的。

## 7b. 电动球阀（6 路）

> 2026-11-10 现场口径：阀名统一 **电动球阀1~6**、组名 **电动球阀组**
> （「电磁阀」旧称作废；现场就是 6 台同规格电动球阀，没有加药/排气等
> 功能差别）。点位：第 i 路 DO=i、开到位 DI=2i、关到位 DI=2i+1。

### 7b.1 命令

| 命令号 | 名称 | 请求载荷 | 应答 |
|---|---|---|---|
| `0x0110` | VALVE_SNAPSHOT | 空 | 6 路状态 BSON |
| `0x0111` | VALVE_CONTROL | `{"index":0..5, "on":true/false}` | 包络 + 最新快照 |

**权限**：快照任何已登录角色可读；控制需 **root + 手动模式**（与变频器/DO 同一套闸门）。

推送主题 `0x00010007`（VALVE_STATUS），200ms 一拍。

### 7b.2 载荷键表

```
{ "count": 6,
  "v0_name": "电动球阀1", "v0_openCmd": false, "v0_openFb": false,
  "v0_closeFb": false,  "v0_state": 0,       "v0_ready": true,
  "v0_valid": true,     "v0_text": "无到位反馈（检查行程开关接线）",
  "v1_name": "电动球阀2", ... }
```

每路字段以 `v{index}_` 前缀（与设备健康的 `dN_` 同一风格）。

| 键 | 类型 | 含义 |
|---|---|---|
| `count` | int | 路数（恒 6） |
| `vN_name` | utf8 | 阀名 |
| `vN_openCmd` | bool | **最近一次下发的命令**（意图，不是结果） |
| `vN_openFb` | bool | 开到位反馈 |
| `vN_closeFb` | bool | 关到位反馈 |
| `vN_state` | int | 阀状态（见下表） |
| `vN_ready` | bool | 该路点位是否已配置 |
| `vN_valid` | bool | 反馈数据是否新鲜 |
| `vN_text` | utf8 | 说明（故障原因/无反馈提示，可能不出现） |
| `vN_cmdResult` | utf8 | **控制命令的处置结果**（只出现在控制应答里；见 §7b.4） |

### 7b.3 控制应答的 `cmdResult`（客户端必须区分）

服务端对"重复点同一侧"有三种不同处置。只回 `ok=true` 的话界面区分不了
"真的动了"和"本来就在那儿"，用户会以为重复点击也生效了 —— 与事实相反。

| 值 | 含义 | 是否写 DO | 是否重置 20s 计时 |
|---|---|---|---|
| `issued` | 首次命令 | 是 | 是 |
| `repeated` | 动作中，同目标的重复请求 | 是（防上次写丢） | **否** |
| `reversed` | 反向（开→关 / 关→开） | 是 | 是（新动作） |
| `ignored` | 已到位且命令与当前位置一致 | **否**（幂等） | 否 |
| `external` | 检测到有人绕过阀接口直接写了 DO | — | 是（接管为新动作） |

> **`repeated` 不重置计时是安全要求**：超时告警靠 `now - cmd_at_ms` 判。
> 若每次点击都重置，用户每 20s 内点一次同侧就能让卡阀**永远不报警**
> （实测连点 8 次，0 告警）。

客户端对照文案（两端同口径，见 `valves.VALVE_CMD_TEXT` / 客户端同名常量）：

```
issued   → 命令已下发
repeated → 动作中，重复命令不重置计时
reversed → 已反向（重新计时）
ignored  → 已在目标位置，无需动作
external → 输出被外部改动，已接管
```

### 7b.4 状态机（**由反馈推导，不看命令回显**）

| 值 | 状态 | 判据 |
|---|---|---|
| 0 | 状态未知 | 两个反馈都为 0，且**从未下过命令**（多为行程开关没接） |
| 1 | 已关 | `closeFb=1, openFb=0` |
| 2 | 已开 | `openFb=1, closeFb=0` |
| 3 | 动作中 | 两个反馈都为 0，且**刚下过命令**、在超时窗口内 |
| 4 | 故障 | 两个反馈**同时为 1**（接线/阀体故障），或动作超时未到位 |

> **为什么 0 和 3 要分开**：两个到位都为 0 有两种完全不同的原因——
> 真的在动作（几秒），还是行程开关没接（永远等不到）。
> 混成一个“动作中”会让现场看到 6 个阀永远在动，不知道该查什么。

**动作超时**：从下发命令起超过 `valves.move_timeout_ms`（**缺省 20s**，
现场一个阀满开→满关约 10s，两倍余量）仍未到位 → 判故障。
按**目标位置**判到位（不是"两个都为 0 就算动作中"）。

### 7b.5 告警帧（同一主题上的事件帧，2026-11-05 新增）

超时/互斥故障是**事件**，服务端在 `0x00010007` 上另发一帧，键空间独立：

```jsonc
{ "ac": 1,                     // 告警条数（**有该键=告警帧**，无 count/v{i}_*）
  "a0_vi": 0,                  // 阀号
  "a0_vn": "电动球阀1",         // 阀名
  "a0_k": 1,                   // 类型：1=超时 2=互斥冲突 3=已恢复
  "a0_t": "动作超时未到位（20s）——全程无任何到位信号，优先查询行程开关接线",
  "a0_at": 123456,             // 发生时刻（单调毫秒）
  "a0_to": 20.0 }              // 超时秒数
```

| 键 | 类型 | 含义 |
|---|---|---|
| `ac` | int | 本帧告警条数（**必须用它判帧类型**） |
| `aN_vi` | int | 阀号 0~5 |
| `aN_vn` | utf8 | 阀名 |
| `aN_k` | int | `1`=超时 `2`=互斥冲突 `3`=已恢复 |
| `aN_t` | utf8 | 告警文字（服务端已写好，客户端直接显示） |
| `aN_at` | int64 | 发生时刻（单调毫秒） |
| `aN_to` | float | 超时秒数 |

**客户端解析必须先认 `ac`**：告警帧没有 `count` 也没有 `v{i}_*`，若照状态帧
解析会把点位表清空 —— 界面上的阀会瞬间全变"未配置"再恢复，闪一下。

**一次动作只告警一次**：判据每拍都成立，服务端用 `timeout_reported` /
`conflict_reported` 标志位去重；到位后发一条 `k=3` 消警。

**只推订阅了本主题的会话**（与周期推送同口径，不额外广播）。

## 7c. 浊度仪（2 台）

两台与电磁流量计**共用一路 485**，只是站号不同（现场站号 1 与 3）。
共用一个串口 ⇒ 服务端串行轮询，客户端只看合并后的一帧。

### 7c.1 命令与主题

| 命令号 | 名称 | 请求载荷 | 应答 |
|---|---|---|---|
| `0x0112` | TURBIDITY_SNAPSHOT | 空 | 2 台浊度 BSON |

推送主题 `0x00010009`（TURBIDITY_STATUS），**500ms** 一拍。
快照任何已登录角色可读；**浊度是只读设备，没有控制命令**。

### 7c.2 载荷键表

```jsonc
{ "count": 2,
  "v0_name": "浊度仪1", "v0_online": true, "v0_ntu": 229, "v0_raw": 1074966364,
  "v1_name": "浊度仪3", "v1_online": true, "v1_ntu": 5,  "v1_raw": 1027438446,
  "v1_temp": 1925,
  "staleMs": 5000 }
```

| 键 | 类型 | 含义 |
|---|---|---|
| `count` | int | 台数（恒 2，由配置 `turbidity.unitIds` 长度决定） |
| `vN_name` | utf8 | 仪器名（服务端给，客户端不猜"原水/出水"） |
| `vN_online` | bool | 该台本轮是否读到数据（停采的台恒 `false`） |
| `vN_ntu` | int | **浊度 ×100**（定点整数，÷100 得 NTU） |
| `vN_raw` | int | 原始 32 位**位模式**（排查换算口径用，不是工程值） |
| `vN_temp` | int | **水温 ×100 ℃**，仅带温度机型有这个键（见 §7c.4） |
| `staleMs` | int | 数据超期阈值 |

**`ntu` 发 ×100 的整数**：与模拟量工程值同一口径（定点整数），避免浮点在
BSON 上的精度争议。客户端 `÷100` 后按两位小数显示。

**`temp` 缺键 ≠ 0℃**：两台仪器型号不同，站1（WZT-701A）没有温度通道，
帧里就**不出现** `v0_temp`；客户端据此显示 `--`，不能当 0℃（见 §7c.4）。

**`raw` 必须一起发**：换算口径一旦不对，`raw` 是唯一能反推真相的量。
调试时先看 `raw` 是不是一个像浮点的位模式（比如 `0x40xxxxxx` ≈ 2 NTU
量级），再判字序/字节序哪一项错了。

**离线那台不写 `ntu`/`raw`**（只给 `online:false`）：客户端据此显示 `--`
而不是 `0.00` —— 自来水浊度 0.00 是"极干净"，含义完全不同。

### 7c.3 寄存器口径（2026-11-09 真机实测，**已确认**）

两台型号/字节序/读取数都不同（实测总表 §5.3/§7）：

| 台 | 站号 | 型号 | 读取 | 字节序 | 温度 |
|---|---|---|---|---|---|
| 浊度仪1 | 1 | WZT-701A | FC03 `0x0000`×**2** | **CDAB** | 无 |
| 浊度仪2 | 3 | ZHEYI-5100ZDY | FC03 `0x0000`×**4** | **DCBA** | 有（后两字） |

- 站1：两字按低字在前拼成 32 位位模式，再按 IEEE754 单精度解释，
  **不除以 100**。手册示例帧 `D7 0A 41 1F → 9.99 NTU` 可验算。
- 站3：4 字节整字节反序（小端 float32）；一帧 4 字 = 浊度 + 水温
  **同刻快照**（分两帧读会有非同刻误差）。
- 站3 用 FC04 请求时**应答功能码恒回 0x03**，故统一用 FC03。
- 两台共用一条 485 ⇒ 串行轮询；站1 在站5 的 49 字节长帧之后需要
  ≥100~125 ms 空闲（工程取 200 ms），站3 不敏感。

口径实现为 `devices.TurbidityMeter` 的构造旋钮
（`byte_order` / `read_count` / `temperature`），站号与旋钮都走配置
（`turbidity.unitIds` / `turbidity_byte_orders` / `turbidity_read_counts`），
协议层不写死。

### 7c.4 温度（站3 独有）

站3（浙仪 ZHEYI-5100ZDY）一帧 4 寄存器：前两字浊度、后两字水温。
设备层随逐台数据下发 `vN_temp`（℃×100）；主页浊度卡与水质监测页都显示。
站1 没有温度通道 ⇒ **缺键**，客户端显示 `--`（不是 0℃）。
2026-11-10 起温度进推送帧（旧口径「只进设备层日志」作废）。

### 7c.5 逐台采集配置（2026-11-10）

两台是**两台独立设备**：采集开关与周期逐台（配置节键见 §7.10c）：

- `turbidity1Enabled` / `turbidity2Enabled`：逐台开关；旧的
  `turbidityEnabled` 降为共同缺省（缺逐台键时回落它）。
- `turbidity1PollMs` / `turbidity2PollMs`：逐台周期；旧 `turbidityPollMs`
  作两台共同缺省。
- 停一台只停该从站轮询，另一台照采；Python 健康条目报「已停用」，
  C 端由数据新鲜度推导显示过期/离线。

## 7d. 进水泵（1 台，只有输出）

进水泵的接触器线圈接在**数字量模块上 6 路阀的下一个 DO**（缺省接线：
阀占 DO0..DO5，泵占 **DO6**；以 `pump_items` 配置为准）。

### 7d.1 命令与主题

| 命令号 | 名称 | 请求载荷 | 应答 |
|---|---|---|---|
| `0x0113` | PUMP_SNAPSHOT | 空 | 泵状态 BSON |
| `0x0114` | PUMP_CONTROL | `{"index":0, "on":true/false}` | 包络 + 最新快照 |

推送主题 `0x0001000A`（PUMP_STATUS），**500ms** 一拍。
控制需 **root + 手动模式**（与阀/DO 同一套闸门）。

### 7d.2 载荷键表

```jsonc
{ "count": 1,
  "v0_name": "进水泵", "v0_on": false, "v0_ready": true,
  "v0_valid": true, "staleMs": 5000 }
```

| 键 | 类型 | 含义 |
|---|---|---|
| `count` | int | 台数（当前 1） |
| `vN_name` | utf8 | 泵名（**同时也写进数字量 DO6 的通道名**，两处同源；DO 口以 cfg 为准） |
| `vN_on` | bool | **输出状态**（DO 回显），**不是"泵在转"** |
| `vN_ready` | bool | 点位是否配齐（module + do） |
| `vN_valid` | bool | 本拍回显是否有效（模块数据新鲜） |
| `vN_text` | utf8 | 不可用原因（可能不出现） |

### 7d.3 ⚠ `on` 是输出状态，不是运行反馈

现场泵**只有接触器输出，没有任何运行反馈点**。所以：

- `vN_on=true` 只代表"输出是开着的"，**不代表泵确实在转**（可能跳闸、
  可能机械卡死、可能接触器烧了）
- 服务端**不会**因"启动后长时间没反应"报警 —— 没有反馈就没有独立的
  真相源，硬造一个超时告警等于撒谎（对比：阀有 2 个到位开关，所以有 20s 超时）
- 界面上必须写明这一点。客户端水质页的泵卡带固定说明行：
  「现场仅有接触器输出、无运行反馈点：此处显示的是输出命令状态，
  不代表泵确实在转。」

要真正监视泵，得现场加一个运行反馈点（接触器辅助触点 / 流量开关），
那时再扩展载荷键（比如 `vN_runFb`）与告警判据。

### 7d.4 幂等与外部改动

- **幂等**：命令值 == 当前回显值 ⇒ 不写 DO，直接回 `ok=true`。
  这与阀的 `ignored` 同一口径（避免无谓的继电器动作与总线占用）。
- **外部改动会被接管**：从数字量页直写泵的 DO（缺省 DO6，绕过泵接口）时，服务端的
  `poll()` 比对模块实际 DO 与已知值，不一致就以**实际输出为准**并记日志
  —— 界面显示一个与实际相反的状态是最危险的。

## 8. 错误处理速查

| 现象 | 原因 |
|---|---|
| 连上就断 | 版本主号不符 / 帧头畸形 |
| 发请求无应答 | 命令号未知但服务端没回（不符规范）或 requestId 没对上 |
| 收不到推送 | 没订阅该主题 / 主题号用了 msgCode 而非载荷 u32 |
| 6s 后断链 | 客户端没回心跳 |
| 登不上 | 用户名/口令错；或 root 已有在线会话 |
| 控制被拒 | 看 §6.3 闸门顺序 |
| 界面点数只有 16 | 客户端没用快照的 `count` 键（应动态重建，见 §7.8） |
| 阀告警把点位清空 | 客户端没先判 `ac` 键就按状态帧解析（见 §7b.4） |
| 浊度显示 0.00 而不是 `--` | 离线时段也写了 `ntu` 键（离线只给 `online:false`，见 §7c.2） |
| 浊度值离谱（×100 或 ×0.01） | 换算口径不符真机（见 §7c.3，先看 `raw` 反推） |
| 泵显示"运行"但实际没转 | `on` 是输出状态不是运行反馈（见 §7d.3），现场需加反馈点 |
