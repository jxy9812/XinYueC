## 1. M512/M513 变频器（Modbus-RTU 从站）

### 1.1 链路参数

| 项 | 值 | 备注 |
|---|---|---|
| 串口 | `/dev/ttyS3` | 与温湿度共用同一条 485 |
| 波特率 | **115200** 8N1 | 面板 PD-00 低 4 位 = 9 |
| 从站号 | **2** | 面板 PD-02 |
| 单帧超时 | 400ms | |
| 重试 | 1 次 | **≥1 才能把滞留的错误帧冲掉** |

### 1.2 读组（FC03）

地址天然分散且**跨组不能一帧读**——0x1000（通讯设定值）与 0x1001~0x1020
（运行参数）地址相邻但分属手册两条条目，一帧同时读会被**静默返回全 0**。

| 起始 | 数量 | 内容 |
|---|---|---|
| `0x1000` | 9 | 给定/频率/母线/电压/电流/功率/转矩/DI/DO |
| `0x1009` | 3 | AI1~AI3 |
| `0x1010` | 4 | PID设定/反馈/PLC阶段/脉冲频率 |
| `0x1019` | 3 | 线速度/上电时间/运行时间 |
| `0x101F` | 2 | 主频率X/辅频率Y |
| `0x3000` | **1** | 运行状态（数量必须 = 1） |
| `0x8000` | **1** | 故障码（数量必须 = 1） |

> **0x1000 起连读的坑**：实测「从 0x1001 起连读会被静默返回全 0」，
> 必须把 0x1000 一并纳入读窗才能取到有效值。

### 1.3 单位换算（**逐点实机标定，勿按手册推**）

| 地址 | 名称 | 单位 | 换算 | 备注 |
|---|---|---|---|---|
| `0x1000` | 通讯设定值 | ±10000 = ±100.00% | ×最大频率/10000 | **int16 补码** |
| `0x1001` | 运行频率 | **0.01 Hz** | ÷100 | ⚠ 与 U0.00 的 ÷10 **不同口径** |
| `0x1002` | 母线电压 | 0.1 V | ÷10 | |
| `0x1003` | 输出电压 | **1 V** | ÷1 | |
| `0x1004` | 输出电流 | 0.01 A | ÷100 | 受 Pd.06 影响 |
| `0x1005` | 输出功率 | 0.1 kW | ÷10 | |
| `0x1006` | 输出转矩 | 0.1 % | ÷10 | |
| `0x1007` | DI 输入状态 | 位图 | — | |
| `0x1008` | DO 输出状态 | 位图 | — | |
| `0x3000` | 运行状态字 | 枚举 | 1=正转 2=反转 3=停机 | |
| `0x8000` | 故障码 | 枚举 | 0=无故障 | 附录1 通信故障表 |

**两个最容易搞错的点**：

1. **0x1001 是 0.01Hz（÷100）**，不是 0.1Hz。历史误设 ÷10 曾让运行频率
   显示放大 10 倍（15Hz 报成 150Hz）。
2. **0x1000 是相对最大频率 P0.10 的百分比**，不是绝对 Hz：
   ```
   raw = round(Hz / P0.10 × 10000)      Hz = raw / 10000 × P0.10
   ```
   P0.10 读不到时按 50Hz 兜底。

#### ⚠ 0x3000 只有 3 个值，加速/减速/停机要靠推导（2026-11-06）

状态字**硬件口径就是 1=正转 / 2=反转 / 3=停机**，厂商不报"加速中/
减速中/正在停机"这些细分。用户要求界面显示这些过渡态，只能由服务端按
频率关系推导 —— 见 `devices.py::VfdM512._derive_phase()`。

**推导判据（优先级从高到低）**

| 条件 | 判定 |
|---|---|
| 故障码 ≠ 0 | `RUN_FAULT`（盖过一切） |
| 已发停止命令 且 输出 > 死区 | `RUN_DECELERATING`（**正在停机**） |
| 未运行 且 输出 > 死区 | `RUN_DECELERATING`（停机过程） |
| 未运行 且 输出 ≈ 0 | `RUN_STOPPED` |
| 设定 > 输出 + 死区 | `RUN_ACCELERATING` |
| 设定 < 输出 − 死区 | `RUN_DECELERATING`（降给定） |
| 已到位 | `RUN_RUNNING_FORWARD` / `RUN_RUNNING_REVERSE` |

**死区 `PHASE_DEADBAND_HZ = 0.15`**：输出是 0.01Hz 分辨率、给定按百分比
换算，两者永远差一点点。不留死区会让"恒速运行"永远被判成加速/减速，
状态字一直闪。

**★ 停机绝不能按「设定 vs 输出」判**：真机实测（板端 2026-11-06），
点停止后变频器的 **0x1000 仍保留旧给定**（48.6Hz），而输出在斜坡下降
⇒ `设定 > 输出` ⇒ 按差值会判成**"加速中"**，实测停机全程显示"加速中"，
完全反了。故停机必须靠"已发停止命令"标记（`_stop_requested`）判定。

> 附带现象：停机后界面会看到"停机 + 输出 0.00Hz + 设定频率 48.61Hz"。
> 那个设定频率是**变频器保留的旧给定**，不是故障。

**两种"减速"语义不同**，对外必须分开（`client_py/model.py`）：

| 场景 | 文案 | 是否算运行（可继续调速） |
|---|---|---|
| 运行中把给定调低 | 「减速中」 | **是** |
| 已发停止命令（斜坡下降） | 「正在停机」 | **否** |

`is_running()` 的判据随之细化：`RUN_DECELERATING` 要走
`_stopping_intent()` 再分一次，不能一律当成运行态 —— 否则停机过程中
还能在线调速，语义混乱；也不能一律当停机 —— 否则降给定后紧接着的
调速请求会被自己拒掉。

#### 0x3000 的写入口径

**不允许**把加速/减速这些推导值写进 0x3000 的读模型。虚拟设备
`VirtualVfd._reg(0x3000)` 必须严格返回 1/2/3（有回归锁
`test_run_state_word_still_has_only_three_values`）。

### 1.3b 转速换算（2026-11-05）

**变频器没有转速寄存器**，转速由输出频率按**铭牌额定点**线性换算：

```
rpm = hz / ratedHz × ratedRpm          （缺省 ratedHz=50, ratedRpm=1440）
hz  = rpm / ratedRpm × ratedHz         （转速给定的反解）
```

| 项 | 值 | 依据 |
|---|---|---|
| 额定转速 | **1440 rpm** | 现场实测：50Hz 下约 1440 转/分 |
| 额定频率 | **50 Hz** | 同上，与额定转速同一点 |

**为什么用额定点而不是极对数公式**：极对数算出的是**同步转速**
（4 极 = 1500 rpm），而异步电机额定点有滑差，实测 1440。用铭牌两个数更贴近
实际，且现场只需抄铭牌、不必知道极数。

**这是估算值，不是实测**：滑差随负载变化。界面标注
"输出转速为频率换算值（额定点 1440 rpm @ 50 Hz）"，不能当成真实转速。

**配置**（`cfg/hsf_server_py.json` 的 `serial` 段）：

```jsonc
"serial": {
  "vfd_rated_rpm": 1440.0,     // 铭牌额定转速
  "vfd_rated_hz": 50.0,        // 额定频率
  "vfd_max_hz": 50.0           // 最大频率（0x1000 的 ±100% 对应它）
}
```

额定点经快照字段 `ratedRpm` / `ratedHz` 下发给客户端，客户端不写死
（两份必然漂移）。

**转速给定**（`OP_SET_SPEED`）：服务端按额定点反解成 Hz 再走频率通道
（变频器本身只接受频率给定）。超出最大频率时**明确报错**，不静默钳位。

#### ⚠ 停机时禁止下发给定（2026-11-05）

`OP_SET_FREQUENCY` / `OP_SET_SPEED` 只在**运行中**可下发；停机时服务端
明确拒绝：

```
{"ok": false, "err": "变频器处于停机状态，不能下发给定（请先启动后再调速）"}
```

| 为什么 | 说明 |
|---|---|
| 给定是**运行参数**，不是可预置的配置 | 允许停机下发会让人以为"设好了但没生效" |
| 会出现自相矛盾的界面状态 | 实测：停机时写 0x1000，输出频率从 0 爬到 25Hz、转速显示 720rpm，而运行状态还是"停机" |
| 语义唯一化 | **先启动，再调速** |

**判据用设备遥测**（`devices.is_running()`），不是客户端界面状态、也不是
"上次发过启动命令"——命令可能没送达、也可能被现场按面板停掉。状态未读到
时按"未运行"处理：宁可拒绝一次调速，也不能在不确定的状态下改运行参数。

**启停/点动/复位不受此限制** —— 它们本来就要在停机时用。

#### 客户端交互（2026-11-06 改版）

原「下发」按钮 + 停机置灰的做法**已取消**（用户口径：「去掉频率或转速
下发，改成在启动状态下实时显示」）。现在是**改值即生效**：

| 场景 | 行为 |
|---|---|
| 运行中改数字框 / 拖滑块 | 停手后自动下发（数字框 400ms、滑块 250ms 去抖；滑块松手立即发） |
| **停机**时改值 | **只预置**，不发帧；提示"已预置给定 N（启动时生效）" |
| 停机后按启动 | 预置值随 `OP_START` 一起携带（`hz`/`rpm` 字段） |

为什么要去抖而不是每格都发：`QSpinBox` 每敲一个数字、滑块每过一格都发
`valueChanged`，逐次下发会在总线上刷一串 FC06（泵会跟着抖）。两个控件
互相回写时还要 `stop()` 掉对方的计时器，否则同一个动作会下发两条。

**预置值必须挡住遥测回写**：停机时变频器回报的 `setFreqHz` 是**上次的
旧值**（真机停机后 0x1000 保留旧给定，实测 48.6Hz 仍在），若不挡住，
用户刚拖好的预置值会被 200ms 的刷新改回去（表现为"拖不动/自己跳回来"）。

### 1.4 控制（FC06）

**命令字 `0x2000`**

| 值 | 含义 |
|---|---|
| 1 | 正转运行 |
| 2 | 反转运行 |
| 3 | 正转点动 |
| 4 | 反转点动 |
| 5 | 自由停车 |
| 6 | 减速停机 |
| 7 | 故障复位 |

**频率给定 `0x1000`**：写 int16 补码（`raw & 0xFFFF`）。负给定表示反向。

**加/减速时间 `0xF011`(P0.17)/`0xF012`(P0.18)**：0.1s 定点，语义是
**满量程时间**——输出从 0 走到 P0.10 最大频率（或反向）的秒数。
虚拟变频器的爬坡斜率按它们推导：`斜率 = 最大频率 / 秒 / 10`（100ms 一拍）。
缺省各 100 = 10.0s（真机 10s 减速口径）⇒ 50Hz 模型 0.5Hz/拍（5Hz/s）；
参数被显式写 0（未配置）时回退固定斜率 2.5Hz/拍兜底（不除零）。

**运行中换向（2026-11-06 口径，C/Python 两端模型一致）**：运行中收到
反方向命令字（`0x2000` 写 1↔2）**不是瞬间翻方向位**——先按 DEC 把输出
降到 0（这段状态字仍报**原方向**，电机确实还在原方向转），过零那一刻才
翻方向、再按 ACC 向新方向爬到给定；全程保持运行态。约定：

- 换向减速中再收到**同向**命令（含翻回原方向）＝取消待决换向，拉回原方向；
- 换向减速中改给定（`0x1000`）只记忆不动目标，过零后按**新**给定加速
  （服务端"先写 1000H 再写 2000H"两步之间不会出现减速毛刺）；
- 换向减速中**自由停车/减速停机/点动**一律取消待决：停车瞬断、减速停机
  过零走停机、点动按自己的方向接管。

**运行中禁止点动（2026-11-06 口径，双保险）**：电机在正常启停语义下运行时，
服务端拒绝 `OP_JOG`（文案"变频器运行中，禁止点动（请先停机再点动）"），
客户端同步把点动按钮置灰。例外：**点动保持中**（JogWatch.active / C 侧
`s_jogWatch[side].m_active`）的心跳帧照常放行——点动手持每 200ms 重发一次
`OP_JOG`，此时设备必然"运行中"，拦心跳会被 600ms 看门狗误停机。模型层
（`VirtualVfd`/`XVirtualModelVfd`）的点动命令字语义不变，闸在应用层。

客户端配套口径：方向下拉**运行中改选立即换向**（发反向 START、捎带当前
给定），停机改选仍是预选（随下次启动下发）；换向途中横幅依次显示
"减速中 → 加速中 → 反转运行"。

### 1.5 ⚠ 协议怪癖

| 怪癖 | 表现 | 处理 |
|---|---|---|
| **错误应答 8 字节且功能码不置 0x80** | 标准异常应答是 5 字节 `[站][fc\|0x80][code][CRC]`；本机是 `[站][fc][80][01][00][code][CRC]`，**功能码保持原值**。通用库会把它当正常读应答 | 显式按 8 字节形态识别 |
| **单点地址不能连读** | `0x3000`/`0x8000` 数量 ≥2 直接回错误帧 (err=0x05) | 数量必须 = 1 |
| 状态区边界 | `0x1000~0x101F` 可连读；`0x1020` 起只允许数量 = 1 | 按组切 |
| 单帧连读上限 | **16 个寄存器**（17 个及以上报 err=0x05） | 每组 ≤ 16 |
| 写通讯参数后 | 有 0.3~0.5s 不应答窗口 | 重试覆盖 |
| 非广播站号 | 其它站号静默不应答 | 只能靠超时判 |

**错误帧的 5 个错误码**：0x02 非法功能码、0x03 不支持、0x04 非法数据值/写只读区、
0x05 非法数据地址。

### 1.6 前置条件（否则写入被静默忽略）

| 寄存器 | 参数 | 需要值 |
|---|---|---|
| `0xF002` | P0.02 命令源 | **2 = 通讯** |
| `0xF003` | P0.03 主频率源 X | **9 = 通讯给定** |
| `0xFD05` | Pd.05 协议 | **1 = 标准 Modbus-RTU** |

Pd-05 = 0（出厂默认）时读应答是 6+2n 字节（比标准多一字节）。
本服务端按标准（5+2n）解析，故**现场必须把 Pd-05 设成 1**。

### 1.7 故障码（`0x8000`）

只列常见项（完整 41 条见 C 侧 `XVfdM512.c` 的故障表）：

| 码 | 中文 | 码 | 中文 |
|---|---|---|---|
| 0x0002 | 加速过电流 | 0x0009 | 欠压故障 |
| 0x0003 | 减速过电流 | 0x000A | 变频器过载 |
| 0x0004 | 恒速过电流 | 0x000B | 电机过载 |
| 0x0005 | 加速过电压 | 0x000C | 输入缺相 |
| 0x0006 | 减速过电压 | 0x000D | 输出缺相 |
| 0x0007 | 恒速过电压 | 0x000E | 模块过热 |
| 0x0008 | 缓冲电阻过载 | 0x0010 | 通讯异常 |
| 0x0013 | 电机调谐故障 | 0x0016 | 变频器硬件故障 |
| 0x001E | 堵载 | 0x001F | PID 反馈丢失 |

> 面板码（`E.oCAC` 等）与 0x8000 数值是**两套编号，不可互推**。

## 2. 温湿度变送器 ZS-SHT30-1T-1H（Modbus-RTU 从站）

### 2.1 链路参数

| 项 | 值 |
|---|---|
| 串口 | `/dev/ttyS3`（与变频器共用） |
| 波特率 | **115200** 8N1（保持寄存器 `000BH = 7`） |
| 从站号 | **4**（`000AH = 4`） |
| 采集节拍 | 500ms |

### 2.2 取数（FC04）

**一条帧取完**：

```
发: 04 04 00 00 00 02 71 9E
收: 04 04 04 00 D9 02 88 7E 79
     │  │  │  └─┬─┘ └─┬─┘
     │  │  │   温度   湿度
     │  │  └ 4 字节
     │  └ FC04
     └ 站号 4
```

- 起始地址 `0x0000`，数量 **2**
- 温度 = `0x00D9` = 217 → **21.7 ℃**
- 湿度 = `0x0288` = 648 → **64.8 %RH**

### 2.3 换算

```
温度: raw >= 10000 ? -(raw - 10000) × 0.1 : raw × 0.1
湿度: raw × 0.1
```

**负温度分支必须实现**：否则 -25℃（raw=10250）会被解成 10250℃。

### 2.4 ⚠ 协议约束

| 约束 | 表现 | 处理 |
|---|---|---|
| **非法请求静默丢弃** | 永远等不到 0x80 异常码 | **只能靠超时判失败** |
| **帧内字节间隔 ≤ 1.5ms** | 逐字节发会整帧丢弃（3ms 间隔 → 0/15 应答） | **一次 write 出完整 8 字节** |
| 块读上限 20 个寄存器 | 21 及以上超时 | 只需 2 个 |
| 不支持 FC10 | 写多寄存器无应答 | 只用 FC06 |
| 地址空间止于 `0x0013` | `0x0014` 及以上全部超时 | |
| `0x003D` 不存在 | 手册写奇偶校验，实测超时 | **软件层不要写它** |
| 偶发残尾 8 字节 | 0.55% 概率正常应答后多吐 8 字节 | 发送前清接收缓冲 + CRC 双校验 |
| 帧间可背靠背 | 与多数 RTU 从站不同，不需要 3.5 字符静默 | 仍留 ≥1ms 余量 |

### 2.5 寄存器表（FC04 输入寄存器）

| 地址 | 内容 | 换算 |
|---|---|---|
| `0x0000` | 温度 uint16 | ×0.1 |
| `0x0001` | 湿度 uint16 | ×0.1 |
| `0x0002~0x0003` | 温度 float32（大端） | 全精度 |
| `0x0004~0x0005` | 湿度 float32（大端） | 全精度 |

u16 与 float32 **同源**：u16 是 float 截断到 1 位小数（不是四舍五入）。
**不要分两次读**——两次读之间测量已刷新，两者会对不上。

## 3. 模拟量输入模块（Modbus-TCP，8 路 4~20mA）

### 3.1 链路参数

| 项 | 值 |
|---|---|
| 地址 | **`192.168.0.11:8234`**（不是 502！该模块只监听 8234） |
| 站号 | **1**（0 和 255 无响应） |
| 采集节拍 | 200ms |
| 单帧往返 | p50 ≈ **1.8 ms** |

### 3.2 读法（FC04）

输入寄存器 `0x0000~0x0007` = 8 路采样值，一帧读完：

```
发: [MBAP: len=6, unit=1] 04 00 00 00 08
收: [MBAP] 04 10 03 E3 00 00 ...     ← 每通道 2 字节
```

> **Modbus TCP 不带 CRC**。MCAP 之后直接是 PDU。
> （早期排查时误加了 CRC，导致「设备不应答」的假故障。）

### 3.3 换算

```
I(mA) = 寄存器值 / 249
```

- 寄存器值单位是**毫伏**（固定 3 位小数点）
- 采样电阻 **249 Ω**
- 满量程 20mA → 20 × 249 = **4980 mV**

**实测基准**：CH1 读到 **995 mV → 3.996 mA**，正是 4~20mA 量程的**活零点**
（4.0mA）。这条读数顺带证实了量程确实是 4~20mA。

### 3.4 寄存器说明

| 地址 | 功能 | 备注 |
|---|---|---|
| `0x0000~0x0011` | 第 1~18 路采样值 | 本模块配 8 路 |
| `0x0031` | 主动上传间隔（0.01s） | 0 = 不上传 |
| `0x0032` | 设备 ID | |
| `0x0033` | 波特率索引 | |
| `0x0039` | 通道数（= 8） | 手册未定义，实测恒定 |
| `0x003A` | 小数点位数（2 = 固定 3 位） | 手册未定义 |

本服务端只读 `0x0000` 起 8 个通道，不读配置寄存器（省总线）。

### 3.5 现场坑：跳线帽

**每路有独立跳线帽**：不短接 = 电压采集，短接 = 电流采集。
**出厂默认是电压采集。** 若这批模块要采 4~20mA，每一路都必须短接跳线帽，
否则软件怎么读都不对。

### 3.6 工程量换算（通道0 = 压差计，2026-11-05）

**现场**：通道 0 接横河 **EJA110A 差压变送器**（2 线制 4~20mA 输出），
出厂量程 **0~1MPa**。

换算（4~20mA 线性映射到 0~满量程）：

```
p = (I - 4.0) / 16.0 × fullScale
```

**配置**（`server_py/cfg/hsf_server_py.json`）：

```json
"analog": {
  "scales": [
    {"index":0, "name":"压差计", "unit":"MPa",
     "fullScale":1.0, "lowMa":4.0, "highMa":20.0}
  ]
}
```

**为什么换算放服务端**：量程是**现场标定参数**，与接线同性质。同一个
EJA110A 型号有 L/M/H/V 多种膜盒，量程跨 10kPa~14MPa 三个数量级；放客户端
意味着每台机器各配一遍、改一次要升客户端。

**三个刻意的处理**：

| 处理 | 原因 |
|---|---|
| **零点容差 0.05mA** | 4~20mA 变送器的**活零点实测就是 3.996mA**（995mV/249Ω）。严格按 `<4mA` 判「断线」会让最正常的工作点天天报警，现场必然忽略。低于 3.95mA 才算真断线（真断线通常 ≤3.6mA） |
| **越限夹端点并标注** | 超 20mA 显示满量程 + 「超量程」，不显示超量程的假读数；低于下限显示 0 + 「断线/欠量程」 |
| **未标定不给值** | `fullScale=0` 时界面显示 `--`，不给假的 0.000 |

协议字段：`e<i>`（换算值 ×1000）、`eu<i>`（单位）、`en<i>`（通道名）、
`ew<i>`（越限说明）。客户端只负责显示。

> **⚠ 量程值务必核对铭牌**：规格书里「最大压力 16MPa」是**耐压**，不是量程。
> EJA110A 的量程由膜盒决定：L=0.5~10kPa / M=1~100kPa / H=5~500kPa /
> V=0.14~14MPa。把耐压当量程的话，过滤器实际几 kPa 的压差会恒显示
> `0.00 MPa`，看起来像传感器坏了。改量程只改 `fullScale` 一行。

### 4.1b 按钮组（现场操作柱）语义 —— **2026-11-06 改版**

> 用户口径（原话）：
> 「按钮启动这些都是自动模式下的逻辑只能在自动模式下生效，一旦切换到
> 手動，为了安全要停止全部设备」
> 「不是根据物理按钮，是根据设备是否开始自动运行，启动按钮只是给一个
> 信号，要满足条件才切换状态」

**输入侧：按键只是请求**

| 按键 | 触点 | 做什么 | 前提 |
|---|---|---|---|
| 启动 `DI13` | **常开**（不按 0 / 按下 1） | 请求进入**自动运行** | 见下表四项，缺一不可 |
| 停止 `DI14` | **常闭**（不按 1 / 按下 0） | 退出自动运行 + **停全部设备** | **无条件受理**（任何模式都生效） |
| 复位 `DI15` | 常开 | 解除急停锁存 | 无条件；**不启动**设备 |
| 急停 `DI12` | **常闭** | **无信号 = 禁止一切启动** | 持续监视 |

> ⚠ **停止是常闭**（用户口径：「停止是常闭的，不按就是通的」「跟急停一样」）。
> 判据取**下降沿**（1→0 = 按下），与常开的启动/复位相反。
>
> **旧实现为什么完全收不到停止**：三路一律取上升沿。停止常闭时开机第一帧
> 「未知→1」被当成"刚按下"（板端日志里那句「未在运行，现场停止按钮仍执行
> 全停」就是这个假沿），而真正按下是 1→0、代码根本不看 —— 按停止毫无反应。
>
> 常闭的另一个意义是**线断了 = 停止**：下降沿判据天然覆盖断线，安全侧正确。
> 触点类型可配：`buttons.items.normally_closed = ["stop_di"]`（缺省就这个）。

**启动的四项前提**（全部满足才切状态）：

1. 当前是**自动模式** —— 手动模式下按启动**完全无效**
2. 急停回路正常（`DI12 = 1`）
3. 急停未被锁存（急停过一次后必须按复位）
4. 控制器当前没在跑（幂等）

> ⚠ **手动模式下按启动不亮灯、不动作**。灯跟的是"设备真的在不在自动运行"，
> 不跟"你按没按过" —— 若灯跟按键走，操作员会看到"启动灯亮了"以为设备在跑，
> 实际什么都没发生，比不亮更危险。

**输出侧：灯跟运行态**

| 灯 | 亮的条件 |
|---|---|
| 启动灯 `DO7` | 自动运行**中** |
| 停止灯 `DO8` | 未运行（含急停；与启动灯**严格互斥**） |
| 复位灯 `DO9` | **点动**：按住复位才亮，松手灭 |

**切回手动 = 全停**（不做"收尾确认"，直接依次）：

1. 停自动控制器
2. 变频器 **减速停机**（`op=5`，不用自由停车 —— 机械冲击小）
3. 逐台停进水泵
4. 逐路关电磁阀
5. 灯切到"停止"（只点停止灯）

逐台独立 `try`：一台设备离线/失败**不阻断**停其它台，失败原因记日志。

**⚠ 急停判据的两个易错点（都踩过）**

| 坑 | 表现 | 正确做法 |
|---|---|---|
| **点表配在离线模块上** | 急停恒读不到 → 按启动永远被拒，报"急停状态未知" | 配置里 `buttons.items.module` 必须指向**在线**模块的下标 |
| **首帧未到就锁存** | 服务端刚启动、数字量还没回第一帧 ⇒ 误判成急停按下 ⇒ **锁存**，之后 `DI12=1` 也解不开（必须人工按复位），日志里还留下一条**不存在的**急停事件 | 从没见过"急停正常"之前**只禁止启动、不锁存**；见到过之后才按真实急停处理 |

急停三态（`estop_ok` 与 `estop_configured` 的分工）：

| 情形 | `estop_configured()` | `estop_ok()` | 允许启动？ |
|---|---|---|---|
| 未装配按钮组 / `estop_di` 未配 | `False` | `None` | **允许**（没有这道安全件，不能拿它当闸） |
| 配了 + 回路通 | `True` | `True` | 允许 |
| 配了 + 按下/断线 | `True` | `False` | **禁止**，且锁存 |
| 配了 + 模块离线（读不到） | `True` | `None` | **禁止**，但**不锁存**（一次都没读到过） |

> **未配置 ≠ 禁止**：这条区分是端到端测试（66 项全红）暴露的 —— 初版把
> `None` 一律当"禁止"，没装操作柱的纯 TCP 现场所有启动/调速全被拒，
> 现场表现是"设备好好的但点不动"。

### 4.2 寄存器映射

| 用途 | 区域 | 地址 | 功能码 |
|---|---|---|---|
| **DO**（输出） | 线圈 | `0x0000~0x000F` | FC01 读 / **FC05 写单点** |
| **DI**（输入） | 离散输入 | `0x0000~0x000F` | FC02 读 |

DI 和 DO 在**两个独立区域**，无法一帧同时取——两帧都成功才算本拍有效。

### 4.3 读

```
DI: FC02 addr=0x0000 count=16   → 2 字节位图
DO: FC01 addr=0x0000 count=16   → 2 字节位图
```

位图**低位在前**：bit 0 = 通道 0。

### 4.4 写

**单点**（FC05）：

```
FC05 addr=N value=0xFF00 (on) / 0x0000 (off)
```

**整组**：本服务端用 **FC05 逐点写**，不用 FC0F（原因见 §4.5）。

### 4.5 ⚠ 协议怪癖（重要）

| 怪癖 | 表现 | 处理 |
|---|---|---|
| **FC0F 会发两次相同应答** | 事务号恒 0000 无法区分；同连接的下一条请求会把重复帧当响应 | **整组写用 FC05 逐点**（16 次，几十毫秒足够） |
| **连接 churn 敏感** | 频繁连断会被打进**数分钟不应答状态**（连 ping 都不通） | 长连复用；**读超时不断连**，只断真正的流错误 |
| 重连过快被断连 | 连接间隔需 ≥1s | 长连避免 |
| 保持寄存器为 0 的型号 | FC03 回 `0x03` 属正常 | 不读 HR |
| 应答慢 | 0.4~0.8s 是**正常**的 | 超时给 2s |

**关于「超时不断连」**：服务端只在**字节流不可用**时断连
（连接被关、读不足长度、OSError）。读超时但连接仍在时**保留连接**，
下一拍重试——因为该模块应答本来就慢，偶发超时属正常抖动。

迟到帧由逐帧校验兜住：MBAP 长度非法 → 判流错位 → 断连重建；
事务号非 0 且不匹配 → 当迟到帧丢弃后继续等。

### 4.5b 现场实际架构：`.12` 聚合 `.13`（对外 32DI/32DO）

**这是理解现场配置的关键**。两台模块不是并列的两个从站，而是**主从聚合**：

```
192.168.0.12  ms=1（主站）  sysDoNu=32  sysDiNu=32   ← 聚合者
              esDoNu1=16  esDiNu1=16
              lip01=192.168.0.13     （条目1 指向 .13）
              rip=192.168.0.9:8080   （往外推）

192.168.0.13  ms=1（主站）  sysDoNu=16  sysDiNu=16   ← 被聚合者
              rip=192.168.0.243:8080 （往外推，本机）
```

`.12` 把 `.13` 的 16 点映射进自己的地址空间，**对外表现为一台 32DI/32DO 设备**。

**所以只轮询 `.12` 就能拿到全部 32 点。**

> **⚠ 2026-11-05 订正（此前文档写错了）**
>
> 本文档早先断言「两台都是 `ms=1`，都往外推数据、**都不响应 Modbus**，
> 要采集必须把 `.12` 改成 `ms=0`」。**实测证伪**：
>
> `.12` 配成 `ms=1` 时**仍然完整应答** FC01/FC02（读 `0x0000` 起 32 点
> 返回 4 字节，正常）。而且**上半区是活的**：写 `.13` 的 DO0 → 读 `.12`
> 得 `0x00010000`（**聚合偏移 = 16**）；写 `.12` 自己的 DO16/DO20/DO31，
> 回读逐位正确、恢复后归零。
>
> 结论：「`ms=1` 就不应答」不是绝对规则，固件版本/接线都会影响。
> **诊断时以实测应答为准，别只凭 `config.js` 里的 `ms` 判死设备。**

### 4.5b-2 32 点采集的两条硬约束（2026-11-05 实测）

| 现象 | 原因 | 处理 |
|---|---|---|
| 32 点读报 `IncompleteReadError` | 模块把**一帧应答拆成多个 TCP 段**发（qty=16 时先回 `0202` 再补 `00`；32 点的 4 字节数据更容易切开）。`readexactly` + 外层 `wait_for` 超时会**取消并把已缓冲的半帧丢掉** → 整条流永久错位 | 只按「还差多少字节」反复 `read()`，EOF 才认失败（`modbus.py` 的 `_read_upto`） |
| 无间隔连发偶发 0 字节应答 | 实测 10 次里 1~2 次收到 `SHORT(0)`；间隔 ≥300ms 基本不出 | 靠重试兜底；**不能把单次空应答当设备失联** |

### 4.5b-3 点数不再写死（`.13` 保留为故障探测）

配置形态：

```json
"modules": [
  {"name":"数字量",       "host":"192.168.0.12","channels":32,"publish":true},
  {"name":"数字量从站.13","host":"192.168.0.13","channels":16,"publish":false}
]
```

`channels` 是该模块实际点数（**单模块 16，聚合后 32**）。

`publish=false` 的语义：**照常轮询、照常出健康条目，但不发点位帧**。
理由：`.13` 的点已经出现在 `.12` 的地址空间里，两边都发会让客户端出现
**两套重复点位**；而 `.13` 自己是否在线是独立故障信息（模块断电/网线松
只由它自己的应答反映），所以保留探测。

客户端**不写死点数**：按快照里的 `count` 键动态重建灯阵/按钮阵
（16 点画 16 格、32 点画 32 格），位宽也跟着点数走（>16 点用 8 位十六进制）。

### 4.5b-4 通道名由服务端推导（被电磁阀占用的口）

服务端直接读阀门点位映射生成名字，**只发被占用的口**：

```
DO16 → 电磁阀1 控制      DI16 → 电磁阀1 关到位    DI17 → 电磁阀1 开到位
DO17 → 电磁阀2 控制      DI18 → 电磁阀2 关到位    DI19 → 电磁阀2 开到位
...                       （共 6 路控制 + 12 路到位）
```

键名 `din<n>` / `don<n>`。**不另建名字表**：点位映射已经是「哪路阀用哪个口」
的唯一事实源，再维护一份必然漏改。接线一改服务端配置一改，客户端零改动
跟着变。未占用的口不发名字，客户端只显示 `CH<n>`。

### 4.5c ⚠⚠ 改工作模式会清空 I/O 点数（本项目最坑的一条）

**实测（2026-11-04）**：

```
改 .12 的 ms: 1 → 0
提交成功（固件返回倒计时页 = "已接受"）
重启后：ms=0 生效 ✓
       但 sysDoNu 32 → 0   ✗
          sysDiNu 32 → 0   ✗
```

**点数清零后，模块在 Modbus 上「TCP 可连但完全零应答」**——所有读请求
返回 0 字节，看起来像设备坏了，其实是它没有任何点位。

**根因**：`POST /config_ch.cgi` 只管辖**网络类**字段
（`ms`/`slaId`/`lip00`/`gw`/`sub`/`rip`/`rport`/`mport`）。
`sysDoNu`/`sysDiNu`/`es*` 这些 **I/O 字段不属于它的表单**，
提交时被固件按"未提供"处理 → 归零。

真正的 I/O 配置在 `/io_param_ch.cgi`，但该页面在部分固件上**返回 0 字节**，
无法脚本化。

**正确做法**：

1. **改任何字段前先备份**：`python tools/mt3a_config.py --backup <ip>`
2. 提交时**把备份里的全部字段原样带上**，只改目标字段
   —— 工具 `--set` 已内置这个行为
3. **改完必须复核点数**（工具会自动比对并报警）
4. 点数真丢了 → 用浏览器打开模块 Web 界面，在 I/O 页手工补回 16/32

现成工具：

```sh
cd HighSpeedFilter/server_py

python tools/mt3a_config.py --list                  # 列出网段内所有模块
python tools/mt3a_config.py --show 192.168.0.12     # 看单台全部配置
python tools/mt3a_config.py --backup 192.168.0.12   # 备份（改前必做）
python tools/mt3a_config.py --set 192.168.0.12 --ms 0   # 改模式（自动备份+复核）
```

### 4.6 ⚠ 最重要：这模块可能被配成「主站」，压根不当从站

**这是最容易误判成"设备坏了/离线"的一条。** MT3A-IO1632 有两个角色，
由 Web 配置的 `ms` 字段决定：

| `ms` | 角色 | 行为 | 我们怎么访问 |
|---|---|---|---|
| **1** | **主站** | **主动**向 `rip:rport` 推送数据；**不响应任何 Modbus 从站请求** | ❌ 采不到（502 连上即被关） |
| 0 | 从站 | 标准 Modbus TCP 从站 | ✅ 按 §4.2 映射读写 |

**现场实测（2026-11-04）两台都是 `ms=1` 主站：**

```
192.168.0.12:  ms=1  rip=192.168.0.11:8080
192.168.0.13:  ms=1  rip=192.168.0.243:8080   ← 本机，read_analog_gui.py 在收
```

**主站模式下的典型现象**（很容易误判）：

```
TCP 502 连接成功，但立刻被对端关闭（未发请求就 RST）
或连上后发什么都是 0 应答，耗时却长达 800~1000ms
```

**判据**：`TCP 可连 + Modbus 零应答 + 耗时近 1 秒` = **大概率是主站模式**，
不是设备坏了、不是线的问题、也不是服务端 bug。

**怎么确认**：模块的 Web 界面免登录可读全量配置：

```sh
curl http://192.168.0.12/config.js      # 看 "ms" 字段：1=主站 0=从站
```

**要当从站采怎么办**：打开模块 Web 界面（账密 `amx666/amx666`），
把工作模式从「主站」改成「从站」并保存（约 2 秒软重启）。

> 本服务端的健康文案会自动区分这两种情况：
> 显示「无 Modbus 应答（检查是否配成主站 ms=1）」而不是笼统的「模块失联」。

### 4.7 ⚠ 调试时最容易犯的错：反复探测把模块打僵

**实测（2026-11-04）**：为排查问题在一分钟内对 `.12` 发了十几次裸 socket
探测，之后该模块**连续 180 次采集返回 `IncompleteReadError`**，再过一会儿
连 `.13` 也开始 `ConnectionResetError`——**TCP 能连、Modbus 不应答**。

这正是本模块的已知特性：**对连接 churn（频繁连断）极敏感**，
会被打进"数分钟不应答"状态，连 ping 都可能不通。

**正确做法**：

| 不要 | 要 |
|---|---|
| 反复起新进程/新 socket 探测 | **复用一条长连接**（本服务端就是长连） |
| 出问题就狂试 | 出问题先**停手等 3~5 分钟**，多半自己恢复 |
| 同时开多个工具连同一模块 | 只留一个采集者（多主站会互相干扰） |
| 用 `--diag` 反复跑 | 一天跑一次足够，它是诊断不是压测 |

判据：**`TCP 可连 + Modbus 无应答` = 模块被打僵**，不是线路问题、也不是
服务端 bug。等它恢复即可，必要时断电重启模块。

### 4.8 Web 配置

模块有 web 界面（`http://<ip>/config.js` 免登录可读全量配置）。
账密 `amx666/amx666`。本服务端不需要它，仅供现场核对 IP/端口/站号。

## 4b. 电磁阀（6 路，1 DO + 2 DI）

### 4b.1 现场接线（2026-11-05 确定）

6 路阀接在 **`.13`** 上，每路占 1 个 DO + 2 个 DI：
**DO 0~5 = 六个阀的输出控制**（0=关、1=开），**DI 0~11 = 六组到位反馈**。

**DI 顺序是「先关到位、后开到位」**：

```
.13 通道            含义
DO0                 阀1 输出
DI0 / DI1           阀1 关到位 / 开到位
DO1                 阀2 输出
DI2 / DI3           阀2 关到位 / 开到位
...                 依次排到 DO5 / DI10,DI11
```

**但 `.13` 已聚合进 `.12`（偏移 16）** ⇒ 服务端实际访问 `.12` 的
**DO16..21 / DI16..27**：

| 阀 | DO | 关到位 DI | 开到位 DI |
|---|---|---|---|
| 1 | 16 | 16 | 17 |
| 2 | 17 | 18 | 19 |
| 3 | 18 | 20 | 21 |
| 4 | 19 | 22 | 23 |
| 5 | 20 | 24 | 25 |
| 6 | 21 | 26 | 27 |

客户端**完全不知道这层映射**，只问"6 个阀什么状态"。

### 4b.2 配置

```jsonc
"valves": {
  "enabled": true,
  "poll_ms": 200,
  "move_timeout_ms": 20000,          // 动作超时→判故障并推送告警
  "items": [
    { "name": "电磁阀1", "module": 0, "do": 16, "openDi": 17, "closeDi": 16 },
    { "name": "电磁阀2", "module": 0, "do": 17, "openDi": 19, "closeDi": 18 },
    { "name": "电磁阀3", "module": 0, "do": 18, "openDi": 21, "closeDi": 20 },
    { "name": "电磁阀4", "module": 0, "do": 19, "openDi": 23, "closeDi": 22 },
    { "name": "电磁阀5", "module": 0, "do": 20, "openDi": 25, "closeDi": 24 },
    { "name": "电磁阀6", "module": 0, "do": 21, "openDi": 27, "closeDi": 26 }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `module` | 数字量模块下标（**0 = `.12`**；`.13` 已聚合进 `.12`，不要填 1） |
| `do` | 该模块的 DO 通道号（聚合后 0~31） |
| `openDi` | **开到位** DI 通道号（接线里是每组 DI 的**后一个**） |
| `closeDi` | **关到位** DI 通道号（每组 DI 的**前一个**） |
| `name` | 界面显示名（同时作为数字量页的通道名来源） |

留空某路（`module/do/openDi/closeDi` 都为 `null`）该路显示"未配置"，
控制被拒，其余路照常工作。

### 4b.3 动作定时器与告警（20s）

**每路一个独立的 20s 定时器**，从下发命令起算到目标位置的到位信号出现为止：

| 项 | 值 | 依据 |
|---|---|---|
| `move_timeout_ms` | **20000** | 现场实测一个阀**满开→满关约 10s**；20s 是两倍余量，能容忍阀体老化/水压偏低，又不至于让人等太久 |

> **原缺省是 8000ms，对 10s 行程根本不够**，每动一次就误报。已改。

**按目标位置判到位**（不是"两个反馈都为 0 就算动作中"），否则"到位了但
另一个开关也吸着"（互斥故障）会被当成没到位。

**超时/互斥告警是一次事件，不是每拍状态**：

- `timeout_reported` / `conflict_reported` 标志位保证**一次动作只告警一次**
  （判据每拍都成立，没有标志位会每 200ms 推一条，客户端被刷屏）
- 每次 `set_valve` 时清零，保证第二次动作还能再报
- 到位后发一条 `CLEARED` 消警，并清零计时

**推送口径**：只推给**订阅了阀主题**的会话，复用
`TOPIC_VALVE_STATUS (0x00010007)`，键空间独立：

```jsonc
{ "ac": 1,                                    // 告警条数（有该键=告警帧）
  "a0_vi": 0, "a0_vn": "电磁阀1",
  "a0_k": 1,                                   // 1=超时 2=互斥 3=已恢复
  "a0_t": "动作超时未到位（20s）——全程无任何到位信号，优先查询行程开关接线",
  "a0_at": 123456, "a0_to": 20.0 }
```

告警类型常量：`VALVE_ALARM_TIMEOUT=1` / `VALVE_ALARM_CONFLICT=2` /
`VALVE_ALARM_CLEARED=3`。

### 4b.4 重复点击与在途反向（判定**全在服务端**）

现场与远程都会有人连点同一个按钮。服务端必须区分下面四种情况，
并把这些行为**全部在服务端实现**（客户端置灰按钮只是便利，
网络重发、C 端客户端、脚本直连都能绕过）：

| 情况 | 处置 | 是否写 DO | 是否重置 20s 计时 |
|---|---|---|---|
| 已到位 + 命令与当前位置一致 | `ignored` | **否**（幂等） | 否 |
| 动作中 + 同目标（重复点） | `repeated` | 是（防上次写丢） | **否** |
| 反向（开→关 / 关→开） | `reversed` | 是 | **是**（新动作） |
| 首次命令 | `issued` | 是 | 是 |

> **为什么"同目标重复"绝不能重置计时器**：超时告警靠 `now - cmd_at_ms`
> 判超时。原本 `set_valve` 无条件 `cmd_at_ms = now`，于是**用户每 20s 内
> 点一次同侧，卡阀就永远不会报警**（实测连点 8 次，0 告警）。
> 同目标是"同一次动作的重复请求"，计时必须从**第一次命令**起算。

判据用**到位反馈**（`item.state`）而不是命令回显：命令回显在阀卡住时
同样为真，用它判会把"卡住的阀"误认为到位。

**处置结果编码进控制应答**（键 `v{i}_cmdResult`，见 `proto.KEY_VALVE_CMD_RESULT`）：

```jsonc
{ "ok": true, "count": 6,
  "v0_cmdResult": "repeated",   // issued / repeated / reversed / ignored / external
  ... }
```

客户端据此给不同状态栏文案（`VALVE_CMD_TEXT`，两端同口径）：

| 值 | 界面文案 |
|---|---|
| `issued` | 命令已下发 |
| `repeated` | 动作中，重复命令不重置计时 |
| `reversed` | 已反向（重新计时） |
| `ignored` | 已在目标位置，无需动作 |
| `external` | 输出被外部改动，已接管 |

> 只回 `ok=true` 的话界面区分不了"真的动了"和"本来就在那儿"，
> 用户会以为重复点击也生效了 —— 与事实相反。

### 4b.5 外部写 DO 的接管（数字量页 / HMI / 自动逻辑）

数字量页可以直接写任意 DO，**包括阀占用的 16..21**。那条路径走的是
`_h_digital_control → DigitalIo.write_do`，**不经过 `ValveBank.set_valve`**。

若不管它，后果是：

| 症状 | 原因 |
|---|---|
| 阀动作那 10 秒显示"**无到位反馈（检查行程开关接线）**" | `cmd_at_ms` 没置位 ⇒ 状态机认为从未下过命令 ⇒ 落到"两反馈都为 0 且无命令"分支 |
| 20s 超时**永远不判** | 没有起算点 |
| 排查方向被带偏 | 提示去查接线，而阀其实在正常动作 |

**修法**：`ValveBank.poll()` 每拍比对**模块实际 DO** 与阀已知位置
（`item.known_do`），不一致就接管为一次新动作（记目标、起算超时、
`cmdResult=external`）。

放在 `poll()` 而不是只修 `_h_digital_control`，是因为**任何**绕过
`set_valve` 的写入都该被接管 —— 包括未来的自动控制模块与现场 HMI。

**首拍校准**：`known_do` 初值要跟真机对齐，但必须等数字量模块**真正
采过一帧**（`last_ok_ms > 0`）才校准。否则服务端刚起来时 `dev.do` 还是
全 0，会被当成"阀在关位"，真数据一到就凭空起算一次假动作
（实测：重启后阀页立刻显示"动作中"，20s 后还误报超时）。

### 4b.6 动作中"停在原位置"不能算到位

**这是超时判据里最容易写错的一处**。反馈显示"已在某一端到位"时，
必须再判断**那一端是不是命令的目标**：

```python
arrived_at_target = (state == Open if cmd_target_open else state == Closed)
if cmd_at_ms and not arrived_at_target:
    state = Moving      # 停在原位置、目标在另一端 ⇒ 仍在途中
else:
    cmd_at_ms = 0       # 真到位了才结束本次动作计时
```

> **原实现无条件 `cmd_at_ms = 0`**。命令刚下发时反馈**必然是旧位置**
> （阀还没开始动），于是"命令开阀 → DI 仍显示关到位 → 判为已到位 →
> 计时清零 ⇒ 报'检查接线' ⇒ 20s 永不超时"。
> 这个缺陷一直被 `_h_valve_control` 里的 `refresh_valve_sources(force=True)`
> 掩盖着，直到从数字量页写 DO 时绕过了那条路径才暴露。

### 4b.7 阀类型（单电控 / 双电控）

软件层不区分，统一按"写 1 = 开、写 0 = 关"：

| 类型 | 现场接线 | 软件行为 |
|---|---|---|
| 单电控（弹簧复位） | DO=1 开阀，断电靠弹簧关 | 写 0 靠弹簧回关位 |
| 双电控（双线圈） | 外部中继自保持 | 写 0 = 关（保持型） |

差别只在继电器接线，服务端与客户端都不用改。

### 4b.8 反馈判读与故障（状态只由反馈推导）

| 开到位 | 关到位 | 判定 |
|---|---|---|
| 0 | 0 | **从未下过命令** → "状态未知"（多为行程开关没接）<br>**刚下过命令** → "动作中"（正常，约 10s） |
| 0 | 1 | 已关 |
| 1 | 0 | 已开 |
| 1 | 1 | **故障**（互斥反馈同时为真 = 接线/阀体故障） |

**不采信命令回显**：写了 1 只代表命令发出去了，阀有没有真动要靠行程开关说话。

**超时文案区分两类原因**：

- **全程无任何到位信号** → "动作超时未到位（20s）——全程无任何到位信号，
  **优先查询行程开关接线**"（指向真正的排查方向，别让人去拆阀）
- **曾经有过反馈但这次没到位** → 真故障（阀卡住/线圈断）

### 4b.9 调试要点

**看到 6 路都「状态未知 / 无到位反馈」** = 行程开关没接线或没供电，
不是软件问题。**2026-11-05 实测**：6 个 DO 逐个通电 6 秒、12 个 DI 全程
恒为 0（用户已说明信号尚未接入）。

**验证控制通路**用 DO 写入：下发"开阀"后 `openCmd` 应变 true、状态变"动作中"，
回读 `.12` 的 DO 位图对应位置 1 —— 即使行程开关没接，这一步也能验证
服务端到模块的写链路。

## 4c. 进水泵（1 台，数字量模块上的一路 DO）

**只有输出，没有反馈**。接触器线圈接在**第 6 路电磁阀的下一个 DO**：

```
.13 通道          .12 地址（聚合偏移 16）      用途
DO0~DO5      →    DO16~DO21                   电磁阀 1~6
DO6          →    DO22                        进水泵      ← 紧邻的下一个口
DI0~DI11     →    DI16~DI27                   6 路阀的 12 个到位反馈
```

### 4c.1 为什么单独一个类（`pumps.PumpBank`）

| | 电磁阀 | 进水泵 |
|---|---|---|
| 反馈 | 2 个 DI（开/关到位） | **无** |
| 状态来源 | 只由反馈推导 | 只由**输出回显**推导 |
| 动作超时告警 | 有（20s） | **无**（没有可比对的反馈） |
| 中间态 | 「动作中」 | 无（切换是即时的） |

塞进 `ValveBank` 会让那套状态机多一条"永远不到位"的特例，两边都变难读。

> **硬造超时告警就是撒谎**：泵启动 20s 后必然"没有反馈到"，照抄阀的逻辑
> 会出现一条**永远成立**的假告警。要真正监视泵，得现场加运行反馈点
> （接触器辅助触点 / 流量开关）。

### 4c.2 配置

```jsonc
"pump": {
  "enabled": true,
  "staleMs": 5000,
  "items": [ { "name": "进水泵", "module": 0, "do": 22 } ]
}
```

`module` 是 `digital.modules` 的下标（`.12` = 0）。`do` 用 **`.12` 的地址
空间**（已聚合，含偏移 16），与电磁阀的配置同一口径。

**名字同源**：DO22 的通道名由服务端从泵配置推导后写入数字量快照的
`names`（`_pump_channel_names`），所以数字量页的 DO22 也显示"进水泵"，
不用手动维护两处。

### 4c.3 幂等与外部改动

| 场景 | 服务端行为 |
|---|---|
| 命令值 == 当前回显 | **不写 DO**，直接回 `ok=true`（避免无谓继电器动作） |
| 首拍（模块还没采过一帧） | 只校准已知位置，**不判**外部改动 |
| DO 被外部改动（数字量页/HMI） | 以**模块实际输出**为准并记日志 |

> **为什么外部改动必须接管**：泵没有反馈，DO 回显是**唯一**能发现"这个口
> 被别人改过"的手段。界面显示一个与实际输出相反的状态是最危险的。

**2026-11-05 已验证**（`--sim`）：启动 → DO22 置位 → 停止 → 归零；
重复启动不再发 FC05（幂等）；从数字量页直写 DO22 后服务端跟随实际值。

## 5. 电磁流量计（LD 系列）

**2026-11-05 已实现**（`devices.FlowMeter` + `virtualdev.VirtualFlowMeter`）。

**现场默认关闭**（`serial.flowmeter_enabled = false`）：真实设备表里还没接
这一路，且多挂一个从站会拖慢同一条 485 的轮询（未接的从站每拍都超时）。
`--sim` 模式下会**自动补挂**一个虚拟流量计，方便把界面跑完整。

> 打开方式（真机）：配置里 `"serial": {"flowmeter_enabled": true,
> "unit_ids": {"flowmeter": 5}}`，或代码里置 `cfg.enable_flowmeter = True`。

### 5.1 链路

| 项 | 值 |
|---|---|
| 串口 | 与变频器/温湿度**共用** 485（同一条总线，按从站号区分） |
| 波特率 | **9600**（参数 `0x0002 = 5`） |
| 从站号 | **5**（非默认 1） |

### 5.2 一帧读完 22 个变量（FC03）

```
发: 05 03 10 10 00 16 <CRC>
收: 05 03 2C <44 字节数据> <CRC>
```

起始 `0x1010`，数量 **22**（0x0016）。

### 5.3 变量表（`0x1010~0x1025`）

| 地址 | 格式 | 内容 | 单位 |
|---|---|---|---|
| `0x1010~0x1011` | F32 | 瞬时流量 | 见 `0x1020` |
| `0x1012~0x1013` | F32 | 瞬时流速 | m/s |
| `0x1014~0x1015` | F32 | 流量百分比 | % |
| `0x1016~0x1017` | F32 | 流体电导比 | |
| `0x1018~0x1019` | U32 | 正向累积**整数部分** | |
| `0x101A~0x101B` | F32 | 正向累积**小数部分** | |
| `0x101C~0x101D` | U32 | 反向累积整数部分 | |
| `0x101E~0x101F` | F32 | 反向累积小数部分 | |
| `0x1020` | U16 | 流量单位代码 | 5 = M³/H |
| `0x1021` | U16 | 累积单位代码 | 1 = M³ |
| `0x1022` | U16 | 上限报警 | |
| `0x1023` | U16 | 下限报警 | |
| `0x1024` | U16 | 空管报警 | |
| `0x1025` | U16 | 系统报警 | |

### 5.4 关键换算

**累积量必须两段拼装**（不是单个 64 位整型）：

```
正向累积 = U32(整数部分) + F32(小数部分)
```

**单位不能写死**：`0x1020` 是仪表侧可改的，必须随数据读上来做标度。

**F32 是大端**（高字在前）。

### 5.5 ⚠ 协议约束

| 约束 | 表现 |
|---|---|
| 参数区永远只返回 1 个寄存器 | 请求 2 个也只回 1 个（字节数字段恒 `0x02`） |
| 变量区越界**静默返回 0** | 不报错，只是读到 0（按固定布局读错地址不会失败） |
| FC03 也能读变量区 | 值完全一致，只是效率低 |
| `0x0047` 等只写寄存器 | FC03 读回异常 `0x83 0x01` |

### 5.6 实现要点（Python 端）

`devices.FlowMeter` 按上面口径实现，三处容易写错的地方都加了注释：

| 点 | 做法 | 为什么 |
|---|---|---|
| **32 位量在设备层拼装** | `_float32(hi, lo)` / `_long32(hi, lo)` | 累积量跳字的那一瞬若跨帧取高低字，会拼出天文数字。一帧读回来立即在本函数内拼好 |
| **累积 = 整数 + 小数** | `forward_total = U32(0x1018) + F32(0x101A)` | 不是单个 64 位整型；小数部分是 0~1 的浮点 |
| **单元码原样透传** | `flow_unit` / `total_unit` 直接来自 `0x1020`/`0x1021` | 仪表侧可改，写死就错；且**两张码表独立**（瞬时 5=m³/h、累积 1=m³） |

**未在线时不写值键**：`encode_flowmeter` 只在 `online` 时写
`flow/speed/forwardTotal/...`，否则只给 `valid=false` —— 客户端据此显示
`--` 而不是 `0`（0 是"真的没流量"，含义完全不同）。

#### 虚拟模型（`virtualdev.VirtualFlowMeter`）

| 项 | 值 |
|---|---|
| 基准流量 | 36.5 m³/h（DN50 量程中点），**±2% 正弦波动、周期 60s** |
| 流速 | 由流量反算 `Q / (π r²)`，DN50 时约 5 m/s |
| 累积量 | 按**真实经过时间**积分（不按"被访问次数"），轮询节拍变了也不影响 |
| 单位码 | `flowUnit=5`（m³/h）/ `totalUnit=1`（m³） |

> **为什么要波动**：恒定值看不出"数据在刷新"，容易误判成界面卡住 ——
> 与独立模拟器 `sim/hsf_sim.py` 同一套口径，两边看到的数一样。

## 5b. 浊度仪（2 台，⚠ 协议口径未确认）

**2026-11-05 已实现**（`devices.TurbidityMeter` + `virtualdev.VirtualTurbidity`）。

### 5b.1 链路

| 项 | 值 |
|---|---|
| 串口 | 与电磁流量计/变频器/温湿度**共用** 485 |
| 波特率 | 9600（与总线其它从站一致） |
| 从站号 | **1 与 3**（现场手工设定，⚠ 待真机确认） |
| 台数 | 2（配置 `turbidity.unitIds` 的数组长度决定） |

> **站号为什么走配置**：用户明确说"这个不确定了"。两台仪器是现场手工设
> 站号的，与出厂/文档值可能不一致 —— 写死在协议里会导致真机接上就全错。
> 改配置即可，不用改代码。

### 5b.2 取数（⚠ 按常见口径，**无资料**）

用户答复：「没有资料，按常见口径先做」。故当前口径为：

```
发: 01 03 00 00 00 02 <CRC>
收: 01 03 04 <hi> <lo> <hi> <lo> <CRC>

raw = (hi0 << 16) | lo0      // 32 位整数，高字在前
NTU = raw / 100.0            // 两位小数
```

| 常量 | 值 | 位置（改这里就够） |
|---|---|---|
| `READ_ADDR` | `0x0000` | `devices.TurbidityMeter` |
| `READ_COUNT` | `2` | 同上 |
| `SCALE_DIVISOR` | `100.0` | 同上 |

**换到真机若口径不同，只改这三个类常量**，上层（`app` / 客户端）一处不用动。

### 5b.3 实现要点

| 点 | 做法 | 为什么 |
|---|---|---|
| **32 位量在设备层拼装** | `raw = (hi<<16)\|lo`，一帧内拼完 | 跨帧取高低字会拼出天文数字 |
| **保留 `raw` 一起下发** | 快照带 `vN_raw` | 换算口径不对时，`raw` 是唯一能反推真相的量 |
| **短帧判失败** | 读回 < `READ_COUNT` 直接抛 | 不能拿半帧当有效换算 |
| **离线不写 `ntu`** | 只给 `online:false` | 客户端显示 `--` 而不是 `0.00`（0.00 = 极干净，含义完全不同） |

### 5b.4 虚拟模型（`virtualdev.VirtualTurbidity`）

| 台号 | 基准 | 波动 |
|---|---|---|
| 0 | 12.5 NTU（偏原水） | ±3%，周期 45s |
| 1 | 3.2 NTU（偏出水） | 同上，**相位错开 180°** |

> **为什么两台要错开相位**：两条曲线完全重合时，界面上看不出是两台独立
> 仪器，会让人以为是同一个值贴了两遍。

未建模地址（如 `0x0010`）**返回 0 而不是抛异常** —— 真机对"有但不用"的
寄存器就是回 0；抛异常会把"读成功但值为 0"变成"整拍失败"，设备永远显示离线。

写操作一律 `KeyError`（浊度仪只读）。

## 6. 各设备通用排障

### 6.1 Modbus 帧格式对照

| 链路 | 帧结构 | CRC |
|---|---|---|
| **RTU**（串口） | `[站号][PDU...][CRC lo][CRC hi]` | **有**（0xA001，低字节在前） |
| **TCP**（网口） | `[tid][pid][len][unit][PDU...]` | **无** |

> 混用是最常见的假故障来源：TCP 加 CRC、或 RTU 忘 CRC，设备都不应答。

### 6.2 超时 vs 异常码

| 设备 | 遇到非法请求时 |
|---|---|
| M512 | 回 8 字节错误帧（含错误码） |
| 温湿度 | **静默丢弃**（只能靠超时） |
| 模拟量 | 忽略或回标准异常 |
| 数字量 | 回标准异常应答 |
| 电磁流量计 | 参数区只回 1 个寄存器；变量区越界**静默回 0** |
| 浊度仪 | ⚠ 未实测（按常见口径实现，见 §5b） |

所以「超时」在不同设备上含义不同——不能一律当「设备坏了」。

### 6.3 用 diag 快速定位

```sh
python3 -m hsfsrv --diag --no-serial    # 只测三个 TCP 设备
python3 -m hsfsrv --diag --no-io        # 只测串口（跳过 TCP）
```

输出会逐个设备打印 OK/失败及具体值。
