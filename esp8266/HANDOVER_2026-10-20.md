## 1. 唯一可用的参照物：底座固件（务必先看这一节）

`build/arduino_lwip/` 是**已验证 ping 0% 丢包、延迟 3-6ms** 的最小固件
（227,904 字节，仅 SoftAP + 仓库 lwip + ICMP，无 GUI/shell/XMemory）。

**它是整个项目的黄金基准。任何怀疑「是不是我把东西改坏了」的时刻，
先烧它验证板子和环境。**

> ⚠️ **今天最大的错误就是拿它当实验田**：往里塞 bisect A/B/C 的改动后没有
> 先备份，导致基准被自己改坏，之后所有「底座也丢包」的观察都是假的，
> 据此推翻的每一个结论都不可靠，白烧了 3 小时。
> **规则：基准目录只读。任何实验先 `cp -r` 出副本再改。**

底座的堆布局是关键信息：它的 `stubs.c` 里 `h_alloc` 是一段 first-fit 堆，
范围 `_bss_end → 0x3FFFC000`。因为底座 .bss 很小（无 GUI/XMemory），
**lwip 实际可用堆约 78KB**，所以它用 lwip 默认的大池也毫无压力。

完整固件的 .bss 有 50KB+（arena + XGui + shell），堆只剩 28~36KB，
**这是所有内存类问题的物理根源**。

## 2. 今天定位并修复的根因（全部有数据佐证）

### 2.1 崩溃重启：TX 缓冲所有权改造引入野指针（**我的 bug**）

- 现象：终端关联后约 2 秒 `Fatal exception 29 (StoreProhibitedCause)`，
  `excvaddr=0x02993350`，板子每 20 秒重启一次
- 根因：为修「疑似泄漏」把 `drv_linkoutput` 改成「拷进静态 scratch、把静态
  缓冲当 `ref2save` 交给胶水」，胶水/blob 的完成路径把该指针当 pbuf 处理
- 修法：**回退成底座的原始语义** —— `pbuf_ref(p)` → `glue2esp_linkoutput(p,...)`
  → blob 完成后回调 `esp2glue_pbuf_freed(p)` → `pbuf_free_r221(p)`
- 验证：`txOut=170 / txFreed=165`，差值恒定 5（在途窗口），**没有泄漏**

### 2.2 「WiFi 变哑」：arena 被收包 pbuf 撑满

- 现象：`rxReq` 持续增长但 `rxOk` 冻结，`txOut` 冻结，WiFi 完全停止收发
- 证据：`varPoolUsed=28148/28640`（98%），`rxReq=392 / rxOk=334`
- 根因：完整固件的 lwip 走 `XMalloc_System` → arena；arena 还要装框架
  （XGui/shell 约 16KB），28KB 不够
- 修法：`XVP_GLOBAL_ARENA_BYTES` 24KB → **36KB**
- 效果：从「几秒就哑」变成「稳定 2 分钟以上」

### 2.3 lwip 池被裁得过小（已验证的配置差异）

| 配置项 | 底座（0% 丢包） | 完整固件（改前） |
|---|---|---|
| `PBUF_POOL_SIZE` | 默认 16 | **6** |
| `MEMP_NUM_PBUF` | 16 | **8** |
| `MEMP_NUM_TCP_PCB` | 4 | 1 |
| `MEMP_NUM_TCP_SEG` | 16 | 4 |
| `MEMP_NUM_SYS_TIMEOUT` | 12 | 8 |

已把它们恢复到接近底座的值（12/16/4/8/8）。**池小 = 突发即丢包**。

### 2.4 `drv_input` 少一次 `pbuf_free`（已修）

```c
/* 修复前：lwip 的 input upcall 收到 pbuf 后直接返回错误，不释放 */
static err_t drv_input(struct pbuf* p, struct netif* netif)
{ (void)p; (void)netif; return ERR_VAL; }
```
lwip 的调用方把所有权交给 input 回调，返回而不 free 就是每帧漏一个 pbuf。
该路径主要被「我们不使用的 IPv6/IGMP 多播帧」触发 —— **关掉 `LWIP_IPV6`
并不够，帧照样会到达网卡，丢弃路径必须释放**。

修复后泄漏分档里 `<=128` 档的增长从「每帧 +1」降到「几乎不涨」。

### 2.5 `XMalloc_Hybrid` 池耗尽 = 硬失败（框架级修复，已提交）

`Src/XMemory/XMemory.c` 原文：
```c
if (size <= XMEMORY_HYBRID_THRESHOLD)
    return XMemory_malloc(size, XMEMORY_TYPE_MULTIPOOL);  // NULL 直接抛出去
```
`XMultiPool_malloc` 找不到档位就返回 NULL（`XMultiPool.c:152`），
于是「池耗尽 = 分配硬失败」，在小内存平台上足以掐死整条初始化链。

已改为**池耗尽 → 走慢路径**，五处加回退（`hybrid_malloc`/`hybrid_calloc`/
`hybrid_realloc` 的三个分支），另给 `XMemory_malloc/realloc/calloc/free`
加了槽位判空。释放侧 `hybrid_free` 本就是三路探测，回退出来的块能正确识别。

> 推论：**不要用「压低 `XMEMORY_HYBRID_THRESHOLD`」来绕池耗尽** ——
> 那只是把流量全赶到 arena，arena 爆了是同样的死法。

### 2.6 构建开关 `RODATA_IN_FLASH`（已写入构建脚本调用方式）

不带 `RODATA_IN_FLASH=1` 构建，26KB `.rodata` 会落进 DRAM 变成 `.dram.rodata`，
`_bss_end` 顶到 `0x3fffdfe0`，**系统堆只剩 7200 字节**，WiFi/lwip 分不到内存，
固件卡在 `user_init` 第一行之前（连启动横幅都打不出来）。

识别法：
```sh
xtensa-lx106-elf-nm -td fw_final.elf | grep -E '_heap_start|_bss_end'
# dram0_0_seg 末地址 0x3ffffc00 - _heap_start = 可用系统堆，< 20KB 就要警惕
```

### 2.7 `erase_flash` 会搞坏 I2C 总线（血泪教训）

烧录脚本每轮 `erase_flash` + 全量写 → 起来后 `idle SDA=0`、所有事务
`start refused`、八页全 `nack=393`，看起来像硬件坏了。
**同一块板、同一份固件，跳过 `erase_flash` 直接 `write_flash` 就一切正常。**

**规则：本板烧录只用 `write_flash`，不要 `erase_flash`。**

### 2.8 I2C 探针用了 `0xAE`（关显示）→ 屏幕全黑

`probe()` 用 `kInit[0]`（= `0xAE`，SSD1306 **关显示**命令）做探测，
而 `gui_oled_init()` 又拿探针返回值当「是否已初始化」的判据：
```
probe() 发 0xAE → 判为已初始化 → 跳过 re-init → 0xAF(开显示) 永远发不出去
```
结果：I2C 日志全对（`init NACK=0`、八页 `nack=0 ok`、`i2cErrs=0`），
**但面板一直关着**。修法：探针改发 `0xE0`(NOP)。

### 2.9 事件循环的框架分配（**当前未解决的泄漏来源，见 §3**）

- 泵关闭时：arena 25 秒只涨 212B 然后**完全停住**
- 泵开启时：arena 5 秒涨 768B，**持续增长不回平**

已做的缓解：
```c
/* 只在 UART RX FIFO 真有数据时才通知 shell 并派发事件 */
if ((*(volatile unsigned int*)0x6000001C & 0xffu) != 0) {
    XConsoleShell_notifyInput(&s_staticShell);
    XCoreApplication_processEvents(0);
}
```
`XConsoleShell_notifyInput` 每次都 `XEvent_create` 一个新事件再投递
（`XConsoleShell.c:2858`），投递后是否逐个删除事件对象**待查**——
`XCoreApplication_sendPostedEvents` 里只看到 `XClassDelete(events)`（删除
队列容器），没看到逐个 `XClassDelete(event)`。**这是下一个要查的点。**

## 3. 当前未解决的问题（接手重点）

### 3.1 慢速 pbuf 泄漏（P0）

**症状**：ping 前 2 分钟 0% 丢包，随后逐渐劣化到 100%；
`varPoolUsed` 单调上涨不回平：

```
13956 → 15748 → 17384 → 20364 → 23612 → 27388 → 30720 → 33524 → 34164 ...
```

**速率**：约 150~200 B / 5 秒（随流量）。

**已知**：
- 泄漏在 `<=128` 字节档（释放侧配对统计 `[leak] beat` 里该档
  `alloc - free` 持续增大）
- TX 侧配对正常（`txOut - txFreed` 恒定为 5，在途窗口）
- `drv_input` 缺的那次 `pbuf_free` 已补，泄漏速率下降但未归零
- 泵关闭时 arena **完全稳定** → 与框架事件派发强相关

**下一步建议**（按性价比排序）：
1. **查 `sendPostedEvents` 是否逐个释放事件对象**（`XCoreApplication.c:570`）
2. 在 `esp2glue_alloc_for_recv` 记录每个 pbuf 指针，在
   `esp2glue_ethernet_input` 返回后核对是否被释放（用小型环形记录表）
3. 用 xiaomi/Espressif 的 `system_show_malloc()` 做一次快照对比
   （仅调试用，官方明示不可用于量产）
4. 若短期要交付：把 arena 提到 44~48KB（系统堆降到 12~16KB，风险自负），
   或在泄漏不可控时增加「空闲时自愈重启」的兜底

### 3.2 延迟仍偏高（P2）

曾测到 3.3 秒延迟，根因是 GUI 整屏 I2C 刷屏忙等（8 页 × ~160ms）。
已改成分页 `flush_step` 并默认关闭周期重绘，当前延迟 4~24ms（好）。
若日后要在跑网络的同时高频刷屏，需要把 I2C 提到 400kHz 或改 DMA/硬件 I2C。

### 3.3 未验证项

- 24 小时长时稳定性（受 §3.1 阻塞）
- TCP 服务（espconn 适配层 `XDeviceNetwork_esp8266_sdk.c` 已写好但
  **被 `--gc-sections` 整个裁掉**，因为总装 app 从未调用框架注册；
  若要用它，需在 app 里调用 `XDeviceNetwork_register()` 并确保链接保留）

## 4. 本轮踩过的所有坑（按重要性排序）

1. **不要改基准**。要对比就先复制。今天一半时间浪费在这上面。
2. **烧录禁用 `erase_flash`**（见 §2.7）。
3. **测量前先确认 PC 连的是 `XinYueAP`**。有 3 次「100% 丢包」是因为
   PC 还连着家里路由器（`netsh wlan show interfaces` 里状态为"已断开"）。
4. **计数器突然归零 = 板子在重启**，不要当成「泄漏消失」。用
   `grep -c 'rst cause'` 和 `Fatal exception` 交叉验证。
5. **I2C 探针必须无副作用**（`0xAE` 是关显示，用 `0xE0`）。
6. **`lwip-esp.o` 的胶水层是 WiFi 驱动与应用协议栈的唯一通路**。
   `esp2glue_alloc_for_recv` 返回 NULL = 该包直接丢弃。所谓「让 SDK 独占
   数据面（BYPASS）」是错误设想——SDK 没有平行协议栈，那样做等于丢掉
   每一个包，而且因为没流量所以看起来"很稳定、不崩溃"。
7. **仓库 lwip 与 SDK lwip 不冲突**：`-D` 重命名把仓库 lwip 放进 `_r221`
   私有命名空间，胶水层保留原名，链接期物理隔离。底座 0% 丢包即证明。
8. **Python heredoc 的 `\\r\\n` 会变成真换行**，破坏 C 字符串。
   改 C 代码请用 Edit 工具，或写完后 `grep -c '^$'` 复核。
9. **被取消的后台构建会留下半成品 .o**，之后增量构建可能报大量
   undefined reference。用 `FORCE_ALL=1` 全量重编。
10. **NONOS SDK 是协作式调度**：定时器回调不要超 15ms，不要长时间关中断，
    否则 WiFi 栈被饿死（[官方 API 手册](https://www.espressif.com.cn/sites/default/files/documentation/2c-esp8266_non_os_sdk_api_reference_en.pdf)）。

## 7. 追加：sendPostedEvents 复查结论（桌面端验证，2026-10-20 晚）

### 7.1 事件对象所有权：已确认逐个释放，不是本次慢速泄漏源

`XCoreApplication_sendPostedEvents` 本身只 `XClassDelete(events)` 释放批次容器，
**事件对象在更深一层逐个回收**：

- 已派发：`XThreadData_deliverPostedEvent`（`XThreadData.c:562`）`XClassDelete(event)`；
- 被 `removePostedEvents` / 接收者析构丢弃：`XThreadData_discardPostedEvent`；
- 被 filter 跳过、延迟删除未到期：函数末尾 `XThreadData_push_front_list` 重新入队，
  入队失败的在同函数内 `discardPostedEvent` 回收。

本次修掉两处**只在入队失败（池耗尽）时触发**的泄漏，正是「arena 越满越快」的放大器：

1. `XThreadData_takePostedEvents`：从无锁队列 `receive` 出队后
   `XVector_push_back_1_base` 返回值被忽略——失败即丢事件 + `posted_events` 计数不回退。
   改为失败立即 `XThreadData_discardPostedEvent(&pe)`。
2. `sendPostedEvents` 的 DeferredDelete 重新入队：`push_back` 失败时事件凭空消失。
   改为把事件挂回原条目，由末尾 `push_front_list` 统一 discard。

### 7.2 桌面闸门（可直接复跑）

```sh
cd build && cmake --build . --target XinYueC_Static --config Debug
cd ../bin/Debug && ./XinYueC_Static.exe --test eventloop
```

输出要求三行均为 `差值 +0`：

```

泵路径 20000 轮: system ... (差值 +0)    # tryPostEvent + processEvents（ESP 泵同路径）
空泵   20000 轮: system ... (差值 +0)
```

`--test xcore-application` 同时把 XCoreApplication 全量 21 项测试跑通。
结论：**框架事件循环的投递/派发/丢弃路径在桌面稳态零增长**，§3.1 剩余 P0
应按原计划转向 pbuf 侧取证（§3.1 第 2 步），不要再回头改 sendPostedEvents。

### 7.3 本板架构的一个已知语义坑（尚未影响当前固件）

本板是「os_timer → `processEvents(0)`」单线程泵，**从不进入 `exec()`**，
因此线程 `loopLevel` 恒为 0。按 `XDeferredDeleteEvent_shouldDeliver` 的 Qt 语义，
`deleteLater` 投递的 DeferredDelete 在该结构下**永远不会被派发**，会一直留在队列里
（每个约 64B，且接收者也永不析构）。当前 app 空闲路径没有 deleteLater 调用，
所以不是本次泄漏源；**但若以后在 ESP 侧启用 shell TCP 后端等会 deleteLater 的模块，
必须显式 `XCoreApplication_sendPostedEvents(NULL, XEVENT_TYPE_DEFERRED_DELETE)` 冲刷**。
